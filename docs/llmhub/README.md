## 产品边界

New API 现有能力继续作为交易与执行内核：

- 用户、认证和权限
- API 令牌
- 余额、充值、额度和调用日志
- 模型定价和倍率
- 上游渠道、模型映射和请求转发
- 基础重试和渠道选择

LLM-Hub 扩展能力使用独立的 `hub_*` 领域命名：

- 渠道商资料、认证和归属
- 渠道供给、模型上架和审核
- 独立探测、稳定性、延迟和排名
- 用户路由偏好与平台池回退
- 质量驱动的动态路由
- 渠道商成本、收入和结算账本

## 核心映射

New API Channel 是唯一的上游配置实体。渠道商中心直接创建和维护 Channel，并复用原生渠道表单、校验、多密钥、模型获取和高级参数能力；不得再建立独立的渠道商“分组” CRUD。`hub_supply_groups` 只是与 Channel 一对一的内部供给扩展，不是第二个业务实体，仅保存渠道商归属、供给倍率、探测周期、上架模型和探测状态。Base URL、API Key、完整模型列表、模型映射和高级参数只保存在 Channel 中。

开发时必须遵守以下约束：

- Channel 创建统一经过 `insertChannelsTx`，更新统一经过 `updateTx`；需要事务内同步扩展数据时复用这两个内核，不复制 Channel 字段清单。
- 渠道商接口只能在原生 Channel 流程上增加归属校验、平台字段策略和 `hub_supply_groups` 扩展，不能另写一套渠道校验或持久化逻辑。
- 渠道商前端只能扩展同一个 `ChannelMutateDrawer`，不得复制一份简化渠道表单。
- 供给探测只新增按模型调度、探测结果和上架状态聚合；实际请求必须复用原生 `testChannel`、Adaptor 和定价预检，不能复制协议测试实现。
- 供给探测必须遵守原生 Channel 状态语义：只有 `auto_disabled` 可以在恢复后自动启用，`manually_disabled` 必须保持关闭，直到用户明确启用。

New API 的 `Channel.Group` 是消费者请求的路由分组，不是渠道商中心的“供给分组”。渠道商不能直接修改该字段，由平台统一管理。

计费保留两个相互独立的倍率维度：

- New API 用户组倍率用于消费者等级、折扣和访问权限。
- `hub_supply_groups.price_multiplier` 用于最终命中供给 Channel 的销售倍率。
- 用户实际扣费为“模型价格 × 用户组倍率 × 供给渠道倍率 × 实际用量”。平台抽成与渠道商收入在独立结算账本中拆分，不反向修改本次用户扣费。
- 重试切换 Channel 时必须刷新供给倍率和预留额度；消费日志必须快照渠道商、供给 Channel 和两种倍率，不能依赖事后查询可变配置。
- 同一请求重试时优先排除本次请求内已经失败的 Channel；所有候选都尝试过后才允许回退复用，以兼容只有一个 Channel 或单 Channel 多密钥的场景。

渠道商收益结算首版遵守以下约束：

- 用户成功扣费后，平台按整数额度拆分 10% 服务费与 90% 渠道商收益，拆分结果之和必须严格等于用户实际扣费。
- 收益账本以 `request_id` 唯一，保存消费用户、令牌、渠道商、供给 Channel、模型和计费倍率快照；重试失败日志共享同一 `request_id`，并记录重试序号和单次耗时。
- 同步请求扣费成功后立即结算；异步任务先进入待结算，任务成功后按最终实际扣费结算，退款成功后取消待结算收益。
- 渠道商自用与普通用户调用使用同一结算规则；测试连接和系统探测不产生渠道商收益。
- 消费余额与渠道商收益相互独立，在 `/wallet` 使用“账户余额 / 供给收益”Tab 展示。
- 渠道商先维护结构化收款账户，首版支持支付宝、微信收款码和个人/对公银行卡；提现保存账户快照，后续修改或删除账户不得改变历史提现记录。
- 提现由渠道商申请，管理员可从“待确认”直接确认打款或拒绝；确认打款在同一事务内完成审核和打款，历史“已批准”记录仍可继续完成打款。首版固定使用人民币，实际金额默认按系统汇率填入且允许调整，币种和根据最终金额反算的有效汇率继续留档但不在界面展示，同时记录转账单号或备注。拒绝和人工调账必须填写原因。
- 失败请求不自动扣用户或补偿渠道商；发现上游确实扣费时，由管理员根据请求链路人工调账。
- 第一版实时聚合收益和提现数据，不增加钱包汇总缓存、独立重试明细表、自动代付、KYC、收款信息加密存储或双重记账；实际币种仅作为人工打款事实记录，不建立多币种余额账户。

```text
New API User
  -> hub_provider.owner_user_id

hub_supply_groups（内部一对一扩展，无独立 CRUD）
  -> new_api_channel_id
```

探测与消费者调用必须经过同一个 Channel 执行路径，避免探测凭证与实际售卖凭证不一致。

## 循环路由保护

LLM-Hub 的供给可能来自其他聚合网关，而渠道商也可能把 LLM-Hub 配置为自己的下游兜底，因此不能假设平台拥有一个不会回流的“自营兜底池”，也不能限制渠道商如何使用自己的平台令牌。循环路由保护必须在黑盒条件下生效。

当前采用受控 hop 标记和请求指纹两层强制保护：

- 所有已接入的用户 relay 入口都在令牌认证后、Channel 分配前校验平台签名的 `X-LLM-Hub-Hop`。标准 HTTP、multipart/form、任务提交、Midjourney 和 Realtime WebSocket 发往上游时由平台覆盖并递增该 Header；达到第 3 跳后返回 HTTP `508` 和 `request_loop_detected`。
- hop 签名使用运行实例的 `CRYPTO_SECRET`；多实例必须使用相同密钥。客户端伪造、渠道通配透传或 Header Override 不能制造有效标记，也不能覆盖平台最终写入的值。
- 指纹覆盖已接入入口的非空 `POST` 请求。JSON 在 8 MiB 内按规范化结构计算，字段顺序不影响结果，顶层 `group` 和 `stream_options` 不参与计算；multipart、表单和其他非 JSON 请求按原始请求体计算。
- 指纹包含规范化路径、非认证查询参数和请求体；Gemini `key`、`api_key`、`access_token` 不参与计算，避免同一递归请求换用不同令牌后绕过检测。
- 同一指纹最多允许 3 个请求同时执行；第 4 个请求返回 `508 request_loop_detected`。请求完成后立即释放占位；Redis 可用时在多实例间共享，租约为 10 分钟，异常时回退到当前进程内保护。

hop Header 不能成为唯一依据。LLM-Hub 会主动把它写入自己的上游请求，但第三方 New API 默认重新构建请求，通常不会继续透传任意 Header；外部网关也可能删除它。反过来，请求指纹也不是绝对递归证明：multipart 边界、跨协议转换或外部网关改写请求体都可能改变指纹，合法的完全相同并发请求也可能相似。两层保护共同使用，不能通过单纯增加重试次数代替。

上线前仍需完成以下闭环：

- 生产多实例必须共享 Redis 并监控降级状态。10 分钟租约需要覆盖允许的最长请求时间，若未来支持更长的流式请求，应增加续租或统一请求期限。
- 10 个现有后台任务轮询适配器已在认证/签名后统一写入初始 hop Header，且没有扩大 `TaskAdaptor` 接口；少数绕过 `relay/channel/api_request.go` 的其他历史直连适配器仍待单独审计，不能把本版描述成覆盖所有内部抓取请求。

## 前端边界

- `/`：公开模型与渠道商稳定性首页。
- `/models/:model`：模型维度的价格、稳定性和延迟比较。
- `/providers/:provider`：渠道商公开详情和供给状态。
- 控制台消费者区域：概览、API 令牌、用量与账单、路由偏好。
- 控制台提供者区域：渠道管理、模型上架、审核状态和结算。
- 管理员区域：供给审核、模型定价和平台运营。

当前控制台的渠道管理页面职责如下：

- `/channels`：管理员维护全部底层 Channel，包括渠道商创建的供给 Channel。
- `/provider`：渠道商只维护归属于自己的供给 Channel，并在同一页面完成连接配置、探测和模型上架。
- `/providers`：管理员查看渠道商主体、所有者和供给汇总，并启用或停用渠道商；这里不复制 Channel CRUD。

`/channels` 与 `/provider` 复用同一套列表状态和表格能力，包括搜索、模型/状态/类型筛选、分页及排序，但分别使用管理员全量接口和渠道商归属接口，不能依赖前端过滤实现数据隔离。停用渠道商时，其供给 Channel 全部退出消费者路由，Channel 配置、上架意图和探测历史继续保留；重新启用后，仅原本已上架且当前探测可用的模型恢复路由。

公开页面后续必须支持可抓取内容、稳定 URL、站点地图和结构化数据。用户只看到 LLM-Hub 产品，不在多个系统之间跳转。

渠道商公开首页首版已采用固定模板：根域名继续展示按模型聚合的全平台稳定性梯子，`{slug}.llm-hub.store` 展示单个渠道商的品牌资料、已上架模型、当前供给数、价格起始倍率、平均延迟和 7 日稳定性时间线。模板与根首页保持同一套视觉语言，但不参与跨渠道商排名；渠道商只能修改资料和供给配置，不能注入自定义 HTML、CSS 或 JavaScript。首版预览入口位于渠道商中心，公开页不展示 Channel 名称、Base URL、密钥、内部错误信息或消费者路由细节。

当前已实现渠道商公开资料编辑和稳定 slug：渠道商通过认证后的 `/api/hub/provider` 更新名称、slug、官网、简介和 Logo URL，后端按用户归属校验并只更新这些公开字段，不会覆盖管理员维护的状态或供给配置。公开接口按 slug 查询，数字 ID 只用于内部关联；根路径根据 Host 区分平台首页与渠道商首页。本地使用 `{slug}.localhost:3100` 验证，`/providers/:slug` 只作为本地 IP 访问或故障排查的路径回退。

渠道商入口不创建“专属 Token”或订阅关系，渠道商身份完全由推理请求的 Host 决定。同一个 New API Token 可以调用根域名，也可以调用任意有效渠道商子域名：

```text
{slug}.llm-hub.store/v1
  -> 优先该 slug 对应渠道商已上架且当前可用的 Channel
  -> 渠道商候选失败或不存在时进入平台公共池
  -> 公共池排除该渠道商的全部 Channel，避免再次绕回

llm-hub.store/v1
  -> 按原有 New API 规则选择平台公共池
```

- Host 只影响本次请求的路由偏好，不修改 Token、用户分组、模型权限、余额或扣费规则。用户从渠道商子域名登录、创建 API 密钥和打开 CC Switch 时始终保留当前子域名；Claude 和 Gemini 使用当前 origin，Codex 使用当前 origin 加 `/v1`。
- `RetryTimes=2` 时最多发起 3 次上游尝试：前两次优先选择该渠道商且严格排除本请求中已失败的 Channel，最后一次保留给公共池。渠道商没有候选时不空等，立即切入公共池；进入公共池后仍严格排除入口渠道商及本请求已经失败的 Channel。该策略不额外增加 New API 的总重试次数。
- 未知渠道商子域名的推理请求返回 `404`，已停用渠道商返回 `503`。根域名、IP、`localhost` 和保留的系统子域继续作为平台入口。
- 成功与失败日志都快照 `hub_requested_provider_id`、`hub_requested_provider_slug`、`hub_routing_phase`、`hub_provider_fallback`、实际命中的 `hub_provider_id`、`hub_supply_group_id`、`supply_multiplier`、`billing_ratio` 和尝试链 `use_channel`，用于完整追踪优先路由、重试、兜底和计费。
- 内存与数据库 Channel 选择都只使用 `abilities.enabled=true` 的模型能力。仅写在 `Channel.Models`、但尚未上架或当前检测不可用的模型不能进入消费者路由。

根域名公开榜单现已接入真实 V2 数据：`GET /api/hub/public/home` 一次批量读取启用渠道商、供给扩展、当前探测目标和最近 7 日样本，再按模型聚合渠道商公开行，避免按渠道商逐个请求产生 N+1 查询。首页只展示已上架模型；已经上架但当前检测失败的模型继续展示并明确标记，未上架模型不进入榜单。公开响应只包含渠道商公开资料、在线状态、供给数量、最低供给倍率、稳定性、样本量、成功请求平均延迟、首字 P50/P95 和 28 段时间线，不返回 Channel 名称、Base URL、密钥或内部错误。模型系列暂按模型名称规则归入 Anthropic、OpenAI、Google、xAI、DeepSeek、阿里、字节、智谱或其他，未知模型的长期元数据来源仍待设计。

公开榜单与探测指标遵守以下规则：

- 文本生成探测使用流式请求，在不增加探测次数的前提下同时记录第一个有效正文或推理增量的 `first_token_ms`，以及完整响应结束时的 `latency_ms`。图片、Embedding、Rerank 和 Responses Compact 等不适用首字指标的端点继续使用非流式探测。
- 综合分满分为 10000 基点：7 日可用率占 80%，首字 P50 占 10%，首字 P95 占 5%，样本置信度占 5%。首字 P50 在 10 秒时速度分降至 0，P95 在 20 秒时降至 0；图片等无首字指标的端点改用可用率 90% 与置信度 10%，避免因指标不适用而被错误降权。
- 样本置信度同时考虑 7 日有效样本量和 56 个三小时桶；单个桶只有达到该端点计划探测量的 80% 才有效。少于 4 个可计分样本时不产生综合分。
- 余额不足、平台模型未定价、无效端点配置、鉴权失败、模型不存在及平台自身探测错误不计入可用率；真实上游连接、响应和超时失败继续计入。余额不足若持续发生，已上架模型仍留在榜单，但从暂停开始在 7 天内线性增加到最高 10% 的排名扣分；同一渠道商有多个供给渠道时，从最后一个可用供给也进入余额暂停时开始计时。

生产接入和后续产品项遵守以下边界：

- **生产域名接入**：应用层已支持 `{slug}.llm-hub.store`。生产发布前配置 `*.llm-hub.store` 通配 DNS 和 TLS，设置 `HUB_PROVIDER_ROOT_DOMAIN=llm-hub.store`、`SESSION_COOKIE_DOMAIN=llm-hub.store`，并把 `TRUSTED_PROXIES` 收紧为应用直接连接的反向代理 IP 或网段；反向代理必须使用 `proxy_set_header Host $host` 保留原始 Host。Cloudflare 使用一条代理状态开启的 `* -> 源站` 通配记录即可自动承接新增 slug，无需逐个调用 DNS API。应用保留 `www`、`api`、`app`、`admin`、`status` 等系统 slug，渠道商 slug 全局唯一且不会随名称自动变化。
- **登录与 OAuth**：Refresh Cookie 共享到根域和渠道商子域；OAuth state 保存原始 origin 与路径，由根域完成第三方回调后再返回原渠道商子域。仅当请求直接来自配置的可信反向代理时，后端才接受 `X-Forwarded-Proto`，避免客户端伪造该头绕过 Origin 校验。
- **回退计费**：每次请求按最终实际命中的 Channel 及供给倍率正常扣费和结算。命中公共池其他渠道商时，收益归实际提供服务的渠道商，不归入口子域对应渠道商；首版不引入差价补贴、渠道商预算或二次分佣。
- **自定义程度**：首版只支持 Logo、名称、官网和简介；模型排序、主题色、营销区块和自定义域名暂不开放，避免把公开页变成不可审计的独立站点。
- **SEO 发布条件**：动态页面先验证真实访问和稳定性数据，再补 slug、canonical、站点地图、结构化数据和抓取策略，避免把未稳定的 URL 体系提前固化。

## 实施顺序

每一步在实现前先确认页面流程、数据归属、改动范围和明确不做的内容。

1. 验证官方基座的本地构建与登录、令牌、调用链路。
2. 建立 LLM-Hub 品牌外壳和角色导航，不改业务逻辑。
3. 移植公开首页，只接真实的只读排名数据。
4. 为 Channel 增加渠道商归属和供给扩展。
5. 接入独立探测和上架审核。
6. 设计并实现质量驱动路由。
