# LLM-Hub V2 开发基线

## 基座

- 产品代码基于 New API 官方提交 `0ab02020603d22e5613bc4cf46bfab06f8567769`。
- LLM-Hub 作为独立产品演进，不自动合并 New API 上游版本。
- 上游安全修复和重大缺陷按需审查后 cherry-pick 或手工迁移。
- New API 的许可证、NOTICE、第三方许可证和项目归属信息必须保留。
- Radar V1 保存在分支 `codex/archive-radar-v1-20260803`，不承担 V2 的账户、令牌或计费职责。

## 产品边界

New API 现有能力继续作为交易与执行内核：

- 用户、认证和权限
- API 令牌
- 余额、充值、额度和调用日志
- 模型定价和倍率
- 上游渠道、模型映射和请求转发
- 基础重试和渠道选择

LLM-Hub 扩展能力使用独立的 `hub_*` 领域命名：

- 渠道商资料、认证和归属
- 供给分组、上架和审核
- 独立探测、稳定性、延迟和排名
- 用户路由偏好与平台池回退
- 质量驱动的动态路由
- 渠道商成本、收入和结算账本

## 核心映射

一个供给分组对应一个 New API Channel。Base URL、API Key 和模型映射只保存在 Channel 中，LLM-Hub 不复制上游凭证。

```text
New API User
  -> hub_provider.owner_user_id

hub_supply_group
  -> new_api_channel_id
```

探测与消费者调用必须经过同一个 Channel 执行路径，避免探测凭证与实际售卖凭证不一致。

## 前端边界

- `/`：公开模型与渠道商稳定性首页。
- `/models/:model`：模型维度的价格、稳定性和延迟比较。
- `/providers/:provider`：渠道商公开详情和供给状态。
- 控制台消费者区域：概览、API 令牌、用量与账单、路由偏好。
- 控制台提供者区域：渠道供给、分组、审核状态和结算。
- 管理员区域：供给审核、模型定价和平台运营。

公开页面后续必须支持可抓取内容、稳定 URL、站点地图和结构化数据。用户只看到 LLM-Hub 产品，不在多个系统之间跳转。

## 实施顺序

每一步在实现前先确认页面流程、数据归属、改动范围和明确不做的内容。

1. 验证官方基座的本地构建与登录、令牌、调用链路。
2. 建立 LLM-Hub 品牌外壳和角色导航，不改业务逻辑。
3. 移植公开首页，只接真实的只读排名数据。
4. 将 Channel 包装为渠道商的供给分组。
5. 接入独立探测和上架审核。
6. 设计并实现质量驱动路由。
7. 设计并实现供应成本与结算账本。

任何一步出现许可证、计费一致性、跨数据库写入或生产兼容问题时，停止实现并先确认方案。
