# 路由与平台兜底实现规格

状态：开发基线（倍率路由版）。产品和算法方案见 [routing-and-fallback-design.md](routing-and-fallback-design.md)。

本文只说明如何把已确认的方案接入现有代码，不重新定义产品规则。实现遵守“小改动、复用 New API、每步可验证、随时可回滚”。

## 当前生效口径

- 新 Token 不再把四个服务档位作为实际选择项，而是按模型族保存倍率闭区间；倍率范围为 `0.01-100.000`，步进 `0.001`，允许超过 `1.000`。`1.000` 只是平台官方基准倍率，不是上限。
- 渠道商子域 Token 不使用自由范围，只能选择该渠道商已经发布的模型族和精确倍率；请求仍按当前 Host 优先该渠道商，失败后在同一倍率约束内进入平台公共池。
- “特价 / 经济 / 标准 / 高品质”仅为前端按最高选中倍率显示的辅助标签，不参与候选过滤、计费或跨档兜底。旧 Token 和未携带 `hub_routing_policy` 的请求继续走旧 New API/服务档位兼容路径。
- 实际用户扣费沿用 New API 的 `BillingSession`。新策略 Key 的计费基准固定为 `1x`，不乘旧用户组倍率；最终费用使用模型价格、最终命中渠道倍率和其他请求倍率。重试只对最终成功渠道结算收益；失败尝试不扣用户、不记渠道商收益。
- 渠道商平台服务费在最终 Channel 选定时与归属、供给倍率一起快照，使用该渠道商覆盖值或当时的全局默认值；后续修改费率不影响本次请求或已创建收益记录。

## 1. 首版范围

### 继续复用

- `Channel`：唯一上游配置实体。
- `Ability`：模型是否可路由的基础能力记录。
- New API 原生 `priority`、`weight`、重试和扣费流程。
- `HubSupplyGroupProbeTarget`、`HubSupplyGroupProbeSample`：模型探测数据。
- `HubRelayAttempt` 和请求日志：单次请求尝试追踪。
- 现有手动禁用、自动禁用语义：任何自动逻辑不得恢复手动禁用渠道。

### 首版明确不做

- 不重写 New API 渠道检测协议或适配器。
- 不新增专属 Token、订阅关系或第二套 Channel CRUD。
- 不跨服务档位兜底。
- 不新增独立调度数据库、尝试明细表或钱包汇总表。
- 不把真实请求日志 JSON 扫描放进请求热路径。
- 不实现实时容量调度、探索流量、公平分流、用户请求半开恢复或机器学习评分。
- 不在本轮实现渠道商实名认证和一人多渠道商限制。

路由模式只保留一个总开关，避免多个独立开关组合出不可解释状态：

```text
static   使用现有渠道商优先、priority + weight 选路
observe  选路不变，只采集并展示可观测数据
active   后续才允许健康数据影响选路
```

默认 `static`。在真实请求指标、配置多实例同步和回滚验证完成前，不允许进入 `active`。

## 2. M0：兼容性与回归基线

这一步不引入动态评分，先保证现有流程的边界没有被实现文档误导。

### 2.1 保留当前渠道选择语义

服务档位公共池当前采用两级选择：

```text
先按渠道商选择
  -> 再在该渠道商内部按 New API priority + weight 选择 Channel
```

不能在接入健康分时悄悄改成全平台先比较 `priority`。全局 priority 和渠道商公平分流是两个不同产品策略，后续若要改变必须单独讨论。

内存 Channel 缓存在每次完整刷新时，同时预建“服务档位 + 模型 + 渠道商”的有序候选桶。请求热路径不再临时按渠道商重新分组或排序全部候选，但仍在最终选择前复查当前端点能力、渠道商状态、Channel 状态和本次失败 Channel 排除。数据库直查路径继续使用原有查询与排序，作为缓存关闭时的兼容行为。

服务档位使用严格的本次失败 Channel 排除；普通 New API 选择保留原有“候选耗尽时可复用”的兼容语义，不能把严格排除扩展到所有渠道流程。

### 2.2 兼容检查

- [x] Affinity 命中路径检查渠道商仍为 active，不能只检查 Channel 和 Ability。
- [x] 服务档位请求不被 New API Affinity 的 `SkipRetryOnFailure` 阻止同档重试和平台兜底，根域名和子域名都适用。
- [x] 自动恢复写库排除手动禁用状态，避免探测先读到自动禁用、管理员随后手动禁用、旧探测结果最后又覆盖为启用。
- [x] 单个模型不支持或端点不匹配时，不通过通用渠道错误路径误伤同 Channel 的其他模型；文本/图片按现有 `ProbeKind` 粗粒度隔离，连接、TLS、基础认证或余额等基础设施故障才保留 Channel 级处理。
- [x] 循环保护不等同于“已访问渠道商集合”。平台公共池排除入口渠道商和本次已失败 Channel；实际 relay 入口同时校验平台签名 hop，非空 POST 再使用并发指纹保护。

`SkipRetryOnFailure` 是 New API Affinity 规则中的一个选项：请求命中粘性 Channel 后，一旦该 Channel 失败就直接返回错误，不再尝试其他 Channel。这个语义适合要求固定上游的普通 New API 场景，但与 LLM-Hub“同档兜底”的产品规则冲突。因此服务档位请求必须忽略该停止重试选项；普通 New API 请求继续保持原行为。

### 2.3 端点发布边界

现有 `Ability` 和供给发布流程继续以 `Channel + Model` 作为可路由单元，不新增端点字段。首版复用探测目标的 `ProbeKind` 在候选选择时隔离文本和图片资格：任一类型健康时保留模型 Ability，文本请求只使用文本健康候选，图片请求只使用图片健康候选，全部类型失败后才删除 Ability。

这里的“端点”是同一模型使用的 API 协议或请求路径，例如 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 或图片生成接口；不是“具体模型”的别名，也与管理员直接创建平台自有 Channel 无关。

这仍是粗粒度隔离，不等于 Chat Completions、Responses、Anthropic Messages 等协议端点分别上架。若要让这些端点真正独立进入 Ability，必须另开设计任务，不能在健康分接入时顺带改变发布语义。

新建渠道的模型默认具有上架意图，现有 `hub_supply_probe` 首次检测成功后自动进入供给池；后续手工上架/下架时，发布状态、供给组汇总状态、Channel 状态和 Ability 重建仍在同一个数据库事务中完成。逐模型关闭自动检测时，同一事务删除其探测目标并按上架意图重建 Ability；重新开启时立即创建 `pending` 目标并在检测成功前退出路由。事务失败不会提交设置，成功后才刷新运行时缓存。运行时缓存也已改为串行构建、完整发布，失败时保留旧缓存；完整刷新同时替换供给倍率、“已配置供给渠道”集合和逐模型免检测资格，避免删除供给扩展后残留上一代归属。普通选路和 Affinity 选路在持有 Channel 缓存读锁时同时带出供给归属、提供商状态、供给组和倍率，后续定价、重试预留、日志与收益结算复用该请求快照，不再读取另一缓存代的供给倍率。

钱包首次预扣和更高价格重试的补差都使用数据库条件更新，余额不足时在发起上游请求前停止；钱包和 Token 的最终差额也强制直写主库，不通过内存批量更新队列。用户/Channel 的累计用量与请求次数仍可批量更新，它们不是资金权威数据。

失败请求的预扣退款使用独立的 `billing_refunds` 恢复记录。记录以 `request_id` 唯一约束，只保存用户 ID、令牌 ID、资金来源、订阅 ID 和各项额度，不保存令牌明文。失败收尾先持久化该记录，再异步执行退款；钱包、订阅基础预扣、订阅重试补差和令牌额度在同一主库事务中回退，成功后才标记 `complete`。进程在异步退款前后中断，或一次退款事务失败时，记录保留为 `pending`，系统任务每 15 秒扫描并重试，因此不会因内存中的 `refunded` 标记提前写入而永久丢失用户预扣额度。失败上游是否已经扣费仍维持首版“只保留排查记录、不自动人工核账”的边界。

同步请求的用户资金已经提交但 Token 差额写回失败时，`BillingSession` 写入 `billing_token_adjustments` pending 记录；恢复任务每 15 秒在同一事务中完成 Token 差额和记录状态更新。成功异步任务的最终差额改用独立的 `billing_task_settlements`：以持久化 `task_id` 唯一，保存预扣、实际额度、资金来源和原始 `request_id`；成功终态 CAS 与结算意图在同一主库事务提交，后续在同一主库事务内调整钱包或订阅、Token 数据库额度、用户/渠道 `used_quota`、持久化 `Task.Quota` 和结算状态。该路径绕过内存批量余额队列，零差额也保留完成记录；事务任一环节失败会整体回滚并保留 `pending`，恢复任务按下一次尝试时间退避，成功后才释放渠道商收益。异步任务失败退款仍复用 `billing_refunds`，在同一事务内完成资金退款、Token 退款和 `Task.Quota=0`。这些恢复记录都不保存 Token key。主库结算与独立日志库仍不宣称跨库原子：完成标记可避免正常重复恢复，但不能消除进程在日志写入与标记更新之间的极短重复或丢日志窗口。

异步任务提交时将模型价格、模型倍率、基础分组倍率、供给倍率、最终综合倍率和附加倍率写入 `TaskBillingContext`。任务完成后的 token 重算优先使用这些快照，运行期间修改模型或供给倍率不会重定价已提交任务；只有历史任务没有有效模型倍率快照时才兼容回退当前配置。

异步任务的退款、差额和渠道商收益相关日志会沿用任务提交时的 `request_id`，同时保留 `task_id` 作为任务阶段标识；没有原始请求 ID 的历史任务仍只能按任务 ID 查询。

进入渠道选路后的服务档位请求按一次客户端请求只保留一条请求级最终记录：同步与异步任务成功时由消费日志保存完整 `hub_attempts`，最终失败时始终补一条错误日志，即使关闭了错误日志开关。中间失败仍写本地运行日志、执行原有自动禁用判断并追加 `hub_attempts`，但不再逐次写数据库错误日志。任务提交在选中渠道后发生的 `LocalError` 也会追加失败尝试，但标记为非渠道健康样本，不触发重试或自动禁用；生成请求上下文、解析原任务或渠道选择阶段的失败只写最终日志，尝试链为空。普通 New API 分组继续保留原有逐次错误日志行为。完整尝试链在管理员日志详情中展示，包含每次尝试的渠道商、Channel、端点、结果、延迟、TTFT、倍率和错误分类；非管理员日志序列化会删除 `hub_attempts`，权限边界不依赖前端隐藏。

渠道商收益的 `pending` 增加可空 `settlement_deferred` 门槛。同步请求先可靠准备收益，准备失败会终止用户结算；用户扣费成功后，最终 gross、平台服务费、Provider 收益和 `settlement_deferred=false` 在同一事务发布，再立即结算。发布已成功但结算失败时，系统任务每 15 秒按最终 gross 补结算。异步任务在提交和运行期间固定保持 `true`，成功终态先完成 `billing_task_settlements`，再原子发布最终 gross 并释放收益，避免恢复器抢在最终额度写入前按预估额度结算。失败退款与待结算 Provider 收益取消在同一主库事务完成；若收益已经结算，退款事务会失败并保留 pending，禁止平台同时承担用户退款和 Provider 收益。

文本、音频和任务提交不再吞最终结算错误：未形成持久化结算时返回不可重试的本地账务错误，且不增加用户/Channel 用量统计；资金已经提交或 Token 差额已形成持久化恢复记录时，按已接受结算继续处理。固定价格音频现在显式携带 `ModelPrice`。普通同步响应可能已由上游适配器写出，此时 HTTP 状态无法完全重写，账务日志和恢复记录仍是权威结果。

异步任务轮询使用 `(channel_id, upstream_task_id)` 复合键。同一平台的两个上游都返回 `1` 时，不再互相覆盖任务、退款或收益归属。

### 2.4 固定渠道令牌与供给定价保护

管理员可以继续使用 New API 原有的固定 Channel Token 调试能力。该能力只在传统分组中保留历史上的“直接指定渠道”语义；服务档位请求仍必须经过同档 Ability、当前请求的文本/图片资格、供给渠道商状态和入口子域归属校验，固定渠道不会因为校验失败而静默切到另一个渠道。

供给计费复用 `model/hub_supply_pricing.go` 的现有内存缓存。缓存未命中时只回查一次 `HubSupplyGroup` 归属：无供给扩展的管理员平台渠道按基础倍率继续运行；数据库已有供给扩展但缓存没有完整倍率快照时，计费在上游请求前失败关闭。这样可以避免供给渠道被误当作平台自营渠道并按 `1x` 计费，同时不为平台渠道新增第二套归属表。

### 3.3 管理员排行粒度

优先按以下维度展示探测状态：

```text
Channel + Model + EndpointType + ProbeKind
```

至少展示：

- 渠道商、Channel、模型、端点、解析出的端点和供给倍率。
- 当前 Probe 状态、模型上架状态、Channel 手动/自动禁用状态。
- 最近探测时间、最近成功时间、最近延迟和 TTFT。
- 探测样本数、成功率、错误码和最后错误。
- 公开排行分及其可用率、TTFT、样本置信度等已有分项。
- 渠道商归属、服务档位资格和跳过原因。

暂无样本、已禁用和未上架渠道必须通过左连接展示，不能只展示成功探测过的渠道。

真实请求既在单条请求日志中保留 `hub_attempts`，也通过 M4-A/M4-B 独立聚合到管理员“真实请求指标”；它仍不混入探测排行，也不参与当前选路。尝试记录包含 `model`、`endpoint_type`、`sample_source` 和失败分类。TTFT 只取流式响应中的有效文本或推理增量；角色、usage、结束事件、图片元数据和非流式请求不会生成 TTFT。

### 3.4 探测口径

探测和真实请求不能一比一混合。探测请求体量小、并发低、成功率可能偏高，只能作为弱先验。现阶段：

- 探测结果用于模型是否可提供和公开状态展示。
- 真实请求先用于单请求追踪，不参与自动健康分。
- 自动端点模式的最终样本必须展示解析端点和尝试链，不能把多次端点尝试的总耗时冒充单端点耗时。
- TTFT 必须区分“首个有意义内容”和“首个上游事件”；图片、Embedding 等非流式请求只展示完整响应时间。
- 日志中的秒级 `UseTime` 不用于毫秒级 TTFT/P95 排名。

## 4. M2：Affinity 的最小兼容修复

Affinity 继续复用 `service/channel_affinity.go`，不新建 Hub 专属缓存系统。

实现状态：已完成最小兼容修复。服务档位缓存键强制包含规范化模型；命中后仍复用现有 Provider、Channel、Ability、请求路径和档位资格检查；失效命中或可重试的上游失败会清除旧映射并进入现有同档重试。普通 New API 分组继续遵守原有 Affinity 配置。

### 4.1 已确定语义

Affinity 是保留上游缓存和会话收益的软粘性，不是永久绑定，也不是质量评分。轻微变慢不能立即切换；只要渠道仍可用，就优先保留。

命中后必须重新检查：

- 渠道商 active、Channel 状态和手动禁用状态。
- 当前模型 Ability、请求路径和服务档位资格。
- 端点能力和当前业务发布状态。

认证失败、模型不支持、渠道商禁用、Channel 进入自动故障状态或请求无法继续时，清理当前 Affinity 并走同档重试和平台兜底。Affinity 不能阻止 LLM-Hub 服务档位兜底。

### 4.2 范围控制

现有通用 Affinity 缓存键是可配置的，改动它会影响 Codex、Claude 等既有缓存和请求覆盖逻辑。首版只要求服务档位使用的规则必须包含规范化模型，避免不同模型共用映射；端点和入口 Host 先通过命中后的能力、路径和渠道商检查隔离，不新增第二套 key 体系。

如果后续出现可复现的“不同端点或入口 Host 互相污染”，再为通用 Affinity 增加字段并单独回归，不在动态评分任务中顺带完成。

### 4.3 模型和端点故障边界

首版不新增模型故障状态机或独立表，复用现有错误码、当前请求的 Channel 排除和供给探测状态：

- 连接、TLS、基础认证、余额和无可用 Key 等可能影响整条 Channel 的故障，继续沿用 New API 的 Channel 级处理。
- `model_not_found` 和 `channel:model_mapped_error` 只表示当前模型不可用，不触发整条 Channel 自动禁用。
- 适配器明确不支持当前请求端点时返回 `channel:endpoint_unsupported`；它只影响本次 `Channel + Model + Endpoint` 尝试，沿用现有同档重试并排除当前 Channel，不跨档，也不关闭该 Channel 的其他模型和端点。
- 同一模型存在文本和图片探测目标时，模型任一 `ProbeKind` 健康即可保留模型级 Ability；实际候选和 Affinity 再按请求路径选择 text/image 资格。供给组此时显示 `partial`，只有所有已上架模型的所有探测类型都不可用时，Channel 才自动退出路由。
- 未知转换错误仍保留原有客户端错误和跳过重试语义，不能通过匹配错误文案自动升级为渠道故障。

该边界不改变 RetryTimes、服务档位资格、Ability 表结构、探测任务、扣费或收益。缓存开启、数据库直查和 Affinity 命中使用同一 `ProbeKind` 判断。后续如果真实流量证明需要跨请求的 `Channel + Model + Endpoint` 熔断，再基于现有探测和短窗口指标单独设计，不能在本次修补中暗加持久状态。

## 5. M3：真实请求健康评分，后置到 observe/active

这一模块不是首版静态路由的前置条件。M3 先补齐真实请求的结构化观测字段，M4-A 再提供只读聚合；两者都不改变当前选路和结算。

### 5.1 必须先补齐的最小字段

真实请求尝试需要可稳定聚合：

```text
model
endpoint_type
sample_source = probe / real_request
skip_reason
```

M3 已完成真实请求观测字段的最小补齐：

- 服务档位真实请求写入结构化 `hub_attempts`，`sample_source=real_request`；M3 阶段不扫描请求日志 JSON，也不参与当前选路。
- 每次尝试记录规范化 `model` 和依据最终请求格式解析出的 `endpoint_type`，避免用模型名称猜测图片、Responses 等端点。
- `first_event_ms` 与 `first_token_ms` 分开记录：前者表示上游首个事件，后者只在首个有意义的文本或推理增量出现后记录；图片元数据、usage、生命周期事件和 `[DONE]` 不伪造 TTFT。
- 失败尝试暂以 `skip_reason=failed_attempt` 表示它不会作为当前请求的成功服务样本；容量、熔断或未来动态筛选原因暂不写入，避免提前引入未实现的调度语义。
- 重试开始时重置本次尝试的首事件和首 token 计时，避免把前一个失败渠道的时间带入后续渠道。

这些字段首版可以继续放在结构化请求日志中；M4-A 已补充独立的 Redis/时间桶聚合，但不能通过扫描 JSON 日志实现自动排行或热路径选路。

### 5.2 评分公式的接入原则

产品方案中的 `A/L/C/R/H` 公式保留为后续候选公式，首版不让它参与选路。未来接入时必须：

- 明确探测和真实请求对成功率、P95 的共同计算口径。
- 明确 TTFT 的数据定义，不能混合首个事件和首个有意义 token。
- 明确没有并发上限或 Redis 数据缺失时的状态，不能伪造容量分。
- 保留现有 provider-first、provider 内 `priority + weight` 顺序。
- 先做 `observe`，再做 `active`；`active` 出现异常时回到 `static`。

### 5.3 暂不实现的动态能力

以下内容记录为后续阶段，不进入当前 M1/M2：

- `CapacityScore`、Channel/渠道商 inflight 和并发租约。
- `healthy -> degraded -> open -> half-open` 新状态机。
- 用户请求触发的半开恢复；恢复优先复用现有供给探测任务。
- fairness factor、provider base weight 和 5% exploration。
- 从请求日志实时聚合真实流量并驱动热路径选路；M4-A 已完成只读聚合，但仍不驱动热路径选路。

Redis 后续只承载短窗口计数和容量租约，数据库中的 Channel 状态、探测样本和账务记录才是权威。Redis 不可用、重启或健康数据过期时，状态为 `unknown`，降级回 `static`，不因为统计故障返回 503，也不启用探索流量。

### 5.4 M4-A：真实请求聚合（已实现）

M4-A 建立独立的 `hub_routing_metrics` 时间桶表，避免污染模型广场使用的 `perf_metrics`。真实请求在最终成功或最终失败时，将本次完整尝试链写入聚合器：

```text
model + endpoint_type + provider_id + channel_id + bucket_ts
```

当前只聚合尝试数、成功尝试数、总耗时和有意义首 token 的平均值。失败尝试也计入尝试数，因此 `success_rate` 是 Channel 尝试级成功率，不等同于用户请求级成功率；一次请求重试两次会产生两条尝试样本，这是为了评估选路候选，不用于计费。

聚合器复用现有性能指标的内存桶、Redis 活跃桶和定时落库/清理机制，管理员只读接口为：

```text
GET /api/hub/admin/routing-metrics
```

支持按模型、端点、渠道商、Channel 和时间范围查询，并按尝试数降序返回。该接口和聚合数据暂不参与选路、优先级、权重、服务档位边界、扣费或收益结算；P95、并发容量、熔断和动态评分留到后续模块，避免把观测数据直接变成调度行为。

管理员页面已接入 `/system-settings/models/channel-health-routing`。页面上半部分继续展示探测状态与现有 7 天排行，下半部分“真实请求指标”独立展示最近 24 小时的尝试数、尝试级成功率、平均完整响应耗时和平均 TTFT。端点标签按实际 `endpoint_type` 展示，不能把 Embeddings、图片、Gemini 等请求误标为 Chat。两部分不合并成一个分数，避免把弱探测样本和真实流量误认为同一口径。

M4-A 已完成以下验证：

- 后端聚合、数据库 Upsert、查询过滤和清理测试通过。
- 前端类型检查、lint、格式检查和生产构建通过。
- 本地重新构建嵌入式前端并重启后，菜单、页面、探测表格和真实请求指标表格均可加载，浏览器控制台无页面错误。
- 本地 Go 服务会把 `web/dist` 嵌入可执行文件；前端构建完成但服务二进制未重新构建时，新路由会被旧前端重定向到默认设置页。验收新页面前必须重新构建并重启本地服务。

真实请求和探测数据分开展示。探测样本对后续可信度的贡献最多按弱先验计算，例如：

```text
effective_samples = real_samples + 0.25 × min(probe_samples, 20)
```

这个权重、20 条样本和延迟时间窗属于待真实数据校准的实现参数，不能在没有运行数据时当成产品承诺。

### 5.5 M4-B：短窗口真实请求指标（已实现，observe-only）

M4-B 在 M4-A 的记录入口上增加短窗口观测，不新建请求明细表，也不改变当前静态选路：

- 以 1 分钟为桶，保留最近 60 分钟的内存聚合；每次清理只删除超出窗口的数据，进程重启后短窗口自然从空开始。
- `request_count_5m` 和 `success_rate_5m` 固定统计当前桶及前 4 个桶；`request_count_60m` 和 `success_rate_60m` 统计最近 60 个桶。失败尝试计入分母，成功尝试计入分子。
- `latency_p50_ms`、`latency_p95_ms`、`first_token_p50_ms` 和 `first_token_p95_ms` 默认统计最近 15 分钟；百分位只使用成功尝试，TTFT 只使用实际记录到的有意义首 token 样本。没有样本时返回空值，前端显示 `-`。
- 百分位使用固定 16 桶直方图，避免保存每条请求和无界排序；返回值是桶上界的近似值，不宣称为精确百分位。
- Redis 可用时，短窗口写入现有记录管道中的 `hub-routing-window:*` 分钟桶，并设置过期时间；查询会合并多实例 Redis 数据，替换本机同一分钟副本，避免重复计数。Redis 不可用时使用本机内存，重启或进程异常不会补回短窗口。
- 短窗口不落库；24 小时平均值仍来自 M4-A 的 `hub_routing_metrics`。因此页面同时显示短窗口 P50/P95 和 24 小时平均值，不能把两者当作同一统计口径。
- M4-B 仅供管理员观察，仍不得改变候选集、Channel `priority/weight`、重试、Affinity、服务档位、扣费或收益。动态健康降权必须另行设计、配置并先经过 `observe` 验证。

### 5.6 M4-C：失败归因观测（已实现，observe-only）

M4-C 复用现有 `NewAPIError` 和响应状态，不复制 `shouldRetry`，只为失败尝试增加稳定的 `failure_class`：

- `upstream`：连接、超时、429、5xx、上游响应读取或响应内容故障。
- `configuration`：鉴权、模型不存在、Channel Key、模型映射、端点配置或价格配置问题。
- `client`：请求体、参数、权限或敏感词等客户端不可通过换 Channel 修复的问题。
- `loop`：平台生成的 `request_loop_detected`，不能再次进入重试或计费。
- `response_started`：已经开始向客户端写响应后才出现的失败，不能重复输出。
- `unknown`：无法可靠归因的其他错误，保守保留，不自动解释成渠道故障。

失败类别写入结构化 `hub_attempts`，并在短窗口接口返回 5 分钟/1 小时类别计数。原有总尝试数和总成功率继续保持全尝试口径，避免历史数据或管理员配置改变后出现不可比的指标；失败类别只为后续 `可切换请求成功率` 和人工排查提供输入，目前不参与健康分、重试、自动禁用、选路或账务。

M4-C 同时补充两条自动禁用边界：平台生成的 `request_loop_detected` 固定不关闭 Channel；`channel:model_mapped_error` 只表示当前模型或端点映射失败，不关闭同 Channel 的其他模型。两者仍保留在请求尝试日志中，供管理员排查。

### 5.7 M4-D：可切换成功率观测（已实现，observe-only）

M4-D 在 M4-B 的短窗口桶上增加可切换请求口径：成功请求始终计入；`upstream`、`configuration`、`response_started` 和 `unknown` 失败仍计入候选健康分的观察分母；`client` 与 `loop` 失败排除，因为更换渠道不能修复用户请求或平台循环。客户端 Context 已取消时优先归为 `client`，不会因响应已经开始而误伤渠道健康。接口新增 5 分钟/1 小时可切换尝试数和成功率，和原有全尝试成功率并列展示。

渠道的 `status_code_mapping` 只改变对外状态码和现有重试判断，M4-D 在映射前保留原始上游状态码用于归因；因此上游 `400 -> 503` 不会被观测误报为上游 5xx。该原始字段不对用户返回，也不改变扣费、收益、选路或自动禁用。

### 5.8 本轮验收口径修正（已实现）

- 管理员日志使用 `/api/log/` 全量接口时不按用户过滤；`/api/log/self` 只用于“仅自己”。前端作用域切换时不再复用另一作用域的旧查询结果，避免管理员列显示个人日志内容。管理员入口文案使用“全部用户”，降低误解。
- 服务档位日志同时保留存储值和最终计费快照：列表、详情优先显示 `billing_ratio`，不再把服务档位的 `group_ratio=1` 当作实际倍率；`special/low/medium/high` 通过现有服务档位国际化标签展示。
- Timing 口径拆开：`frt` 是首个上游事件（First event），`ttft` 是首个有意义文本或推理增量（TTFT）。列表和详情不再把 `frt` 冒充 TTFT；非流式或没有有效首字的请求可以没有 TTFT。
- “渠道健康与路由”页面当前明确为仅观测。探测指标、真实请求指标和排名分可供管理员排查，但仍不改变实时候选、priority、weight、重试、扣费或收益。
- 服务档位在渠道选择中间件提前耗尽候选并直接返回 `503` 时，也写入一条最终管理员错误日志；该路径没有上游尝试，不产生扣费或收益流水，但保留服务档位、模型、请求路径、路由阶段和 `request_id`。

同一请求在 LLM-Hub 与渠道商服务器上的首 T 可能不同：LLM-Hub 统计的是客户端到 LLM-Hub 的完整可见链路，渠道商日志通常统计的是它收到上游事件的时间。两者差值可能发生在渠道商向下游转发、代理/CDN 缓冲或连接传输阶段。现阶段先以 LLM-Hub 的 `ttft` 作为用户体验指标，并通过 `first_event_ms`、`first_token_ms` 和请求 ID 对照定位；没有证据前不强制更换 HTTP 协议或压缩设置。

### 5.9 流式首 T 传输诊断（已实现，真实请求复验通过）

本轮标准档真实请求分别记录到约 `15.2s` 和 `65.0s` 的 TTFT，而渠道商内部日志约 `3-4s` 收到首字。LLM-Hub 在收到首个上游事件后约 `150ms` 即识别有效首字并写出，因此该差值不是简单的页面展示误差：用户很可能真实等待了 `15-65s`，主要延迟位于渠道商应用向 LLM-Hub 输出首个 SSE 之前。对应渠道的 Nginx 会按客户端声明返回 gzip，压缩或代理缓冲是当前最小可验证因素。

首轮修复不改变路由、Affinity、探测任务或账务：

- 流式上游请求在渠道未显式覆盖 `Accept-Encoding` 时默认发送 `identity`，避免 gzip 中间层积攒小 SSE 数据块；渠道 Header Override 仍具有最高优先级。
- `hub_attempts` 增加 `response_headers_ms`、`first_body_byte_ms`、`upstream_protocol`、`content_encoding`、`transfer_encoding` 和 `upstream_uncompressed`，并继续保留 `first_event_ms` 与 `first_token_ms`。
- Responses 流式下游事件、数据段写入或 Flush 失败不再被 Gin `Render` 吞掉，而是终止本次流并进入现有失败/部分成功判定。
- 根域名服务档位的 Affinity 命中仍记录为 `public_pool`；只有渠道商子域入口的优先命中记录为 `preferred`，避免诊断数据误报路由阶段。

复测时按以下顺序判读：响应头已经很慢，说明上游或渠道商应用迟迟没有开始响应；响应头很快但首响应体字节很慢，说明渠道商应用、Nginx、CDN 或传输层在缓冲；首响应体字节快但首事件/首字慢，再检查 SSE 分帧和协议解析。`Accept-Encoding: identity` 若显著改善 TTFT，保留该修复；若没有改善，再对单一渠道做 HTTP/1.1 对照，不能直接全局切换协议。

本地短请求真实复验结果：标准档 `/v1/responses` 客户端约 `1.55s` 收到首事件、`3.14s` 收到首个文本、`3.41s` 完成；管理员日志的同一尝试为响应头 `1.354s`、首响应体字节 `1.355s`、首事件 `1.355s`、首字 `2.941s`、总耗时 `3.210s`。特价档同类请求客户端约 `1.73s` 收到首字、`1.74s` 完成；管理员日志为响应头 `1.380s`、首响应体字节/首事件/首字约 `1.547s`、总耗时 `1.557s`。两次均为 `HTTP/2.0 + identity`，客户端与网关记录的差值约 `0.2s`，证明新口径能定位首 T 且压缩修复对这两次请求有效。

上述结果不能替代原异常负载的完整验证：旧标准档请求约有 `32k` 输入并使用高推理强度，短请求变快不代表长上下文 P95 已经稳定。最终验收需要在同一 Channel 上连续发起至少 5 次等价负载，对照客户端、LLM-Hub 和渠道商三方 request ID。`first_body_byte_ms` 表示网关应用开始读取响应体的时间，不是网络抓包时刻；`first_token_ms` 表示网关解析到有效增量的时间，是客户端可见首 T 的下界。若客户端仍显著更慢，再排查 LLM-Hub 下游代理或 CDN 缓冲。

完成下游写错误传播并重启后的再次复验中，标准档日志 `9739` 的网关首字为 `2.645s`、客户端为约 `2.684s`，特价档日志 `9740` 的网关首字为 `2.572s`、客户端为约 `2.610s`；两者差值均约 `40ms`。两次均单次命中本档 Channel，且对应收益记录满足 `gross_quota = platform_fee_quota + provider_income_quota`。这证明当前分段计时与客户端短请求体验一致，但不改变前述长上下文验收要求。

## 6. 状态和账务不变量

- 服务档位只决定候选边界，不跨档切换。
- 价格倍率不进入健康分，供给倍率只做档位资格过滤。
- 入口渠道商和最终服务渠道商分开记录。
- 收益归最终成功 Channel 所属渠道商。
- 同一请求只产生一次用户成功扣费和一次收益结算。
- 失败尝试记录 `request_id + attempt_index + channel_id + error_category`。
- 首版忽略失败尝试可能产生的上游费用：失败尝试不扣用户、不记渠道商收益，也不进入人工核账；只保留路由排查所需的失败记录。
- 服务档位流式响应复用现有 `StreamStatus` 和 Usage 判定最终尝试：正常结束为 `success`；异常结束且已有有效输出为 `partial_success`，按实际可测量用量扣费并结算当前渠道商；异常且无有效输出为 `failed`，最终额度归零并退回预扣。客户端主动断开后的部分输出仍扣实际用量，但不作为渠道健康失败。普通 New API 分组不套用该规则。
- `hub_attempts` 对每个失败重试记录 `consumer_charge_status=not_charged`、`charged_quota=0`，最终成功或部分成功记录本次实际扣费额度；失败尝试不会参与用户扣费或渠道商收益。
- 收益预备或结算失败时保留 pending/错误状态，由现有恢复任务补重试；这只针对平台内部收益账务，不代表首版会核对失败上游是否扣费。
- 已经开始输出流式响应后，不再切换上游。
- 手动禁用不得被探测、自动启用或健康恢复逻辑覆盖。
- 循环保护错误不得再次进入普通重试、扣费或收益结算。
- 服务档位候选耗尽和最后一次可切换故障耗尽预算使用同一个 `503 service_tier_unavailable` 用户契约；尝试链仍保存原始失败，普通 New API 分组不改写。

## 8. 开发顺序、开关和回滚

建议按以下顺序单独提交：

1. M0：补现有路由、Affinity、手动禁用竞态和循环保护回归测试。
2. M1：管理员只读渠道状态和现有探测排行，不改变选路。
3. M2：服务档位 Affinity 的最小模型隔离和 Provider 状态检查。
4. M3：补真实请求统计字段和统一 TTFT/延迟口径，只进入 `observe`。
5. M4：在真实数据稳定后再讨论 `active` 健康降权；容量、探索、公平和半开恢复继续拆开。

当前任何新动态模块都必须能回到现有的渠道商优先、公共池排除入口渠道商、Channel 排除和 `priority + weight` 选路。回滚不得删除探测样本、请求日志或账务记录。

渠道商实名认证、一人多渠道商限制和企业主体审核单独作为治理模块，在开放公共入驻和收益规模化前完成。

## 9. Agents 审查结论

本规格经路由、账务、复杂度和运维四个方向的只读审查后收缩为当前版本。共同结论：

- 必须保留服务档位边界、渠道商入口优先、公共池排除入口渠道商、本次失败 Channel 排除、Affinity 可用性检查、现有 priority/weight、手动禁用保护和最终账务归属。
- 首版不应同时引入 Redis 实时聚合、容量调度、探索流量、公平因子、新半开状态机和动态总分。
- 现有公开排行和未来实时路由分数不能在没有数据口径时并行成为两个“健康真相”。首版先展示现有探测指标，后续有真实请求数据再确定是否拆成公开分和路由分。
- `HubRelayAttempt` 适合单请求排查，但要驱动真实健康排行前，必须补模型、端点和样本来源等最小字段。
- 当前代码中的渠道商级随机、渠道商内部 priority/weight 是已验证语义，实现时不能悄悄改成全局 priority。
- 手动/自动禁用状态区分已经实现；自动恢复写库的条件竞态、根域名服务档位被 `SkipRetryOnFailure` 截断、Affinity 未检查 Provider 状态，属于进入动态路由前的兼容修复。
- 失败上游可能扣费不进入首版账务闭环，不新增 `unknown` 核账流程；成功请求的用户扣费和最终渠道商收益仍保持幂等。

任何需要新增持久化模型、替换现有检测流程或改变扣费语义的建议，必须回到产品讨论后再实现。

## 10. 动态倍率令牌实现记录

第一版实现采用 `tokens.hub_routing_policy` JSON 字段，不新增方案表。根域名策略保存模型族和倍率闭区间，倍率合法范围为 `0.01-100.000`、步进和持久化精度为 `0.001`；`1.000` 只是平台官方基准倍率，不是上限，前端新增模型族默认取包含 `1.000` 的有效范围，若该模型族只有高价供给则从实际最小倍率开始。渠道商子域名策略保存渠道商作用域、模型族和渠道商已发布的单个精确倍率。旧 Token 和旧分组字段继续保留，未携带策略的请求完全走原有 New API/服务档位路径。

新增策略只改变候选过滤：先按策略筛选模型族和供给倍率，再复用现有渠道健康/上架检查、亲和、priority、weight、渠道商优先、公共池兜底和失败 Channel 排除。动态候选仍先随机选择渠道商，再在渠道商内部按 priority/weight 选择 Channel；普通选择、Affinity 和固定 Channel 使用同一策略边界。平台自有 Channel 在根域名按倍率 `1.000` 参与；兜底不突破策略边界。Token 字符串、计费价格、模型基础价格和失败扣费口径不变。

新策略 Key 的 `group=default` 只是兼容字段。价格基准固定为 `1.000x`，不会再乘管理员配置的旧 `default` GroupRatio 或用户组覆盖；最终计费倍率由成功 Channel 的供给倍率决定。

供给上架时会额外生成内部 `hub-routing` Ability。它让新策略发现不落在旧四档边界内的高倍率供给，例如 `5.500x`，但不会暴露给普通 `default` Token；旧四档 Ability 继续生成并服务历史 Token。服务启动时会在一个事务中重建已有 Hub 供给的 Ability 并刷新渠道缓存，用于回填升级前创建的供给；当前内测规模下优先采用这个直接且幂等的兼容方案，供给量明显增长后再评估改成一次性迁移。缓存选路、数据库选路、可用性统计、Affinity 和固定 Channel 校验共用同一候选组判断，避免只在某一条链路支持高倍率。

入口 Host 的渠道商作用域优先于 Token 请求体：渠道商子域不能使用绑定到另一渠道商的 Token；根域仍可管理或使用已有渠道商 Token。异步任务会在现有 BillingContext JSON 中保存入口 Provider 和路由阶段；复用已锁定 Channel 时，除模型族和倍率外还要求续作 Key 属于同一入口 Provider。原任务曾由平台兜底到其他 Provider 不改变该入口归属。

接口与界面实现：

- `GET /api/token/routing-options` 根据当前 Host 返回根域名范围选项或渠道商精确倍率选项，并返回每个倍率桶的渠道数和渠道商 ID，仅用于前端准确去重计数，不暴露 Channel、Base URL 或密钥。
- 新策略 Token 的 `/v1/models` 会读取内部 `hub-routing` Ability，并继续按 Token 已选模型族过滤；通用模型定价接口会排除该内部组，避免把实现细节展示成用户可选 Group。
- `POST/PUT /api/token/` 接收结构化 `hub_routing_policy`，后端重新绑定并校验 Provider 作用域，不信任请求体中的 Provider ID。
- 根域名使用范围滑块和 `0.001` 数值输入；渠道商子域名只显示该渠道商当前发布的精确倍率。
- Token 列表展示模型族与倍率摘要，不再把策略 Token 的内部 `default` 分组暴露给用户。
- 已选渠道后来下架时，编辑界面明确标记为不可用并要求移除；请求路径继续按统一 `503` 契约失败。

Realtime 请求不再在每次 `response.done` 调用旧 `PostConsumeQuota`。分段阶段基于累计 usage 调用 BillingSession `Reserve`，连接结束后只执行一次 `SettleBillingAndProviderEarning`；固定价格模式携带 `ModelPrice`，阶梯计费模式按累计输入输出计算预留，模型倍率和最终供给倍率使用请求快照。文字增量、响应头事件和首个有效输出分别计时，异常 WebSocket 读取不会再被误记为正常 EOF；预留或最终结算错误会返回调用方。异常且无有效输出的新策略请求结算为零，已产生有效输出时按累计用量结算。客户端 WebSocket 完成升级后，任何 Relay 错误都禁止换 Channel 重试，避免第一次会话已结算后第二条 Channel 继续产生未计费 usage。

自动化测试已经覆盖策略归一化、根域名 Provider 防伪、创建/更新持久化、Token 缓存、私有分组和内部组写入拒绝、高倍率内部 Ability、通用定价隐藏、同倍率渠道商优先与平台兜底、平台兜底 Affinity 复用、固定 Channel 越倍率拒绝、跨渠道商子域 Token 拒绝、Realtime 累计预留与禁止重试、`/v1/models` 实际可路由过滤，以及前端新旧 Key 分流和失败关闭。三路静态复核发现的 Realtime P0 已修复；收益准备/释放和退款意图无法落库时的恢复缺口已记录在加固清单，后续需要独立账务设计。最终仍需浏览器验收：根域名多模型族交互、子域名精确倍率、渠道商停用后的同倍率兜底、旧 Token 编辑体验和实际账单倍率。
