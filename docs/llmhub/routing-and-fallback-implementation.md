# 路由与平台兜底实现规格

状态：开发基线（倍率路由版）。产品和算法方案见 [routing-and-fallback-design.md](routing-and-fallback-design.md)。

本文只说明如何把已确认的方案接入现有代码，不重新定义产品规则。实现遵守“小改动、复用 New API、每步可验证、随时可回滚”。

## 当前生效口径

- 新 Token 不再把四个服务档位作为实际选择项，而是按模型族保存倍率闭区间；倍率范围为 `0.01-100.000`，步进 `0.001`，允许超过 `1.000`。`1.000` 只是平台官方基准倍率，不是上限。
- 渠道商子域 Token 不使用自由范围，只能选择该渠道商已经发布的模型族和精确倍率；请求仍按当前 Host 优先该渠道商，失败后在同一倍率约束内进入平台公共池。
- “特价 / 经济 / 标准 / 高品质”仅为前端按最高选中倍率显示的辅助标签，不参与候选过滤、计费或跨档兜底。旧 Token 和未携带 `hub_routing_policy` 的请求继续走旧 New API/服务档位兼容路径。
- 实际用户扣费沿用 New API 的 `BillingSession`。新策略 Key 的计费基准固定为 `1x`，不乘旧用户组倍率；最终费用使用模型价格、最终命中渠道倍率和其他请求倍率。重试只对最终成功渠道结算收益；失败尝试不扣用户、不记渠道商收益。
- 渠道商平台服务费在最终 Channel 选定时与归属、供给倍率一起快照，使用该渠道商覆盖值或当时的全局默认值；后续修改费率不影响本次请求或已创建收益记录。

## 1. 首版范围

### 继续复用

- `Channel`：唯一上游配置实体。
- `Ability`：模型是否可路由的基础能力记录。
- New API 原生 `priority`、`weight`、重试和扣费流程。
- `HubSupplyGroupProbeTarget`、`HubSupplyGroupProbeSample`：模型探测数据。
- `HubRelayAttempt` 和请求日志：单次请求尝试追踪。
- 现有手动禁用、自动禁用语义：任何自动逻辑不得恢复手动禁用渠道。

### 首版明确不做

- 不重写 New API 渠道检测协议或适配器。
- 不新增专属 Token、订阅关系或第二套 Channel CRUD。
- 不跨服务档位兜底。
- 不新增独立调度数据库、尝试明细表或钱包汇总表。
- 不把真实请求日志 JSON 扫描放进请求热路径。
- 不实现实时容量调度、探索流量、公平分流、用户请求半开恢复或机器学习评分。
- 不在本轮实现渠道商实名认证和一人多渠道商限制。

当前健康信号已经进入实际选路，但只在现有候选集合内部调整 `weight` 或排除明确不可用的候选。它不改变渠道商优先、Provider 内 `priority + weight`、模型族倍率边界、Affinity、重试、扣费和收益归属。短窗口数据缺失、Redis 异常或运行时快照超过 3 分钟时自动回到中性权重，不因观测系统故障制造 `503`。本轮不再增加 `static/observe/active` 多状态开关，避免配置组合产生两套运行语义；回滚通过版本发布完成。

## 2. M0：兼容性与回归基线

这一步不引入动态评分，先保证现有流程的边界没有被实现文档误导。

### 2.1 保留当前渠道选择语义

服务档位公共池当前采用两级选择：

```text
先按渠道商选择
  -> 再在该渠道商内部按 New API priority + weight 选择 Channel
```

不能在接入健康分时悄悄改成全平台先比较 `priority`。全局 priority 和渠道商公平分流是两个不同产品策略，后续若要改变必须单独讨论。

内存 Channel 缓存在每次完整刷新时，同时预建“服务档位 + 模型 + 渠道商”的有序候选桶。请求热路径不再临时按渠道商重新分组或排序全部候选，但仍在最终选择前复查当前端点能力、渠道商状态、Channel 状态和本次失败 Channel 排除。数据库直查路径继续使用原有查询与排序，作为缓存关闭时的兼容行为。

服务档位使用严格的本次失败 Channel 排除；普通 New API 选择保留原有“候选耗尽时可复用”的兼容语义，不能把严格排除扩展到所有渠道流程。

### 2.2 兼容检查

- [x] Affinity 命中路径检查渠道商仍为 active，不能只检查 Channel 和 Ability。
- [x] 服务档位请求不被 New API Affinity 的 `SkipRetryOnFailure` 阻止同档重试和平台兜底，根域名和子域名都适用。
- [x] 自动恢复写库排除手动禁用状态，避免探测先读到自动禁用、管理员随后手动禁用、旧探测结果最后又覆盖为启用。
- [x] 单个模型不支持或端点不匹配时，不通过通用渠道错误路径误伤同 Channel 的其他模型；文本/图片按现有 `ProbeKind` 粗粒度隔离，连接、TLS、基础认证或余额等基础设施故障才保留 Channel 级处理。
- [x] 循环保护不等同于“已访问渠道商集合”。平台公共池排除入口渠道商和本次已失败 Channel；实际 relay 入口同时校验平台签名 hop，非空 POST 再使用并发指纹保护。

`SkipRetryOnFailure` 是 New API Affinity 规则中的一个选项：请求命中粘性 Channel 后，一旦该 Channel 失败就直接返回错误，不再尝试其他 Channel。这个语义适合要求固定上游的普通 New API 场景，但与 LLM-Hub“同档兜底”的产品规则冲突。因此服务档位请求必须忽略该停止重试选项；普通 New API 请求继续保持原行为。

### 2.3 端点发布边界

现有 `Ability` 和供给发布流程继续以 `Channel + Model` 作为可路由单元，不新增端点字段。首版复用探测目标的 `ProbeKind` 在候选选择时隔离文本和图片资格：任一类型健康时保留模型 Ability，文本请求只使用文本健康候选，图片请求只使用图片健康候选，全部类型失败后才删除 Ability。

这里的“端点”是同一模型使用的 API 协议或请求路径，例如 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 或图片生成接口；不是“具体模型”的别名，也与管理员直接创建平台自有 Channel 无关。

这仍是粗粒度隔离，不等于 Chat Completions、Responses、Anthropic Messages 等协议端点分别上架。若要让这些端点真正独立进入 Ability，必须另开设计任务，不能在健康分接入时顺带改变发布语义。

新建渠道的模型默认具有上架意图，现有 `hub_supply_probe` 首次检测成功后自动进入供给池；后续手工上架/下架时，发布状态、供给组汇总状态、Channel 状态和 Ability 重建仍在同一个数据库事务中完成。逐模型关闭自动检测时，同一事务删除其探测目标并按上架意图重建 Ability；免检测资格只覆盖模型实际支持的文本或图片 `ProbeKind`，不会虚构另一类端点。重新开启时立即创建 `pending` 目标并在检测成功前退出路由。事务失败不会提交设置，成功后才刷新运行时缓存。运行时缓存也已改为串行构建、完整发布，失败时保留旧缓存；完整刷新同时替换供给倍率、“已配置供给渠道”集合和逐模型免检测资格，避免删除供给扩展后残留上一代归属。普通选路和 Affinity 选路在持有 Channel 缓存读锁时同时带出供给归属、提供商状态、供给组和倍率，后续定价、重试预留、日志与收益结算复用该请求快照，不再读取另一缓存代的供给倍率。

钱包首次预扣和更高价格重试的补差都使用数据库条件更新，余额不足时在发起上游请求前停止；钱包和 Token 的最终差额也强制直写主库，不通过内存批量更新队列。用户/Channel 的累计用量与请求次数仍可批量更新，它们不是资金权威数据。

失败请求的预扣退款使用独立的 `billing_refunds` 恢复记录。记录以 `request_id` 唯一约束，只保存用户 ID、令牌 ID、资金来源、订阅 ID 和各项额度，不保存令牌明文。失败收尾先持久化该记录，再异步执行退款；钱包、订阅基础预扣、订阅重试补差和令牌额度在同一主库事务中回退，成功后才标记 `complete`。进程在异步退款前后中断，或一次退款事务失败时，记录保留为 `pending`，系统任务每 15 秒扫描并重试，因此不会因内存中的 `refunded` 标记提前写入而永久丢失用户预扣额度。失败上游是否已经扣费仍维持首版“只保留排查记录、不自动人工核账”的边界。

同步请求的用户资金已经提交但 Token 差额写回失败时，`BillingSession` 写入 `billing_token_adjustments` pending 记录；恢复任务每 15 秒在同一事务中完成 Token 差额和记录状态更新。成功异步任务的最终差额改用独立的 `billing_task_settlements`：以持久化 `task_id` 唯一，保存预扣、实际额度、资金来源和原始 `request_id`；成功终态 CAS 与结算意图在同一主库事务提交，后续在同一主库事务内调整钱包或订阅、Token 数据库额度、用户/渠道 `used_quota`、持久化 `Task.Quota` 和结算状态。该路径绕过内存批量余额队列，零差额也保留完成记录；事务任一环节失败会整体回滚并保留 `pending`，恢复任务按下一次尝试时间退避，成功后才释放渠道商收益。异步任务失败退款仍复用 `billing_refunds`，在同一事务内完成资金退款、Token 退款和 `Task.Quota=0`。这些恢复记录都不保存 Token key。主库结算与独立日志库仍不宣称跨库原子：完成标记可避免正常重复恢复，但不能消除进程在日志写入与标记更新之间的极短重复或丢日志窗口。

异步任务提交时将模型价格、模型倍率、基础分组倍率、供给倍率、最终综合倍率和附加倍率写入 `TaskBillingContext`。任务完成后的 token 重算优先使用这些快照，运行期间修改模型或供给倍率不会重定价已提交任务；只有历史任务没有有效模型倍率快照时才兼容回退当前配置。

异步任务的退款、差额和渠道商收益相关日志会沿用任务提交时的 `request_id`，同时保留 `task_id` 作为任务阶段标识；没有原始请求 ID 的历史任务仍只能按任务 ID 查询。

进入渠道选路后的服务档位请求按一次客户端请求只保留一条请求级最终记录：同步与异步任务成功时由消费日志保存完整 `hub_attempts`，最终失败时始终补一条错误日志，即使关闭了错误日志开关。中间失败仍写本地运行日志、执行原有自动禁用判断并追加 `hub_attempts`，但不再逐次写数据库错误日志。任务提交在选中渠道后发生的 `LocalError` 也会追加失败尝试，但标记为非渠道健康样本，不触发重试或自动禁用；生成请求上下文、解析原任务或渠道选择阶段的失败只写最终日志，尝试链为空。普通 New API 分组继续保留原有逐次错误日志行为。完整尝试链在管理员日志详情中展示，包含每次尝试的渠道商、Channel、端点、结果、延迟、TTFT、倍率和错误分类；非管理员日志序列化会删除 `hub_attempts`，权限边界不依赖前端隐藏。

渠道商收益的 `pending` 增加可空 `settlement_deferred` 门槛。同步请求先可靠准备收益，准备失败会终止用户结算；用户扣费成功后，最终 gross、平台服务费、Provider 收益和 `settlement_deferred=false` 在同一事务发布，再立即结算。发布已成功但结算失败时，系统任务每 15 秒按最终 gross 补结算。异步任务在提交和运行期间固定保持 `true`，成功终态先完成 `billing_task_settlements`，再原子发布最终 gross 并释放收益，避免恢复器抢在最终额度写入前按预估额度结算。失败退款与待结算 Provider 收益取消在同一主库事务完成；若收益已经结算，退款事务会失败并保留 pending，禁止平台同时承担用户退款和 Provider 收益。

文本、音频和任务提交不再吞最终结算错误：未形成持久化结算时返回不可重试的本地账务错误，且不增加用户/Channel 用量统计；资金已经提交或 Token 差额已形成持久化恢复记录时，按已接受结算继续处理。固定价格音频现在显式携带 `ModelPrice`。普通同步响应可能已由上游适配器写出，此时 HTTP 状态无法完全重写，账务日志和恢复记录仍是权威结果。

异步任务轮询使用 `(channel_id, upstream_task_id)` 复合键。同一平台的两个上游都返回 `1` 时，不再互相覆盖任务、退款或收益归属。

### 2.4 固定渠道令牌与供给定价保护

管理员可以继续使用 New API 原有的固定 Channel Token 调试能力。该能力只在传统分组中保留历史上的“直接指定渠道”语义；服务档位请求仍必须经过同档 Ability、当前请求的文本/图片资格、供给渠道商状态和入口子域归属校验，固定渠道不会因为校验失败而静默切到另一个渠道。

供给计费复用 `model/hub_supply_pricing.go` 的现有内存缓存。缓存未命中时只回查一次 `HubSupplyGroup` 归属：无供给扩展的管理员平台渠道按基础倍率继续运行；数据库已有供给扩展但缓存没有完整倍率快照时，计费在上游请求前失败关闭。这样可以避免供给渠道被误当作平台自营渠道并按 `1x` 计费，同时不为平台渠道新增第二套归属表。

管理员可通过 `/system-settings/models/channel-health-routing` 查看，数据接口为 `GET /api/hub/admin/routing-health`。页面在原有探测和公开排行数据之外，展示当前真实请求健康、探测/真实 TTFT、可用性因子、延迟因子、静态权重和最终有效权重；这些实时信号已经参与实际选路。公开排行仍保持原 7 天口径，不与分钟级路由状态合并成同一个分数。

- [x] 按 `Channel + Model + EndpointType + ProbeKind` 展示当前状态。
- [x] 展示渠道商归属、Channel 手动/自动禁用、上架、探测和服务档位 Ability。
- [x] 复用 7 天探测样本排除规则、P50/P95、置信度和现有公开排行公式。
- [x] 未上架、暂无样本、手动禁用、自动禁用和平台自营未监控渠道均保留在列表中。

- [ ] 使用现有数据库核对无样本、手动禁用、自动禁用、未上架和平台自营行。

### 3.2 复用的数据来源

- 探测目标和结果：`model/hub_supply_probe.go`。
- 公开排行现有计算：`model/hub_ranking.go`。
- 渠道商和供给归属：`model/hub_supply_group.go`、`model/hub_supply_pricing.go`。
- 单请求尝试排查：`service/hub_attempt_log.go` 和请求日志。

管理员页面同时展示探测原始指标、现有公开排行和实时路由因子，但不把它们包装成新的综合 `H` 分。公开排行用于长期展示，实时因子用于短窗口选路，两者口径和用途必须在页面中明确区分。

### 3.3 管理员排行粒度

优先按以下维度展示探测状态：

```text
Channel + Model + EndpointType + ProbeKind
```

至少展示：

- 渠道商、Channel、模型、端点、解析出的端点和供给倍率。
- 当前 Probe 状态、模型上架状态、Channel 手动/自动禁用状态。
- 最近探测时间、最近成功时间、最近延迟和 TTFT。
- 探测样本数、成功率、错误码和最后错误。
- 公开排行分及其可用率、TTFT、样本置信度等已有分项。
- 渠道商归属、服务档位资格和跳过原因。

暂无样本、已禁用和未上架渠道必须通过左连接展示，不能只展示成功探测过的渠道。

真实请求既在单条请求日志中保留 `hub_attempts`，也通过 M4-A/M4-B 独立聚合到管理员“真实请求指标”。它不混入 7 天探测排行，但符合健康资格的真实请求会形成分钟级路由信号。尝试记录包含 `model`、`endpoint_type`、`sample_source` 和失败分类。TTFT 取流式响应中的有效文本、推理或工具调用增量；角色、usage、结束事件、图片元数据和非流式请求不会生成 TTFT。工具型 Responses 若只等待文本增量，会把已经开始输出的 function/custom tool 参数漏掉并虚高 TTFT，因此工具调用增量必须纳入有效输出。

### 3.4 探测口径

探测和真实请求不能按请求数一比一混合。探测请求体量小、并发低、成功率可能偏高；真实请求 RPM 又可能很高，因此两者分别形成信号：

- 探测结果决定基础路由资格、失败退避和探测 TTFT 先验。
- 真实请求按完整分钟聚合，每分钟最多形成一次状态变化；只有可切换请求计入健康分母。
- 客户端错误、平台循环和配置错误不计入健康分母；上游、响应已开始和无法归因的错误保守计入。
- 当前未结束的分钟不参与判断，单分钟至少 20 个合格样本才有效；低流量或空分钟保持中性，不算失败。
- 自动端点模式的最终样本必须展示解析端点和尝试链，不能把多次端点尝试的总耗时冒充单端点耗时。
- TTFT 必须区分“首个有意义内容”和“首个上游事件”；图片、Embedding 等非流式请求只展示完整响应时间。
- 日志中的秒级 `UseTime` 不用于毫秒级 TTFT/P95 排名。

## 4. M2：Affinity 的最小兼容修复

Affinity 继续复用 `service/channel_affinity.go`，不新建数据库表或独立路由系统；F4 只增加一个与现有主缓存并列的轻量 fallback 状态缓存。

实现状态：已完成最小兼容修复。服务档位缓存键强制包含规范化模型；命中后仍复用现有 Provider、Channel、Ability、请求路径和档位资格检查；失效命中或可重试的上游失败会清除旧映射并进入现有同档重试。普通 New API 分组继续遵守原有 Affinity 配置。

### 4.1 已确定语义

Affinity 是保留上游缓存和会话收益的软粘性，不是永久绑定，也不是质量评分。轻微变慢不能立即切换；只要渠道仍可用，就优先保留。

命中后必须重新检查：

- 渠道商 active、Channel 状态和手动禁用状态。
- 当前模型 Ability、请求路径和服务档位资格。
- 端点能力和当前业务发布状态。

认证失败、模型不支持、渠道商禁用、Channel 进入自动故障状态或请求无法继续时，清理当前 Affinity 并走同档重试和平台兜底。Affinity 不能阻止 LLM-Hub 服务档位兜底。

### 4.2 范围控制

现有通用 Affinity 缓存键是可配置的，改动它会影响 Codex、Claude 等既有缓存和请求覆盖逻辑。首版只要求服务档位使用的规则必须包含规范化模型，避免不同模型共用映射；端点和入口 Host 先通过命中后的能力、路径和渠道商检查隔离，不新增第二套 key 体系。

如果后续出现可复现的“不同端点或入口 Host 互相污染”，再为通用 Affinity 增加字段并单独回归，不在动态评分任务中顺带完成。

### 4.3 模型和端点故障边界

首版不新增完整的模型故障状态机或独立表，复用现有错误码、当前请求的 Channel 排除和供给探测状态。真实使用发现，探测任务把目标标记为 `testing`、或一次临时 `524` 记为 `error` 时，原实现会立即删除该模型的路由资格并制造连续本地 `503`。本轮增加一个最小的连续失败计数修正：

- 已经成功过的目标在 `pending/testing` 期间继续保留原路由资格。
- 第一次连续探测失败仍记录 `error` 和失败样本，目标继续参与路由，可用性因子降为 `0.70`。
- 第二次连续探测失败移除对应 `Channel + Model + ProbeKind` 的基础路由资格；若最近完整分钟的真实请求仍为 `healthy`，真实流量可以覆盖该探测隔离。任意一次探测成功立即清零计数并恢复。
- 失败后的自动重试间隔取管理员正常探测间隔与失败退避的较小值：第 1-9 次最多 5 分钟、第 10-29 次最多 15 分钟、第 30-99 次最多 60 分钟。这样正常探测设为 1 小时时，故障恢复不必至少等待 1 小时。
- 连续失败达到 100 次后状态改为 `suspended`，`next_probe_at=0`，不再占用自动探测资源。管理员手动测试会清零失败次数并解除暂停。
- 从旧版本迁移的既有 `error` 目标按已达到第二次失败处理；历史 `consecutive_failures >= 100` 的目标迁移到暂停态，避免升级时意外重新放量。
- 自动探测只处理启用/自动禁用 Channel 和 active Provider；手动测试可以检测手动禁用 Channel，但绝不自动重新启用。执行前再次检查状态；领取时同时 CAS 到期时间和租约令牌，旧 due 列表不能抢回已经完成并安排到未来的目标，旧结果也不能覆盖新测试或管理员操作。
- 执行资格检查或 Channel 读取错误只释放本次租约并恢复原状态，不增加渠道连续失败次数。目标结果、探测样本、供给组汇总和 Channel 路由状态在同一数据库事务提交；任务中断或执行资格变化时，控制器回队未完成目标并重新汇总供给组，避免长期停留在 `testing`。
- 现阶段所有探测失败统一使用宽松规则。余额不足、无效 Key、账号封禁等高置信错误是否应立即隔离，以及不同 HTTP/上游错误码的降级级别，保留为后续待办，不能依赖模糊错误文案直接禁用。

其他边界保持不变：

- 连接、TLS、基础认证、余额和无可用 Key 等可能影响整条 Channel 的故障，继续沿用 New API 的 Channel 级处理。
- `model_not_found` 和 `channel:model_mapped_error` 只表示当前模型不可用，不触发整条 Channel 自动禁用。
- 适配器明确不支持当前请求端点时返回 `channel:endpoint_unsupported`；它只影响本次 `Channel + Model + Endpoint` 尝试，沿用现有同档重试并排除当前 Channel，不跨档，也不关闭该 Channel 的其他模型和端点。
- 同一模型存在文本和图片探测目标时，模型任一 `ProbeKind` 健康即可保留模型级 Ability；实际候选和 Affinity 再按请求路径选择 text/image 资格。供给组此时显示 `partial`，只有所有已上架模型的所有探测类型都不可用时，Channel 才自动退出路由。
- 未知转换错误仍保留原有客户端错误和跳过重试语义，不能通过匹配错误文案自动升级为渠道故障。

该边界不改变 RetryTimes、服务档位资格、扣费或收益。缓存开启、数据库直查和 Affinity 命中使用同一 `ProbeKind` 判断。本轮不引入独立熔断表、探索流量或容量调度；动态健康状态仍保存在内存快照中，Affinity 的临时 fallback 记录使用现有 HybridCache，数据库探测目标仍是基础路由资格的权威来源。

### 4.4 F4/F5：平台兜底后的亲和恢复

平台兜底不能覆盖原来的亲和渠道。旧的 `new-api:channel_affinity:v1` 整数缓存继续保存 `preferred`，新增的 `new-api:channel_affinity:fallback:v1` 只保存临时兜底渠道、下一次恢复时间和小型失败计数，因此旧缓存不需要迁移。

- 真实请求失败时，服务档位重试使用 `ClearCurrentChannelAffinityCacheForRetry`：preferred 保留，fallback 失败只清理 fallback，恢复尝试失败则增加恢复失败次数。
- 兜底请求成功时只写 fallback；冷却期间不再撞击 preferred。冷却到期后，只有现有 `Channel + Model + ProbeKind` 资格可路由时才尝试 preferred。
- preferred 恢复成功后删除 fallback 并正常刷新 preferred TTL。手工禁用或渠道商禁用不会被恢复逻辑重新启用；fallback 被禁用时只清理 fallback，不删除原 preferred。
- 恢复等待复用 `HubSupplyProbeRetryDelayMinutes`：按请求端点沿用文本/图片探测周期和 5/15/60 分钟上限退避，连续失败达到 100 次仍进入 `suspended`，Affinity 不会额外发起探测或绕过暂停。
- 普通 New API 分组不读取或写入 fallback 缓存，原有 Affinity 语义不变。

## 5. M3：真实请求健康评分与动态权重

M3/M4 已补齐真实请求结构化字段、短窗口聚合和动态权重。它只改变同一现有优先级候选中的选择概率或硬排除明确失效候选，不改变候选价格边界、Provider 优先、Affinity、重试和结算。

### 5.1 必须先补齐的最小字段

真实请求尝试需要可稳定聚合：

```text
model
endpoint_type
sample_source = probe / real_request
skip_reason
```

M3 已完成真实请求观测字段的最小补齐：

- 服务档位真实请求写入结构化 `hub_attempts`，`sample_source=real_request`；运行时健康直接复用请求完成时写入的分钟桶，不扫描请求日志 JSON。
- 每次尝试记录规范化 `model` 和依据最终请求格式解析出的 `endpoint_type`，避免用模型名称猜测图片、Responses 等端点。
- `first_event_ms` 与 `first_token_ms` 分开记录：前者表示上游首个事件，后者只在首个有意义的文本、推理或工具调用增量出现后记录；图片元数据、usage、生命周期事件和 `[DONE]` 不伪造 TTFT。
- 失败尝试暂以 `skip_reason=failed_attempt` 表示它不会作为当前请求的成功服务样本；容量、熔断或未来动态筛选原因暂不写入，避免提前引入未实现的调度语义。
- 重试开始时重置本次尝试的首事件和首 token 计时，避免把前一个失败渠道的时间带入后续渠道。

这些字段首版可以继续放在结构化请求日志中；M4-A 已补充独立的 Redis/时间桶聚合，但不能通过扫描 JSON 日志实现自动排行或热路径选路。

### 5.2 当前生效公式

信号键为 `Channel + 规范化模型 + ProbeKind(text/image)`。不按最终上游协议细分，因为选路发生在 Channel 协议转换之前，而现有 Ability 也以 `Channel + Model` 为发布粒度；文本和图片继续隔离。

```text
探测可用性 A_probe:
  0 次连续失败 = 1.00
  1 次连续失败 = 0.70
  >= 2 次或已暂停 = 0；最近真实流量 healthy 时可覆盖为 1.00

真实可用性 A_real（只读最近一个完整分钟，至少 20 个合格样本）:
  success_rate >= 95%          healthy，1.00
  80% <= success_rate < 95%   degraded，success_rate
  success_rate < 80%           unhealthy，max(0.25, success_rate)
  相邻两个有效分钟都 unhealthy  quarantined，0
  无样本或样本不足             unknown，1.00

A = healthy 真实流量覆盖后的探测值，否则 min(A_probe, A_real)

S50 = clamp(1 - TTFT_P50 / 10s, 0, 1)
S95 = clamp(1 - TTFT_P95 / 20s, 0, 1)
TTFT_source = (2 * S50 + S95) / 3
real_confidence = min(real_ttft_samples, 100) / 100
real_adjusted = 1 + (TTFT_real - 1) * real_confidence
L = max(0.20, 0.70 * TTFT_probe + 0.30 * real_adjusted)

effective_weight = static_weight * A * L
```

真实健康只读取最近两个已经结束的 1 分钟窗口，当前未结束分钟不会重复产生状态信号。TTFT 使用最近 15 个完整分钟的成功样本，少于 20 个时保持中性；首字慢只软降权，不能单独下架。有效权重仅在原有同 `priority` 候选内生效；原始权重全部为 0 时继续保留 New API 等权随机语义。

### 5.3 暂不实现的动态能力

以下内容记录为后续阶段，不进入当前 M1/M2：

- `CapacityScore`、Channel/渠道商 inflight 和并发租约。
- `healthy -> degraded -> open -> half-open` 新状态机。
- 用户请求触发的半开恢复；恢复优先复用现有供给探测任务。
- fairness factor、provider base weight 和 5% exploration。
- 按最终上游协议细分健康状态；当前只按文本/图片隔离，避免协议转换前后的 key 不一致。

Redis 当前只承载短窗口计数，不承载 Channel 权威状态或账务。Redis 查询失败时不发布空快照，继续使用上一次运行时快照；快照超过 3 分钟后变为 `unknown` 并恢复中性权重，不因为统计故障返回 503，也不启用探索流量。真实请求健康采集跟随 Hub 路由开关，不再依赖模型广场的性能指标展示开关；关闭后者不会静默关闭动态健康与 TTFT 降权。

### 5.4 M4-A：真实请求聚合（已实现）

M4-A 建立独立的 `hub_routing_metrics` 时间桶表，避免污染模型广场使用的 `perf_metrics`。真实请求在最终成功或最终失败时，将本次完整尝试链写入聚合器：

```text
model + endpoint_type + provider_id + channel_id + bucket_ts
```

当前只聚合尝试数、成功尝试数、总耗时和有意义首 token 的平均值。失败尝试也计入尝试数，因此 `success_rate` 是 Channel 尝试级成功率，不等同于用户请求级成功率；一次请求重试两次会产生两条尝试样本，这是为了评估选路候选，不用于计费。

聚合器复用现有性能指标的内存桶、Redis 活跃桶和定时落库/清理机制，管理员只读接口为：

```text
GET /api/hub/admin/routing-metrics
```

支持按模型、端点、渠道商、Channel 和时间范围查询，并按尝试数降序返回。该 24 小时落库聚合仍只用于管理员观察，不直接参与选路；实时选路读取 M4-B 的分钟窗口，避免在请求热路径查询数据库。

管理员页面已接入 `/system-settings/models/channel-health-routing`。页面上半部分继续展示探测状态与现有 7 天排行，下半部分“真实请求指标”独立展示最近 24 小时的尝试数、尝试级成功率、平均完整响应耗时和平均 TTFT。端点标签按实际 `endpoint_type` 展示，不能把 Embeddings、图片、Gemini 等请求误标为 Chat。两部分不合并成一个分数，避免把弱探测样本和真实流量误认为同一口径。

M4-A 已完成以下验证：

- 后端聚合、数据库 Upsert、查询过滤和清理测试通过。
- 前端类型检查、lint、格式检查和生产构建通过。
- 本地重新构建嵌入式前端并重启后，菜单、页面、探测表格和真实请求指标表格均可加载，浏览器控制台无页面错误。
- 本地 Go 服务会把 `web/dist` 嵌入可执行文件；前端构建完成但服务二进制未重新构建时，新路由会被旧前端重定向到默认设置页。验收新页面前必须重新构建并重启本地服务。

真实请求和探测数据分开展示并分别形成信号，不按样本数直接混合。当前阈值和延迟窗口属于可通过后续真实数据校准的实现参数，不作为渠道商产品承诺。

### 5.5 M4-B：短窗口真实请求指标（已进入选路）

M4-B 在 M4-A 的记录入口上增加短窗口信号，不新建请求明细表：

- 以 1 分钟为桶，保留最近 60 分钟的内存聚合；每次清理只删除超出窗口的数据，进程重启后短窗口自然从空开始。
- `request_count_5m` 和 `success_rate_5m` 固定统计当前桶及前 4 个桶；`request_count_60m` 和 `success_rate_60m` 统计最近 60 个桶。失败尝试计入分母，成功尝试计入分子。
- `latency_p50_ms`、`latency_p95_ms`、`first_token_p50_ms` 和 `first_token_p95_ms` 默认统计最近 15 分钟；百分位只使用成功尝试，TTFT 只使用实际记录到的有意义首 token 样本。没有样本时返回空值，前端显示 `-`。
- 百分位使用固定 16 桶直方图，避免保存每条请求和无界排序；返回值是桶上界的近似值，不宣称为精确百分位。
- Redis 可用时，短窗口写入现有记录管道中的 `hub-routing-window:*` 分钟桶，并设置过期时间；查询会合并多实例 Redis 数据，替换本机同一分钟副本，避免重复计数。Redis 不可用时使用本机内存，重启或进程异常不会补回短窗口。
- 短窗口不落库；24 小时平均值仍来自 M4-A 的 `hub_routing_metrics`。因此页面同时显示短窗口 P50/P95 和 24 小时平均值，不能把两者当作同一统计口径。
- 每分钟刷新一次路由快照，只读取最近两个完整分钟。单分钟至少 20 个健康合格样本才产生状态；两个相邻有效分钟都低于 80% 才硬隔离。
- M4-B 可以改变同一现有优先级内的有效权重或隔离当前 `Channel + Model + ProbeKind`，但不得改变 Channel 静态配置、Affinity 边界、服务档位、倍率策略、扣费或收益。

### 5.6 M4-C：失败归因与健康资格（已实现）

M4-C 复用现有 `NewAPIError` 和响应状态，不复制 `shouldRetry`，只为失败尝试增加稳定的 `failure_class`：

- `upstream`：连接、超时、429、5xx、上游响应读取或响应内容故障。
- `configuration`：鉴权、模型不存在、Channel Key、模型映射、端点配置或价格配置问题。
- `client`：请求体、参数、权限或敏感词等客户端不可通过换 Channel 修复的问题。
- `loop`：平台生成的 `request_loop_detected`。普通请求不能再次进入重试；服务档位请求可在既有重试预算内排除当前 Channel 后切换候选，循环失败本身不计费。
- `response_started`：已经开始向客户端写响应后才出现的失败，不能重复输出。
- `unknown`：无法可靠归因的其他错误，保守保留，不自动解释成渠道故障。

失败类别写入结构化 `hub_attempts`，并在短窗口接口返回 5 分钟/1 小时类别计数。原有总尝试数和总成功率继续保持全尝试口径；动态健康只使用 `health_eligible` 子集，其中 `client`、`configuration` 和 `loop` 被排除，其他失败保守计入。`bad_response_status_code` 的原始 `401/403/404` 明确归为配置问题，不能被前面的通用上游错误分支误计入健康分母。该资格只影响运行时健康统计，不改变重试、New API 自动禁用或账务。

M4-C 同时补充两条自动禁用边界：平台生成的 `request_loop_detected` 固定不关闭 Channel；`channel:model_mapped_error` 只表示当前模型或端点映射失败，不关闭同 Channel 的其他模型。两者仍保留在请求尝试日志中，供管理员排查。

### 5.7 M4-D：可切换请求成功率（已进入选路）

M4-D 在 M4-B 的短窗口桶上增加可切换请求口径：成功请求始终计入；`upstream`、`response_started` 和 `unknown` 失败计入健康分母；`client`、`configuration` 与 `loop` 失败排除，因为更换渠道不能修复用户请求、平台循环或配置错误。客户端 Context 已取消时优先归为 `client`，不会因响应已经开始而误伤渠道健康。接口新增 5 分钟/1 小时可切换尝试数和成功率，和原有全尝试成功率并列展示。

渠道的 `status_code_mapping` 只改变对外状态码和现有重试判断，M4-D 在映射前保留原始上游状态码用于归因；因此上游 `400 -> 503` 不会被观测误报为上游 5xx。该原始字段不对用户返回，也不改变扣费、收益、选路或自动禁用。

### 5.8 本轮验收口径修正（已实现）

- 管理员日志使用 `/api/log/` 全量接口时不按用户过滤；`/api/log/self` 只用于“仅自己”。前端作用域切换时不再复用另一作用域的旧查询结果，避免管理员列显示个人日志内容。管理员入口文案使用“全部用户”，降低误解。
- 服务档位日志同时保留存储值和最终计费快照：列表、详情优先显示 `billing_ratio`，不再把服务档位的 `group_ratio=1` 当作实际倍率；`special/low/medium/high` 通过现有服务档位国际化标签展示。
- Timing 口径拆开：`frt` 是首个上游 SSE 事件（First response time），`ttft` 是首个有意义文本、推理或工具调用增量。为与原版 New API 和渠道商日志保持一致，日志列表中的“首字”固定展示 `frt`；详情页同时展示两个指标用于诊断。历史日志没有 `frt` 时列表才回退 `ttft`。
- “渠道健康与路由”页面明确标识为实时路由信号，展示探测健康、真实分钟健康、TTFT、可用性/延迟因子和静态/有效权重；公开排名分仍保持独立的长期展示口径。
- 服务档位在渠道选择中间件提前耗尽候选并直接返回 `503` 时，也写入一条最终管理员错误日志；该路径没有上游尝试，不产生扣费或收益流水，但保留服务档位、模型、请求路径、路由阶段和 `request_id`。

同一请求在 LLM-Hub 与渠道商服务器上的首 T 仍可能不同。两套 New API 的计时都从各自完成模型解析和渠道选择后开始，并非客户端入口到首字的完整端到端时间；外层 LLM-Hub 的计时还包含向渠道商发送请求、渠道商自身入口解析和响应返回，而渠道商日志的 `frt` 不包含其入口解析。核对链路时必须使用同一 `upstream_request_id` 比较双方列表的 `frt`，再用 LLM-Hub 详情中的 `first_event_ms`、`first_token_ms` 定位额外时间，不能把 `frt` 与 `ttft` 混为同一指标。

### 5.9 流式首 T 传输诊断（已实现，持续复验）

本轮早期曾把列表的 `ttft` 直接与渠道商列表的 `frt` 对比，因口径不同而放大了差异；该结论已废止。传输问题仍独立存在：2026-08-19 将同一渠道切换为不经过 Cloudflare 的直连域名后，LLM-Hub 的首事件仍比渠道商应用晚，证明灰云不能单独解决问题。随后从 LLM-Hub 生产服务器对该直连地址进行压缩 A/B：`identity` 约 `1.6-2.6s` 收到首事件且事件连续到达，gzip 约 `5.5-6.1s` 才收到首事件且多个事件集中成批到达，确认压缩协商是该链路可由平台消除的缓冲因素。

本轮传输修复不改变路由、Affinity、探测任务或账务：

- 流式上游请求在渠道未显式覆盖 `Accept-Encoding` 时由 LLM-Hub 默认发送 `identity`，避免要求每个渠道商修改 DNS、反向代理或响应头；渠道 Header Override 仍具有最高优先级。非流式请求继续使用 New API/Go 标准压缩协商。
- `hub_attempts` 增加 `response_headers_ms`、`first_body_byte_ms`、`upstream_protocol`、`content_encoding`、`transfer_encoding` 和 `upstream_uncompressed`，并继续保留 `first_event_ms` 与 `first_token_ms`。
- Responses 流式下游事件、数据段写入或 Flush 失败不再被 Gin `Render` 吞掉，而是终止本次流并进入现有失败/部分成功判定。
- 根域名服务档位的 Affinity 命中仍记录为 `public_pool`；只有渠道商子域入口的优先命中记录为 `preferred`，避免诊断数据误报路由阶段。

复测时按以下顺序判读：响应头已经很慢，说明上游或渠道商应用迟迟没有开始响应；响应头很快但首响应体字节很慢，说明渠道商应用、Nginx、CDN 或传输层在缓冲；首响应体字节快但首事件/首字慢，再检查 SSE 分帧和协议解析。平台默认 `identity` 只作用于流式上游请求，不切换 HTTP 协议，也不要求渠道商配合；若个别渠道明确需要其他编码，可通过现有 Header Override 单独覆盖。

此前经 `x-llm.net + Cloudflare` 的对照同时混入 CDN、上游模型耗时和不同请求样本，曾错误得出“identity 会聚合 SSE”的结论。直连 `x-llm.cc` 后使用相同请求进行 A/B，结果稳定显示 gzip 才会使多个事件集中到达，而 `identity` 保持连续事件节奏，因此以直连对照为准恢复流式默认 `identity`。这项修复不能消除渠道商模型本身的首 T，也无法修复无论是否压缩都主动缓冲 SSE 的上游；此类渠道继续由现有 TTFT 健康路由降低权重。

上述结果不能替代原异常负载的完整验证：旧标准档请求约有 `32k` 输入并使用高推理强度，短请求变快不代表长上下文 P95 已经稳定。最终验收需要在同一 Channel 上连续发起至少 5 次等价负载，对照客户端、LLM-Hub 和渠道商三方 request ID。`first_body_byte_ms` 表示网关应用开始读取响应体的时间，不是网络抓包时刻；`first_token_ms` 表示网关解析到有效增量的时间，是客户端可见首 T 的下界。若客户端仍显著更慢，再排查 LLM-Hub 下游代理或 CDN 缓冲。

2026-08-19 发布 `llmhub-f29b25a-20260819-1` 后，连续真实请求的 LLM-Hub 首事件相对 X-LLM 首事件约多 `1.9-2.8s`，多数约 `2s`；同一条约 `13.1` 万输入的请求总耗时分别为 X-LLM `38.61s`、LLM-Hub `39.31s`。该差异当前作为可接受的跨系统传输观察项，不作为故障处理；后续持续关注 P50/P95 是否恶化。X-LLM 的 `frt` 与 LLM-Hub 的 `frt/first_event_ms` 口径最接近；`ttft` 只作为详情诊断和健康信号，不能再用于双方列表对比。

完成下游写错误传播并重启后的再次复验中，标准档日志 `9739` 的网关首字为 `2.645s`、客户端为约 `2.684s`，特价档日志 `9740` 的网关首字为 `2.572s`、客户端为约 `2.610s`；两者差值均约 `40ms`。两次均单次命中本档 Channel，且对应收益记录满足 `gross_quota = platform_fee_quota + provider_income_quota`。这证明当前分段计时与客户端短请求体验一致，但不改变前述长上下文验收要求。

2026-08-19 17:00 后使用 `upstream_request_id` 对齐 13 条 Codex Responses 长上下文请求，确认此前“平台只增加约 2 秒”的表述不完整。典型三条中，渠道商 `frt` 为 `5.241s / 2.546s / 2.374s`，LLM-Hub `first_event_ms` 为 `7.411s / 4.875s / 4.844s`，两个日志字段相差约 `2.17-2.47s`；该差值还包含渠道商入口解析和选路等未被其 `frt` 计入的阶段，不能整体视为 LLM-Hub 的转发开销。LLM-Hub 在这三条中的上游请求准备约 `0.24-0.28s`，响应头到首响应体约 `0.22s`、首响应体到首事件约 `0.04-0.22s`，且 SSE 收到后立即写出，没有发现收到事件后继续缓冲数秒的证据。

原列表 `ttft` 为 `7.829s / 7.336s / 7.175s`，比同请求 `first_event_ms` 晚约 `0.4-2.5s`。受控的强制工具调用请求会在生命周期事件之后立即出现 `response.function_call_arguments.delta`；旧规则不会把任何工具参数记为 TTFT。修正上线后的两次服务端验证分别得到 `first_event_ms=5.283s / 6.868s`、`first_token_ms=5.500s / 6.878s`，差 `217ms / 10ms`，确认工具增量已经被记录，且未改变 SSE 转发。历史日志没有保存首个有效事件类型，因此不能断言历史差值全部由该分类错误造成。另一次顺序 A/B 中，经 Hub 的三个首包为 `1.70s / 1.83s / 2.15s`，直连三个独立请求为 `21.82s / 5.92s / 1.88s`，进一步说明上游生成波动使不同请求之间的倍数对比无效。后续验收必须使用同一请求 ID 的分段时间，并同时看绝对毫秒差值，不能用不同请求或不同计时口径的倍数下结论。

最终复核确认列表 helper 曾强制返回 `ttft`：例如同一条 LLM-Hub 请求的 `frt=9.087s`、`ttft=16.056s`，页面因此人为多显示约 `7s`；另一条 `frt=4.043s`、`ttft=6.747s`，同样被放大。列表现已恢复原版 New API 的 `frt` 口径，旧数据无需重算，刷新页面即可按 `frt` 展示；该修复只改变日志展示，不改变计费、路由、流式转发或健康统计。

## 6. 状态和账务不变量

- 服务档位只决定候选边界，不跨档切换。
- 价格倍率不进入健康分，供给倍率只做档位资格过滤。
- 入口渠道商和最终服务渠道商分开记录。
- 主要服务收益归最终成功 Channel 所属渠道商；跨渠道商平台兜底成功时，可从该收益中支付入口渠道商引流佣金。
- 同一请求只产生一次用户成功扣费和一次收益结算。
- 失败尝试记录 `request_id + attempt_index + channel_id + error_category`。
- 首版忽略失败尝试可能产生的上游费用：失败尝试不扣用户、不记渠道商收益，也不进入人工核账；只保留路由排查所需的失败记录。
- 服务档位流式响应复用现有 `StreamStatus` 和 Usage 判定最终尝试：正常结束为 `success`；异常结束且已有有效输出为 `partial_success`，按实际可测量用量扣费并结算当前渠道商；异常且无有效输出为 `failed`，最终额度归零并退回预扣。客户端主动断开后的部分输出仍扣实际用量，但不作为渠道健康失败。普通 New API 分组不套用该规则。
- `hub_attempts` 对每个失败重试记录 `consumer_charge_status=not_charged`、`charged_quota=0`，最终成功或部分成功记录本次实际扣费额度；失败尝试不会参与用户扣费或渠道商收益。
- 收益预备或结算失败时保留 pending/错误状态，由现有恢复任务补重试；这只针对平台内部收益账务，不代表首版会核对失败上游是否扣费。
- 已经开始输出流式响应后，不再切换上游。
- 手动禁用不得被探测、自动启用或健康恢复逻辑覆盖。
- 循环保护错误不得进入普通请求的重试、扣费或收益结算；服务档位请求仅可按既有重试预算排除当前 Channel 后切换候选，循环失败本身仍不扣费或结算。
- 已配置供给因探测、Channel 或 Provider 状态而暂时耗尽，以及最后一次可切换故障耗尽预算，使用 `503 service_tier_unavailable` 并返回 `Retry-After: 30`；尝试链仍保存原始失败。倍率策略 Key 请求当前模型和倍率范围内从未配置的供给时使用非重试型 `404 model_not_found`。普通 New API 分组不改写。

## 9. Agents 审查结论

本规格经路由、账务、复杂度和运维四个方向的只读审查后收缩为当前版本。共同结论：

- 必须保留服务档位边界、渠道商入口优先、公共池排除入口渠道商、本次失败 Channel 排除、Affinity 可用性检查、现有 priority/weight、手动禁用保护和最终账务归属。
- 实时健康只复用现有 Redis 分钟桶和内存快照，不同时引入容量调度、探索流量、公平因子、新半开状态机和动态总分。
- 现有公开排行和实时路由因子必须明确区分用途：公开排行是长期展示，实时因子是短窗口选路，不能把两者包装成同一“健康分”。
- `HubRelayAttempt` 适合单请求排查，但要驱动真实健康排行前，必须补模型、端点和样本来源等最小字段。
- 当前代码中的渠道商级随机、渠道商内部 priority/weight 是已验证语义，实现时不能悄悄改成全局 priority。
- 手动/自动禁用状态区分已经实现；自动恢复写库的条件竞态、根域名服务档位被 `SkipRetryOnFailure` 截断、Affinity 未检查 Provider 状态，属于进入动态路由前的兼容修复。
- 失败上游可能扣费不进入首版账务闭环，不新增 `unknown` 核账流程；成功请求的用户扣费和最终渠道商收益仍保持幂等。

任何需要新增持久化模型、替换现有检测流程或改变扣费语义的建议，必须回到产品讨论后再实现。

## 9.1 循环保护收尾记录

循环渠道处理已按最小改动完成，代码提交为 `4a54085`。本次只调整同步 Relay 的重试判定，并复用现有 `RetryTimes`、失败 Channel 排除集合、服务档位候选过滤和尝试链记录。

- 普通 New API 请求收到平台生成的 `request_loop_detected` 时保持 HTTP `400` 终止语义，不进入客户端可见的重试放大。
- 服务档位请求收到该错误时，可以在既有重试预算内排除当前 Channel 并切换下一个候选；`RetryTimes=0` 仍只尝试一次，最大配置为 10 次重试。
- 指定具体 Channel 的请求不切换；已失败 Channel 不会在同一请求中重新选中。
- 循环错误不扣费、不产生收益、不触发 Channel 自动禁用，也不改变健康统计口径。
- 任务类 Relay 已复用统一的结构化上游错误解析，只对明确的 `request_loop_detected` 放开未锁定服务档位任务换 Channel；续作等锁定原 Channel 的任务立即终止，其他任务类 `400` 仍保持不重试。循环错误码会完整传给尝试日志和自动禁用判断，不会被压成 `fail_to_fetch_task` 或误禁用 Channel。

已通过 `go test ./middleware ./controller ./service`。该提交待下一次 LLM-Hub 生产发布后进行线上循环链路验收；本记录不改变既有 hop、请求指纹和多跳上限设计。

任务失败收尾同时补了空结果保护：最终失败或适配器异常返回空结果时不会解引用 `nil`；失败仍由既有 BillingSession 退款，只有得到成功任务结果后才进入最终扣费和渠道商收益结算。

## 9.2 F2/F3 渠道排名与质量优先选路

F2/F3 第一版采用最小接入，不新增健康存储、容量模型或公平状态机：

- 服务档位和动态倍率策略的候选在完成原有模型、端点、倍率、Provider 状态、Channel 状态、循环和本次失败排除后，统一应用真实质量带。
- 真实成功率样本达到 20 后，保留距离当前最优不超过 1 个百分点的候选；真实 TTFT 样本达到 20 后，再保留 `P95 <= max(best × 1.20, best + 300ms)` 的候选。
- 质量带在 Channel `priority` 之前执行，避免慢 Channel 仅凭高 priority 压过明显更快的 Channel。
- 质量带之后仍先等概率选择有合格候选的渠道商，再在该渠道商内部按 `priority + effective_weight` 选择，拆分多个 Channel 不会增加渠道商级命中概率。
- 最优成熟候选达到 95% 成功率健康线时，样本不足的候选作为兜底；本次更优 Channel 失败并被排除后会重算质量带，较慢或冷启动候选可自然接手。所有成熟候选都低于健康线或都无成熟样本时，保留全部候选继续使用原有探测健康和有效权重。
- 图片等无 TTFT 场景只应用真实成功率带。实时键仍按 `Channel + 归一化模型 + text/image` 聚合，Chat/Responses 的精确 EndpointType 拆分暂不扩大实现。
- 管理员渠道健康接口改为对完整筛选集补齐能力、探测、真实信号和跳过原因，随后全局排序、编号并分页；禁用、未上架和暂无样本行不会被隐藏。

本次不修改 Affinity、重试预算、服务档位或倍率边界，也不进入扣费与渠道商收益结算路径。F4 的 preferred/fallback 拆分仍是独立后续模块。

## 9.3 核心路由复核（2026-08-21）

本轮并行复核覆盖质量带、平台兜底、preferred/fallback Affinity、循环保护，以及它们与重试、扣费、渠道商收益和自动禁用的交互。

已按最小改动修复：

- 异步任务保留 `request_loop_detected`，服务档位可排除循环 Channel 后使用剩余预算重试；普通任务和其他 HTTP `400` 行为不变。
- 循环任务失败不会污染渠道健康或触发自动禁用；最终失败退款，成功才结算收益。
- 平台 fallback 临时状态保存原 preferred，并在成功时只续自身 TTL、不推迟既定恢复时间；主 Affinity 自然过期后仍保留恢复目标，但不会用旧请求上下文复活已删除或已替换的主记录。
- 任务失败和空适配器结果增加空值保护，不再存在失败收尾 panic 风险。
- 异步任务预扣费失败显式标记为本地错误，不参与换 Channel、渠道健康或自动禁用。

待单独讨论，不在本次扩大实现：

- 冷却到期的恢复请求尚无跨请求 single-flight 租约；高并发下可能同时有多次恢复尝试。需要轻量 Redis `SET NX` 与单机锁后再宣称“全局只允许一次”。
- preferred 被手工禁用或判定不可路由时仍沿用现有清理语义；已有 fallback 临时状态只保存恢复目标，不会绕过 Channel/Provider 当前状态检查或自动解除手工禁用。
- 质量带把所有少于 20 个真实样本的冷渠道放到成熟健康渠道之后，新渠道可能长期难以获得真实样本；是否加入少量受控探索需要产品确认。
- 实时健康当前按 `Channel + Model + text/image` 聚合，Chat、Responses、Messages 等文本端点会共享信号；拆到精确 EndpointType 会增加探测、缓存和迁移范围。
- 管理员同健康状态的排名目前先看 TTFT、再看成功率，与实际路由先成功率带、再 TTFT 带不完全一致；排名口径需与候选池维度一起调整。
- 请求指纹目前为全平台相同请求体共享并发上限，可能让不同用户的相同请求互相占位；按用户还是按 Token 隔离会改变多网关循环兜底能力，需先确认边界。
- 不共享 `CryptoSecret` 的独立网关无法互认 signed hop，仍主要依赖请求指纹；视频内容 GET 代理也尚未接入 hop/指纹保护。这两项先作为黑盒多网关限制记录。

## 9.4 平台兜底引流佣金

兜底引流佣金沿用现有 `HubProviderEarning` 单请求账本，不新建第二套流水或结算任务。一个成功请求仍由同一个 `request_id` 控制准备、发布、结算、退款取消、恢复和幂等；账本增加入口渠道商、入口 Owner、佣金比例和佣金额度快照。历史记录的新字段默认为 0，仍按原账目解释。

默认全局开关开启、比例为 100 basis points（1%）。只有请求最终处于 `platform_fallback`、入口 Provider 与实际服务 Provider 不同、入口 Provider 存在且有效时才保存佣金快照；最终落账前会再次检查入口 Provider 状态，期间被禁用或删除则把佣金归还实际服务 Provider。根域公共池、正常 preferred 命中、同 Provider 重试、禁用或不存在的入口 Provider 均保存为 0。路由阶段和入口 Provider 只从服务端请求上下文或已校验的 Token 路由策略读取，不信任客户端提交值。

最终结算公式为：

```text
platform_fee = round(gross * platform_fee_bps / 10000)
referral_income = min(round(gross * referral_bps / 10000), gross - platform_fee)
serving_provider_income = gross - platform_fee - referral_income
```

因此 `gross = platform_fee + serving_provider_income + referral_income` 始终成立，佣金不会让实际服务渠道商收益变成负数。平台服务费和用户最终扣费均不改变。异步任务成功时按最终 gross 重新计算三方金额；失败或退款继续取消同一条 pending 收益，不留下独立佣金。佣金计入入口渠道商的累计收益、可提现收益和转余额额度，服务渠道商流水显示本次扣减；管理员可在渠道商结算设置中关闭或调整后续请求的比例。

该功能不读取或写入候选、Affinity、健康、排名和恢复状态。四项渠道商结算全局设置通过一个接口写库，并以单次运行时快照发布，避免开关和比例在请求中途混合生效；旧的单项设置接口对这些键也复用同一发布路径。引流方的收益明细会隐藏实际服务 Channel、供给组、Token 和消费者等内部字段，并把用户扣费列明确标记为佣金计算基数；管理员明细保留原始服务方、渠道、消费者和倍率快照用于审计。重复准备同一 request_id 时保留首次返佣快照，入口渠道商是否仍有效只在最终结算时复核。自动化测试覆盖账目守恒、普通请求无佣金、开关关闭、同 Provider、入口失效、100% 平台服务费、异步最终金额重算、幂等以及佣金转余额。

## 10. 动态倍率令牌实现记录

第一版实现采用 `tokens.hub_routing_policy` JSON 字段，不新增方案表。根域名策略保存模型族和倍率闭区间，倍率合法范围为 `0.01-100.000`、步进和持久化精度为 `0.001`；`1.000` 只是平台官方基准倍率，不是上限，前端新增模型族默认取包含 `1.000` 的有效范围，若该模型族只有高价供给则从实际最小倍率开始。渠道商子域名策略保存渠道商作用域、模型族和渠道商已发布的单个精确倍率。旧 Token 和旧分组字段继续保留，未携带策略的请求完全走原有 New API/服务档位路径。

新增策略只改变候选过滤：先按策略筛选模型族和供给倍率，再复用现有渠道健康/上架检查、亲和、priority、weight、渠道商优先、公共池兜底和失败 Channel 排除。动态候选仍先随机选择渠道商，再在渠道商内部按 priority/weight 选择 Channel；普通选择、Affinity 和固定 Channel 使用同一策略边界。平台自有 Channel 在根域名按倍率 `1.000` 参与；渠道商子域 Token 的 preferred 阶段严格匹配精确倍率，platform fallback 阶段允许不高于该倍率的更便宜候选，不允许更贵候选。Token 字符串、计费价格、模型基础价格和失败扣费口径不变。

新策略 Key 的 `group=default` 只是兼容字段。价格基准固定为 `1.000x`，不会再乘管理员配置的旧 `default` GroupRatio 或用户组覆盖；最终计费倍率由成功 Channel 的供给倍率决定。

供给上架时会额外生成内部 `hub-routing` Ability。它让新策略发现不落在旧四档边界内的高倍率供给，例如 `5.500x`，但不会暴露给普通 `default` Token；旧四档 Ability 继续生成并服务历史 Token。服务启动时会在一个事务中重建已有 Hub 供给的 Ability 并刷新渠道缓存，用于回填升级前创建的供给；当前内测规模下优先采用这个直接且幂等的兼容方案，供给量明显增长后再评估改成一次性迁移。缓存选路、数据库选路、可用性统计、Affinity 和固定 Channel 校验共用同一候选组判断，避免只在某一条链路支持高倍率。

入口 Host 的渠道商作用域优先于 Token 请求体：渠道商子域不能使用绑定到另一渠道商的 Token；根域仍可管理或使用已有渠道商 Token。异步任务会在现有 BillingContext JSON 中保存入口 Provider 和路由阶段；复用已锁定 Channel 时，除模型族和倍率外还要求续作 Key 属于同一入口 Provider。原任务曾由平台兜底到其他 Provider 不改变该入口归属。

接口与界面实现：

- `GET /api/token/routing-options` 根据当前 Host 返回根域名范围选项或渠道商精确倍率选项，并返回每个倍率桶的渠道数和渠道商 ID，仅用于前端准确去重计数，不暴露 Channel、Base URL 或密钥。
- 新策略 Token 的 `/v1/models` 会读取内部 `hub-routing` Ability，并继续按 Token 已选模型族过滤；通用模型定价接口会排除该内部组，避免把实现细节展示成用户可选 Group。
- `POST/PUT /api/token/` 接收结构化 `hub_routing_policy`，后端重新绑定并校验 Provider 作用域，不信任请求体中的 Provider ID。
- 根域名使用范围滑块和 `0.001` 数值输入；渠道商子域名只显示该渠道商当前发布的精确倍率。
- Token 列表展示模型族与倍率摘要，不再把策略 Token 的内部 `default` 分组暴露给用户。
- 已选渠道后来下架时，编辑界面明确标记为不可用并要求移除；请求路径继续按统一 `503` 契约失败。

Realtime 请求不再在每次 `response.done` 调用旧 `PostConsumeQuota`。分段阶段基于累计 usage 调用 BillingSession `Reserve`，连接结束后只执行一次 `SettleBillingAndProviderEarning`；固定价格模式携带 `ModelPrice`，阶梯计费模式按累计输入输出计算预留，模型倍率和最终供给倍率使用请求快照。文字增量、响应头事件和首个有效输出分别计时，异常 WebSocket 读取不会再被误记为正常 EOF；预留或最终结算错误会返回调用方。异常且无有效输出的新策略请求结算为零，已产生有效输出时按累计用量结算。客户端 WebSocket 完成升级后，任何 Relay 错误都禁止换 Channel 重试，避免第一次会话已结算后第二条 Channel 继续产生未计费 usage。

自动化测试已经覆盖策略归一化、根域名 Provider 防伪、创建/更新持久化、Token 缓存、私有分组和内部组写入拒绝、高倍率内部 Ability、通用定价隐藏、同倍率渠道商优先与平台兜底、平台兜底 Affinity 复用、固定 Channel 越倍率拒绝、跨渠道商子域 Token 拒绝、Realtime 累计预留与禁止重试、`/v1/models` 实际可路由过滤，以及前端新旧 Key 分流和失败关闭。三路静态复核发现的 Realtime P0 已修复；收益准备/释放和退款意图无法落库时的恢复缺口已记录在加固清单，后续需要独立账务设计。最终仍需浏览器验收：根域名多模型族交互、子域名精确倍率、渠道商停用后的同倍率兜底、旧 Token 编辑体验和实际账单倍率。
