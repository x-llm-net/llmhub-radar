## 2. 产品目标与边界

### 2.1 目标

1. 平台超级管理员保留全平台最终控制权。
2. 域名级总代理可以经营自己的品牌域名并管理该域名下的渠道商。
3. 渠道商继续只管理自己的供给、倍率和收益，普通用户继续使用成熟的余额、密钥和扣费功能。
4. 同一个账号可以同时是消费者、渠道商和一个或多个总代理的管理员，不要求注册多个账号。
5. 独立域名只改变品牌入口、管理范围和分账归属，不削弱平台默认兜底，也不改变 Channel 级质量路由。

### 2.2 第一版明确不做

- 不做无限级代理树，只支持“平台 -> 域名总代理 -> 渠道商”两级经营关系。
- 不引入可视化通用 RBAC、用户自定义角色或逐按钮授权。
- 不把总代理伪装成特殊渠道商，也不使用 `parent_provider_id` 表达租户关系。
- 不复制一套 New API 用户、余额、密钥、日志或路由系统。
- 不允许仅靠前端隐藏菜单实现权限控制。
- 不在角色权限阶段同时实现复杂分账、认证或风控。

## 3. 已确认角色模型

### 3.1 平台超级管理员

- 管理全平台模型、模型价格、New API 系统配置和平台路由参数。
- 管理所有租户、独立域名、渠道商、Channel、认证、风控和平台级排名。
- 查看全平台日志和账务。
- 配置平台与总代理之间的分成规则。
- 对租户管理员的操作拥有最终否决、停用和纠正权。

### 3.2 域名级总代理管理员

- 管理自己租户的品牌资料、域名和管理员成员。
- 可以直接创建渠道商，也可以审核用户提交到本租户的渠道商申请。
- 管理本租户下的渠道商状态，查看渠道及 F1 排名、流量、收益和分成数据。
- 不能进入 New API 平台级管理后台。
- 不能修改全局模型、平台路由、统一定价或其他租户数据。
- 可以配置本租户默认渠道商服务费率，并按渠道商单独覆盖，给重要渠道商让利。
- 只能查看、不能修改总平台对自己的抽成率；该费率仅由平台超级管理员配置。

### 3.3 渠道商

- 管理自己的公开资料、供给 Channel、倍率、收益和结算。
- 每个渠道商最终必须归属于且只能归属于一个域名总代理；不区分“直营渠道商”和“普通渠道商”两种类型。
- 同一个用户在同一租户下最多拥有一个渠道商，但可以在不同租户下分别拥有渠道商；渠道商资料、供给和结算均按 `provider_id` 隔离。
- 渠道商公开地址为 `{slug}.{租户主域名}`。`slug` 仅在所属租户内唯一，不同租户可以使用相同 `slug`，请求通过“租户域名 + slug”精确路由。
- 实际成功服务的渠道商获得供给收益，不能因为请求入口域名而伪造服务归属。
- 渠道商管理员不能查看同租户其他渠道商的密钥、联系方式明细或收益明细。

### 3.4 普通用户

- 管理自己的余额、密钥、使用日志和账号设置。
- 只能在一个明确的总代理入口下提交渠道商申请，申请归属由服务端根据可信 Host 确定。
- 在渠道商专属子域名下不显示“成为渠道商”，服务端也必须拒绝从该入口创建无关申请。

### 3.5 角色可组合

角色不是互斥身份。同一个 `User` 可以同时具备：

```text
普通用户能力
+ 自己拥有的渠道商管理能力
+ 一个或多个租户的管理员能力
```

现有 New API `User.Role` 只继续表达平台级普通用户、管理员和超级管理员，不把租户角色塞进该字段。租户管理员使用独立成员关系，渠道商权限继续由渠道商所有权或成员关系表达。

最终权限由“平台角色 + 租户成员关系 + 渠道商归属 + 当前资源范围”共同决定。当前访问域名只用于解析活跃租户，不能仅凭 Host 自动获得管理权限。

## 4. 权限矩阵

`全量` 表示全平台；`本租户` 和 `自己` 都必须由服务端添加数据范围条件。

| 能力 | 平台超级管理员 | 域名管理员 | 渠道商 | 普通用户 |
|---|---|---|---|---|
| New API 平台设置 | 全量 | 禁止 | 禁止 | 禁止 |
| 全局模型、价格和路由 | 全量 | 只读公开结果 | 只读可供给模型 | 只读可用模型 |
| 租户与独立域名 | 全量 | 本租户 | 禁止 | 禁止 |
| 租户管理员成员 | 全量 | 本租户 | 禁止 | 禁止 |
| 创建渠道商 | 全量 | 本租户 | 禁止重复创建 | 提交申请 |
| 审核渠道商申请 | 全量 | 本租户 | 禁止 | 禁止 |
| 停用渠道商 | 全量 | 本租户 | 禁止 | 禁止 |
| 渠道商资料 | 全量 | 本租户 | 自己 | 公开信息 |
| Channel 状态和排名 | 全量 | 本租户上架/下架及排名 | 自己的供给开关和数据 | 禁止 |
| Channel 上游密钥 | 按现有密文规则 | 禁止读取明文 | 自己 | 禁止 |
| 用户请求日志 | 全量 | 本租户脱敏范围 | 自己收益相关脱敏范围 | 自己 |
| 渠道商收益 | 全量 | 本租户汇总及分成所需范围 | 自己 | 禁止 |
| 渠道商服务费率 | 可查看/兜底管理 | 配置本租户默认值及按渠道商覆盖 | 只读自己的费率 | 禁止 |
| 平台对总代理抽成率 | 配置 | 只读自己的费率 | 禁止 | 禁止 |
| 提现与结算审核 | 全量 | 查看本租户、标记风险 | 自己申请 | 禁止 |
| 审计日志 | 全量 | 本租户管理员操作 | 禁止 | 禁止 |

### 4.1 默认最小权限

- 域名管理员能管理渠道商审核和状态，但默认不能读取或修改渠道商保存的上游密钥。
- 域名管理员可以控制 Channel 在本租户的上架资格，但不能修改 Channel 的上游凭证、Base URL、模型映射和供给倍率，也不能覆盖渠道商、平台或自动健康状态。
- 域名管理员日志默认不展示用户提示词、完整请求体、用户联系方式和租户外实际服务渠道商身份。
- 渠道商只能看到计算自己收益、质量和故障所需的数据，不能借由平台兜底查看其他渠道商身份。
- 超级管理员可以越过租户范围执行平台治理，但所有敏感写操作必须进入审计日志。

## 5. 服务端授权与数据隔离

### 5.1 请求上下文

每个管理请求应解析以下上下文：

```text
actor_user_id
platform_role
active_tenant_id       // 由可信 Host/路由解析，不信任前端提交
tenant_membership_role // 无成员关系时为空
owned_provider_ids
```

平台超级管理员天然拥有全平台权限，不需要加入 `TenantMember`。超级管理员可以显式选择租户范围，该选择只用于管理界面上下文、过滤和审计，不是授权前提；其他用户的 `tenant_id` 不能由查询参数自由指定。前端菜单只反映权限结果，不承担安全责任。

### 5.2 查询规则

1. 所有租户资源查询必须先应用 `tenant_id` 范围，再分页、统计和导出。
2. 通过资源 ID 读取、更新或删除时，必须再次验证该资源属于当前租户。
3. 批量接口、搜索、下拉选项、日志导出和统计接口同样适用，不能只保护列表页。
4. 缓存键必须包含租户范围，避免把一个租户的结果返回给另一个租户。
5. 数据库中保存的租户归属不能被普通更新接口改写；迁移渠道商使用单独的超级管理员操作。

### 5.3 跨租户平台兜底

独立域名不会把路由锁死在当前租户。路由顺序仍为：

```text
入口渠道商可用供给
  -> 当前策略允许的同渠道商切换
  -> 平台公共池兜底（可跨租户）
```

租户身份不能突破模型、端点、倍率、健康、重试和循环保护边界。跨租户兜底成功后：

- 超级管理员看到完整尝试链和实际服务归属。
- 入口租户管理员看到本租户请求结果、兜底状态和与自身分成有关的数据；租户外渠道商默认匿名化。
- 实际服务渠道商看到自己的服务量和收益，不看到入口用户的敏感信息。
- 普通用户只看到自己的请求、扣费和错误，不看到内部供给关系。

## 6. 建议领域模型

第一版独立引入 `Tenant`，不在 `HubProvider` 上增加递归父级：

```text
Tenant
  -> TenantDomain
  -> TenantMember
  -> HubProvider
  -> TenantRevenuePolicy
```

建议最小字段：

```text
Tenant
  id, name, slug, status, brand_config, created_at, updated_at

TenantDomain
  id, tenant_id, host, is_primary, verification_status, status

TenantMember
  id, tenant_id, user_id, role(owner/admin), status
  UNIQUE(tenant_id, user_id)

HubProvider
  tenant_id       // 最终必填；一个渠道商只属于一个总代理

TenantRevenuePolicy
  id, tenant_id, policy_type, rate_bps, status, effective_at, created_by
```

`TenantMember.role` 第一版只保留 `owner/admin`，两者业务权限可以先相同，`owner` 只额外负责成员和租户关键资料，避免提前拆运营、财务、审核员等细角色。

所有迁移必须同时支持 SQLite、MySQL 和 PostgreSQL。`tenant_id` 在迁移完成前可以暂时为空，但空值只表示“历史归属待确认”，不是一种渠道商类型，也不能据此创建新的渠道商或授予总代理权限。

- 渠道商管理列表在租户 Host 下只返回本租户 `HubProvider.tenant_id` 数据；无租户上下文仍沿用原平台全局列表行为。历史 `tenant_id IS NULL` 数据没有被自动归入任何租户。
- 渠道商 Logo、状态、服务费设置、收益明细、收益汇总和人工收益调整均增加按资源 ID 的租户归属校验；跨租户资源按不存在处理，不泄露资源是否存在。

- 健康排名在租户 Host 下只构造本租户渠道商的 Channel/Model 行，平台公共池和其他租户不会出现在结果中。
- 路由指标在租户 Host 下按本租户供给渠道过滤响应；查询仍复用现有全局指标聚合逻辑，并在控制器层做有界过滤，暂不重构指标存储和聚合链路。
- 管理员使用日志列表和日志统计在租户 Host 下按本租户的 `HubSupplyGroup.new_api_channel_id` 过滤；主库先解析 Channel ID，日志库只执行 `channel_id IN (...)`，因此兼容日志独立库/ClickHouse，不做跨库 JOIN。
- 无渠道的租户管理日志查询返回空结果；平台管理员没有租户上下文时继续使用原全平台日志范围。
- 本步按当前 Channel 与供给关系解析租户范围；已删除或尚未归属的历史 Channel 没有自动归入租户，也不伪造历史归属。后续若要求渠道迁移/删除后仍可按原租户查历史日志，需要单独增加归属快照，当前不扩大范围。
- 本步只过滤日志记录本身，租户管理员响应中的 `Other.hub_attempts` 诊断链暂不做跨租户匿名化，作为后续独立的展示脱敏议题；普通用户仍沿用既有脱敏逻辑。
- 已补充普通用户、活跃/禁用成员、平台管理员、Provider 列表/按 ID 写操作、渠道 ID 范围和健康列表范围测试。
- Channel 管理路由已统一经过租户权限策略：普通总代理只可查看本租户 Channel 列表、搜索和详情；测试、余额刷新、全局 `Channel.Status`、删除、编辑及其他操作不会因为租户成员关系被放行。租户上架/下架继续使用独立的 `HubSupplyGroup.TenantPublished` 接口。平台管理员和超级管理员仍按原有平台级 `authz` 权限访问。

前端在租户总代理上下文中只展示渠道页面和渠道商页面等允许入口；渠道列表不再请求平台级 ownership 统计，也不展示平台或其他总代理的归属筛选。渠道行和批量操作只保留租户级上架/下架，隐藏测试、余额刷新、全局启停、编辑、删除和标签操作。前端隐藏只是减少误操作，不能替代后端鉴权。

### 6.5 T1-B-3 已实现：超级管理员租户初始化入口（2026-08-23）

为便于内测先建立“域名 -> 租户 -> 总代理用户”的最小闭环，已增加平台超级管理员专用的 `/tenant-admin` 页面和对应 RootAuth 接口：

- 超级管理员可以创建、启用或停用租户；租户标识使用受限的 slug，后续用于品牌域名解析，不把普通用户角色改造成平台角色。
- 超级管理员可以给租户添加域名，选择主域名，并选择是否立即标记为已信任。当前“立即信任”是内测初始化开关，不等于已经实现 DNS TXT 或 HTTP 文件自动验证。
- 超级管理员可以搜索启用中的普通用户，并把用户指定为该租户的 `owner/admin`；成员角色第一版只做访问授权，不拆出不同业务权限。
- 每个租户最多只能有一个 `owner`，唯一性不受成员 `active/disabled` 状态影响；停用 owner 不会释放 owner 角色。更换 owner 必须先把旧 owner 改为 `admin`（或移除该成员），再设置新 owner。这样允许短暂没有 active owner，由管理员完成角色交接；实际访问仍要求成员为 active 的 `owner/admin`。
- 页面只对超级管理员显示；普通总代理不可以管理 Tenant、Domain 或 Member，也不能通过修改请求参数跨租户操作。

最小测试路径：超级管理员创建租户 -> 添加并信任测试域名 -> 指定普通用户为 `owner` -> 用该用户访问该可信域名的 `/providers` 和 `/channels`。未验证、停用或未知域名不会建立租户上下文；普通用户在平台主域名下仍不能凭成员关系获得总代理权限。该入口不改余额、计费、路由、收益或提现账本。

### 6.6 已实现：超级管理员渠道商总览（2026-08-23）

平台超级管理员在任意可信域名访问 `/providers` 和 `/channels` 时都使用平台全局范围，并保留总代理筛选；总代理管理员仍只看到当前域名对应的本租户数据。早期的 `/provider-overview` 只读页面保留兼容，但不再显示独立菜单，避免和 `/providers` 重复。

- 总览只读，不提供跨总代理审核、下架、结算或其他写操作，避免扩大超级管理员以外的操作边界。
- 支持按全部总代理、指定总代理、渠道商状态和渠道商/用户/官网关键词筛选。
- 列表展示渠道商所属总代理、所有者、状态、渠道数量、可用模型数量和创建时间；`tenant_id` 为空只作为历史兼容或数据异常处理，不在界面中表现成一种合法经营类型。
- 后端 `GET /api/hub/admin/provider-overview` 及 Logo 接口均使用 `RootAuth`；普通管理员和总代理不能通过 URL、查询参数或图片接口跨租户读取数据。
- 当前历史数据仍按既有迁移规则保留：`tenant_id IS NULL` 只表示历史归属待确认，不新增“平台直营”类型，也不改变路由、计费、收益和提现行为。

## 7. 渠道商创建、审核与归属

已确认总代理支持两种入口：

### 7.1 管理员直接创建

域名管理员可以在本租户直接创建渠道商，但首版只允许绑定一个已启用且尚未拥有渠道商的现有用户，不发出认领邀请。创建成功后渠道商直接为 `active`，所有者立即可以进入渠道商中心配置供给；一个用户仍只能拥有一个渠道商。

- 租户管理员只能创建到当前可信 Host 对应的总代理，不能通过请求体改写 `tenant_id`。
- 平台超级管理员必须明确选择目标总代理，不能把渠道商创建成没有归属的历史数据。
- 创建时默认生成带四位短标识的临时子域名；平台超级管理员和租户管理员都可以关闭该开关，直接申请无短标识子域名。关闭时由后端检查租户内唯一性；同一租户名称已占用就拒绝创建，不同租户不冲突。
- 所有者候选接口只返回已启用、未删除且尚未拥有渠道商的用户；后端在创建事务中再次校验。
- 创建后，管理员点击渠道商名称进入 `/provider/:providerId`，查看该渠道商资料、收益摘要和渠道列表；接口同时执行超级管理员全局范围或总代理本租户范围校验。
- 认领邀请、管理员迁移所有者和创建时上传徽标暂缓，后续确有需求再单独设计。

### 7.2 用户提交申请

用户从租户品牌入口提交申请时，申请自动带上服务端解析的 `tenant_id`。域名管理员可以审核本租户申请，平台超级管理员保留复核、停用和纠正能力。

### 7.3 状态操作

- 域名管理员停用渠道商只影响该渠道商及其 Channel，不自动禁用用户账号。
- 域名管理员对具体 Channel 的上架/下架只修改租户上架状态；渠道商主动禁用、平台禁用和自动健康状态保持独立，任何一层禁用都不能被其他层自动恢复。
- 超级管理员可以冻结租户；租户冻结后的品牌入口、渠道管理、供给和结算具体行为需在 T1/T3 讨论。
- 历史未归属渠道商归入某个总代理、总代理之间迁移或解除归属，只能由超级管理员执行并记录审计；第一版不提供自助迁移。归属确认前，不新增新的经营类型，也不把数据自动塞入某个默认总代理。

### 7.4 渠道创建入口

- 渠道商页面或渠道商详情页是创建供给渠道的唯一入口，创建时同时建立 `Channel`、`HubSupplyGroup` 和渠道商归属关系。
- 全局渠道列表只用于查看、搜索、上下架、测试、健康状态、排名和管理员治理，不提供创建渠道入口。
- 已关闭全局渠道列表的前端创建按钮和后端 `POST /api/channel/` 路由；渠道创建只走渠道商页面或详情页，避免产生没有总代理和渠道商归属的孤儿 `Channel`。
- 已修复租户渠道管理的只读辅助接口权限：总代理可以读取模型、运行参数和归属筛选选项，归属选项只返回当前租户；渠道编辑、删除、测试、密钥等敏感操作仍需平台权限。
- 从已解析的可信租户域名提交渠道商入驻时，服务端自动写入 `HubProvider.tenant_id`；平台主域名提交的历史数据仍需管理员确认后回填。

## 8. 日志、排名与可见性

- F1 排名对象仍是 `Channel + Model + EndpointType`，总代理身份不进入健康分和路由分。
- 超级管理员查看全平台排名；域名管理员只查看本租户 Channel 排名。
- 域名管理员可以按渠道商聚合查看，但不能查看其他租户原始排名。
- 日志必须区分入口租户、入口渠道商、实际服务租户、实际服务渠道商和实际 Channel。
- 系统探测和管理员测试不计入用户消费账，界面也应与真实请求区分。

建议请求与账本至少持久化或快照以下归属：

```text
origin_tenant_id
origin_provider_id
served_tenant_id
served_provider_id
served_channel_id
```

不能只在查询时通过当前渠道商关系反推历史租户，否则渠道商迁移后旧账会改变归属。

## 9. 多方分账边界

已确认：费率分为两层，权限不能混用：

- **渠道商服务费率**：默认 `10%`。总代理可以配置本租户默认值，并按每个渠道商单独覆盖，用于商务让利；渠道商只读自己的有效费率。
- **平台对总代理抽成率**：默认按总代理实际毛利润的 `30%`。仅平台超级管理员可以配置，总代理只读。

成功请求需要分别计算并可审计：

```text
用户实际扣费
  -> 实际服务渠道商收益
  -> 入口渠道商引流收益（如适用）
  -> 域名总代理分成（如适用）
  -> 平台收入
```

已确认并按第一版实现：

1. 跨租户平台兜底时，总代理毛收入归最终实际服务渠道商所属的服务总代理，不给入口总代理隐式分成。
2. 现有 1% 入口渠道商引流收益仍从实际服务渠道商收入中扣除，不参与总代理毛利润和平台抽成计算。
3. 退款、失败重试、转余额和提现继续复用现有收益账本的幂等流程；分账费率只在成功请求建立时快照。

无论最终公式如何，都必须满足：

```text
用户实际扣费 = 各收益方入账 + 平台收入
失败尝试不重复扣用户费用，也不生成渠道商或总代理收益
同一 request_id + settlement_type 幂等
```

不得把总代理比例直接叠加到现有服务费字段，以免平台收入为负或重复分成。历史 `tenant_id IS NULL` 的渠道仍按旧账务解释，完成归属回填后新请求才启用两层分账。

### 9.1 已确认的费率层级

总代理分成采用两层抽成：

1. 先按最终服务渠道商的有效服务费率计算总代理毛收入；租户默认 `10%`，总代理可按渠道商覆盖。
2. 总平台再按总代理毛收入计算平台服务费，默认 `30%`。
3. 扣除平台服务费后的金额是总代理净收入。

- 渠道商服务费率由总代理配置；平台对总代理抽成率由超级管理员配置。两者都必须有全局/租户默认值和历史快照。
- 总代理可以为每个渠道商调整服务费率，包括给大渠道商降到 `5%` 或 `0%`；平台只对总代理实际产生的毛利润抽成，不设置虚拟保底利润。
- 两层分成都只拆分成功请求的既有用户扣费，不增加用户扣费，不改变模型价格和倍率。
- 历史归属待确认的渠道商暂不套用新的总代理分账规则；完成实际归属确认并回填 `tenant_id` 后，才进入对应总代理的服务费和分账规则。

新账单（`settlement_version = 2`）保存以下请求快照，修改配置不会回算历史账单：

```text
tenant_id
provider_service_fee_basis_points
platform_fee_basis_points
reseller_gross_quota
reseller_net_income_quota
```

其中 `platform_fee_basis_points` 的单位是万分比，默认 `3000 = 30%`；它的计算基数是总代理毛收入，不是用户消费额。渠道商服务费率也是万分比，默认 `1000 = 10%`，可由总代理按渠道商覆盖。

以用户消费 `100`、总代理毛分成 `10%`、平台抽取总代理毛收入的 `30%` 为例：

```text
总代理毛收入   = 100 × 10% = 10
总平台收入     = 10 × 30% = 3
总代理净收入   = 10 - 3 = 7
服务渠道商收入 = 100 - 10 = 90
```

平台对总代理的抽成可在前期设置为 `0%`，此时总代理毛收入和净收入都是 `10`；后续调整只影响新请求，历史账目使用请求成功时的费率快照，不反算。

若总代理把某个渠道商服务费率降为 `5%`，同样消费 `100` 时：渠道商收入 `95`、总代理毛收入 `5`、平台收入 `1.5`、总代理净收入 `3.5`。若降为 `0%`，渠道商收入 `100`，总代理和平台本次收入均为 `0`。

### 9.2 跨域名兜底账务（已确认第一版）

这里的两个总代理是两个不同概念：

- **入口总代理**：用户从哪个品牌域名进入，或者当前用户关系归属于哪个租户。例如用户从 `aiproxy.com` 进入，入口总代理就是 A。
- **服务总代理**：最终成功响应的 Channel 属于哪个租户。例如平台兜底选中了 B 租户的 Channel，服务总代理就是 B。
- 如果入口 Channel 和最终服务 Channel 属于同一租户，入口总代理和服务总代理是同一个，不产生跨域名拆分。

跨域名时必须同时快照：

```text
origin_tenant_id       // 用户从哪个总代理域名进入
origin_provider_id     // 用户原本选择或亲和的渠道商
served_tenant_id       // 最终服务渠道商属于哪个总代理
served_provider_id
served_channel_id
```

保留现有单请求渠道商收益记录，并增加每个请求最多两条租户收益明细（入口、服务租户相同时只写一条），不建设通用财务总账：

```text
渠道商收益记录（现有 `HubProviderEarning`）
  serving_provider_income
  origin_provider_referral_income
  reseller_gross_income

同一条收益记录的租户分账快照
  request_id + tenant_id
  provider_service_fee_basis_points
  reseller_gross_quota
  platform_fee_basis_points
  platform_fee_quota
  reseller_net_income_quota
```

每笔请求必须满足：

```text
用户扣费 = 服务渠道商收入 + 入口渠道商引流收益 + 总代理毛收入
总代理毛收入 = 各总代理净收入 + 总平台收入
```

费率、归属和策略版本在请求成功时快照；渠道商之后迁移租户不能改变历史账目。跨域名兜底时，以最终实际服务渠道商当时生效的渠道商服务费率计算总代理毛收入，入口渠道商或入口租户的费率不改变服务渠道商合同。跨域名只影响成功请求的收入拆分，失败尝试仍不扣费、不产生任何收益。

当前建议的最小版本是：跨域名时，总代理毛收入归**实际服务渠道商所属的服务总代理**，不默认在入口和服务总代理之间做 `50/50` 拆分。原因是这笔费率来自服务总代理与旗下渠道商的商务约定，且服务总代理承担了实际供给和稳定性责任；入口租户不应凭“用户从这里进入”自动获得一半利润。

如果以后需要奖励入口总代理的获客、客服和品牌经营，再新增明确的“租户引流费率”，按平台配置并单独快照；不能用一个没有业务名称的 `50/50` 隐式分账。

仍需确认的选项是：

1. 全部归实际服务租户：最简单，也奖励稳定供给；入口租户只保留现有兜底引流收益。
2. 全部归入口租户：符合“谁运营用户谁取得经营收入”，但实际服务租户没有管理供给的收益。
3. 在入口租户和服务租户之间拆分：兼顾获客和供给，但需要额外比例、舍入和历史快照。

第一版建议选择方案 1。若用户消费 `100`、服务渠道商费率 `5%`、平台抽成率 `30%`：服务渠道商得 `95`，服务总代理毛收入 `5`，平台得 `1.5`，服务总代理净得 `3.5`。入口总代理不额外取得总代理分成；若本次同时满足现有入口渠道商 `1%` 引流规则，该 `1` 仍从服务渠道商收益中支付，服务渠道商最终得 `94`。

现有 1% 是具体入口渠道商的引流收益，从服务渠道商收益中支付，与总代理收入分开列示，不能混成同一分录。

### 9.3 资金闭环与提现审核（待确认）

#### 9.3.1 平台统一收款

用户充值必须由平台统一接收并进入现有平台钱包。总代理不能在平台外向用户收款，否则会导致：

- 用户余额、模型扣费和退款无法由平台统一保证；
- 用户从不同品牌域名进入时无法共用一个可信余额；
- 平台无法核对总代理实际收款和渠道商收益；
- 跨域名兜底、失败退款和转余额会出现平台账外资金。

如果总代理自行向用户收款并自行向渠道商打款，那就已经是总代理独立经营的另一套支付系统，这部分交易事实上不属于 LLM-Hub 的统一账务和保障范围，不应和平台内的 API 消费混在一起。第一版不采用这种模式。

#### 9.3.2 系统自动审核，平台统一打款

总代理可以参与运营查看，但不需要人工逐笔“批准”提现。当前实现申请提交后由系统在同一事务内完成预审，通过后直接进入“待平台打款”；历史遗留或人工创建的 `pending` 仍可由平台复核。状态为：

```text
申请中
  -> 系统预审通过并冻结可提现额度
  -> 待平台打款
  -> 已打款 / 打款失败
```

系统预审至少检查：

- 收益已经结算，不是 pending；
- 金额达到最低提现额且可提现余额充足；
- 没有重复的冻结或进行中的提现；
- 收款账户快照有效；
- 账户、渠道商和租户均处于允许提现状态；
- 幂等键、额度冻结和状态迁移有效。

总代理可以查看本租户提现；系统预审未通过的历史/异常申请保留在“申请中”，由平台人工复核，不直接把平台资金标记为已打款。超级管理员可以驳回或处理异常提现。总代理自己的经营收益提现和存在利益冲突的申请同样只由平台确认实际打款。

#### 9.3.3 对账

平台按内部账本和支付结果自动对账：

```text
可提现余额
= 已结算收益
 - 已转入用户余额
 - 进行中提现冻结额（申请中/审核通过但未打款）
 - 已打款提现
```

“进行中提现冻结额”和“已打款提现”必须互斥；已撤销或失败的提现不进入扣减项，额度释放后自然回到可提现余额。这样不能因为状态迁移或重复对账把一笔提现扣两次。

每笔外部打款都保存唯一支付单号、金额、收款账户快照、状态和时间。定时对账发现“内部已打款但外部失败”“外部成功但内部未完成”或金额不一致时，自动告警并暂停相关自动处理，不人工修改历史收益分录。

#### 9.3.4 T5-3 第一版：内部只读对账

第一版先不接外部支付 API，也不自动把提现推进为已打款。超级管理员在“总代理财务总览”中看到每个租户的只读对账状态：

- 核对启用租户是否有且只有一个 active owner；
- 核对转余额分录是否为已结算的负向租户收益；
- 核对提现状态、金额、收款账户快照和已打款字段是否完整；
- 核对进行中的提现是否重复，以及转余额/提现冻结额是否超过已结算收益。

正常显示“账目正常”，异常显示“需要人工检查”和具体原因。对账只读，不会自动修改收益、冻结额度、提现状态或用户余额；异常继续保留平台人工处理路径。自动预审和外部支付结果对账另列后续小步。

### 9.4 提现资金责任

- 收入属于实际服务渠道商所在租户，因此跨域名兜底产生的服务渠道商收益由 `served_tenant_id` 对应的总代理查看和运营；资金仍由平台统一结算。
- 提现申请继续锁定可提现余额，审核不能改变收益金额、收款账户快照或历史分录。
- 总平台保留冻结、驳回、人工调账和审计权限。

### 9.5 退款与责任归属（待确认）

#### 9.5.1 用户退款口径

- API 请求的合格退款按用户本次**实际扣除的余额/额度**返还，不按扣除平台服务费后的净额返还。用户不应该因为平台内部的分账规则少拿退款。
- 请求失败、没有有效输出或平台规则认定为不可用结果时，返还本次实际扣费；失败尝试不生成渠道商、总代理或平台收益。
- 已产生有效输出的请求，默认按实际有效用量结算；用户对有效结果的主观不满意不自动触发全额退款，另走客服规则。
- 余额返还和收益冲销使用同一个 `request_id` 的幂等结算链；现金充值退款属于支付系统规则，不与 API 请求余额冲销混用。

#### 9.5.2 内部冲销顺序

用户返还 `R` 时，平台内部同时冲销该请求对应的分账：

```text
取消未结算的渠道商/总代理收益
  -> 冲回已结算的实际服务渠道商收益
  -> 冲回服务总代理毛收益
  -> 冲回平台从该总代理收益中取得的抽成
  -> 冲回入口渠道商引流收益（如有）
```

平台不因为退款继续保留本请求的平台抽成。这样用户拿回的是实际扣费，平台也不会把退款成本伪装成平台收入。

#### 9.5.3 谁承担上游失败成本

不新增人工追踪上游账单或索赔系统，沿用平台现有请求和收益账本：

1. 实际服务渠道商是第一责任方，因为上游凭证、Base URL 和上游关系由它提供；其待结算收益先被取消，已结算部分形成负向调整或从后续收益抵扣。
2. 渠道商归属的总代理是第二责任方。总代理从旗下渠道商服务费中获益，也负责渠道商的入驻和运营；渠道商余额不足时，是否由总代理承担补足责任需要写入总代理合作规则。
3. 平台只负责先把用户账务恢复正确，不把这笔退款记成平台最终损失，也不替渠道商或总代理永久核销负债。

如果只是平台自身路由失败且请求没有产生上游成本，用户余额仍按规则返还，但不应生成任何渠道商或总代理负债。真正需要承担上游成本的场景，以实际服务渠道商与总代理之间的合作约定为准。

为避免已提现收益无法冲回，自动提现前应只使用已结算且通过观察期的余额；已经打款后发生退款，则记录负向收益并抵扣该主体未来收益，长期无法抵扣的异常由平台人工处理，不直接从平台收入中核销。

## 10. 审计要求

以下操作至少记录操作者、平台角色、租户、资源、操作前后值、时间、请求 ID 和来源 IP：

- 创建、审核、停用和迁移渠道商。
- 新增、验证、启用和移除独立域名。
- 新增、移除租户管理员或修改成员角色。
- 创建、修改、启停总代理分成规则。
- 超级管理员跨租户修改数据。
- 提现、结算和人工账务调整。

敏感字段如上游密钥、Token 和密码不能写入审计明文。

## 11. 渠道额度与上游域名风控

当前只记录治理方向，不在角色权限模块实现：

- 每个普通账号或渠道商可免费创建的启用供给 Channel 有上限，初步观察值为 5 条。
- 付费扩容、认证后扩容和管理员特批与免费额度分开记录。
- 统计规范化上游 origin，识别同一上游域名被多少账号、渠道商和 Channel 使用。
- 同一上游 origin 的复用量达到可配置阈值后触发增强认证和人工审核；`100` 只是早期观察值。
- 域名重复是风险信号，不能自动证明主体相同，也不能自动合并收益。
- 第一版渠道商归一化继续防止仅靠拆分 Channel 增加流量。

## 12. 实施顺序

每个阶段单独讨论、实现、测试和更新状态，不一次铺开全部功能。

### 12.1 小步交付与联合验收

每个可独立验证的小步都按同一个闭环推进：

```text
确认本步范围和不做项
  -> 实现最小改动
  -> 自动化测试与代码检查
  -> 更新设计/实现文档
  -> 发布 LLM-Hub 内测环境
  -> 提供用户测试任务和预期结果
  -> 用户实测并反馈
  -> 核对服务日志、路由数据和账务数据
  -> 共同确认通过后标记完成
```

- 不等整个 T1-T7 全部完成后再集中验收；优先拆成用户能理解、能操作、能观察结果的小步。
- 每次交付都说明本次改了什么、未改什么、测试入口、测试账号/角色前提、操作步骤、预期结果和需要反馈的数据。
- 自动化测试负责权限边界、越权、迁移和账务不变量；用户验收负责真实角色体验、页面信息、操作流程和业务结果，两者不能互相替代。
- 用户操作完成后，由开发侧核对服务日志、数据库归属、路由尝试和分账结果，不能只以页面提示成功作为通过依据。
- 用户验收未通过时停留在当前小步修复；原则上不进入依赖该结果的下一步。
- 讨论中的临时问题先记入对应章节。除非阻塞当前验收或存在数据/资金风险，不临时扩大当前实现范围。
- 文档设计阶段不发布；进入代码阶段后，仍遵循 LLM-Hub 内测期约定，完成自动验证后直接发布供用户测试，无需重复请求发布确认。
