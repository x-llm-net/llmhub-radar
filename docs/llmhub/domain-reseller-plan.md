# 独立域名总代理专题

## 1. 文档状态

本文记录未来的域名级总代理能力，和“渠道排名与 Affinity 恢复切换”的 F1-F6 分开讨论、分开实施。当前只固定会影响其他模块的数据和权限边界，不立即修改域名解析、管理后台或账务。

示例：总代理拥有 `aiproxy.com` 并将域名解析到 LLM-Hub。总代理可以在该品牌域名下管理多个渠道商；终端用户仍使用 LLM-Hub 的账号、密钥、路由和平台兜底能力。

## 2. 已确认角色

### 平台超级管理员

- 管理全平台模型、模型价格、New API 系统配置和平台路由参数。
- 管理所有总代理、渠道商、Channel、认证、风控和平台级排名。
- 查看全平台账务，并配置平台与总代理之间的分成规则。

### 域名级总代理管理员

- 管理自己的品牌域名、品牌资料、成员和下属渠道商。
- 查看自己租户范围内的渠道、F1 排名、流量、收益和分成数据。
- 不能进入 New API 平台级管理后台，不能配置全局模型、平台路由或查看其他租户数据。

### 渠道商

- 继续管理自己的资料、供给 Channel、倍率和收益。
- 可以归属于平台直营范围，也可以归属于某个域名总代理租户。
- 渠道商供给仍由实际成功 Channel 获得收益，不能因为入口域名而改变服务归属。

## 3. 建议领域模型

独立引入 `Brand/Tenant`，不在 `HubProvider` 上增加递归 `parent_provider_id`：

```text
Tenant
  -> Domains
  -> TenantAdmins
  -> Providers
  -> RevenueSharePolicy
```

这样总代理是品牌和经营范围，不是假装成一个特殊渠道商。首版只支持平台到总代理、总代理到渠道商两级，不做无限级代理树。

## 4. 多方分账边界

一次成功请求至少区分：

```text
platform_id
tenant_id
origin_provider_id
served_provider_id
served_channel_id
```

账务方向先记录为待讨论：

```text
用户实际扣费
  -> 实际服务渠道商收益
  -> 域名总代理分成（如适用）
  -> 平台收入
```

需要单独确认总代理分成按平台服务费、渠道商收益、用户消费额还是固定差价计算。未确认前不得把一个比例直接叠加到现有服务费字段，否则容易造成平台收入为负或重复分成。

平台兜底到租户外渠道时，总代理是否仍获得入口流量分成也需要单独确认；该决策不应通过修改 `served_provider_id` 实现。

## 5. 对当前 F1-F6 的影响

- F1 排名接口必须支持租户范围过滤：超级管理员全量，域名管理员仅本租户。
- F2 健康分只评价 Channel，不加入总代理收益或品牌因素。
- F3 路由不能因为总代理身份突破模型、端点、倍率、健康和循环保护边界。
- F4/F5 Affinity 键未来需要包含租户/入口域名范围，避免同一用户跨品牌复用错误亲和。
- F6 验收需要增加跨租户越权、租户内渠道商故障和平台兜底账务场景。

这些是兼容要求，不代表总代理功能要先于 F1-F6 实现。

## 6. 渠道额度与上游域名风控

当前建议作为治理规则记录，不直接写死阈值：

- 每个普通账号或渠道商可免费创建的启用供给 Channel 有上限，初步建议为 5 条。
- 付费扩容、认证后扩容和管理员特批应与免费额度分开记录。
- 统计规范化后的上游 origin（协议、主机、端口），识别同一上游域名被多少账号、渠道商和 Channel 使用。
- 同一上游 origin 的复用量达到可配置阈值后，触发更强认证和人工审核；`100` 可以作为早期观察值，不能先写成永久安全边界。
- 域名重复只作为风险信号，不能直接证明多个 Key 或渠道一定属于同一主体，也不能自动合并收益。
- 创建额度不能代替流量公平。F3 仍需决定重复 Channel 是否累加权重，以及同渠道商在单个模型池中的总份额是否受限。

在个人/企业认证和一人多账号约束完成前，“每个账号 5 条”只能降低滥用速度，不能彻底阻止规避。

## 7. 后续功能点

### T1：Tenant 与域名归属

创建租户、验证独立域名、配置根域和渠道商子域解析，明确域名冲突和迁移规则。

### T2：租户管理员权限

实现租户成员、角色和服务端数据范围授权；禁止依赖前端菜单隐藏实现隔离。

### T3：租户下渠道商管理

定义总代理创建、邀请、审核、停用和迁移渠道商的流程，以及平台超级管理员的最终控制权。

### T4：品牌入口与用户归属

定义注册、登录、充值、密钥、公开页和跨域 Cookie/OAuth 行为；明确用户是否属于租户以及能否跨品牌使用余额。

### T5：多方分账

确定分成基数、优先顺序、退款、失败请求、平台兜底、提现和账本幂等规则。

### T6：额度、认证和风控

实现免费 Channel 上限、上游域名复用统计、增强认证、人工审核和管理员特批。

### T7：隔离验收

覆盖跨租户权限、域名冲突、渠道商迁移、平台兜底、多方账务和循环依赖。

## 8. 后续讨论入口

该专题以后从 **T1：Tenant、独立域名和渠道商归属关系** 开始，不在当前 F1-F6 讨论中展开。
