# 倍率路由加固清单

> 当前实现以 `tokens.hub_routing_policy` 为新 Token 的权威路由约束。四个服务档位仅保留旧请求兼容和 UI 辅助含义，不是新 Token 的跨档边界；倍率合法范围为 `0.01-100.000`，允许大于 `1.000`。

状态：审查完成，按批次修复中。本文件记录当前仍需处理的风险、已确认决策和验收条件；完成项应保留并标记状态，避免同类问题再次引入。

## 已确认决策

> 以下旧四档条目保留为历史兼容记录。新倍率策略以本节新增规则和“动态倍率令牌实现记录”为准。

- 新策略 Key 的内部 `group=default` 只为兼容存储；计费基准固定为 `1x`，不得再乘旧 `GroupRatio` 或用户分组覆盖。
- 根域每个模型族保存一个倍率闭区间；渠道商子域每个模型族只保存一个已发布的精确倍率。
- 新策略合法倍率为 `0.01-100.000x`，允许官 Key、CCMax 等 `1x` 以上供给；四档名称仅是界面标签。

- 供给倍率统一使用小数倍率：`1.0 = 1x = 100%`，`0.1 = 0.1x = 10%`。管理页面必须明确显示 `x`，不得用 `100` 表示无限或 100%。
- 高品质档是“质量资格 + 价格保护”，不是 `medium` 之上的连续价格区间。首版高品质最高供给倍率保护建议为 `1.0`，以后由管理员配置。
- 同一个 `Channel + Model` 可以同时满足多个服务档位。经过高品质审核的低价供给可以服务高品质 Token；这不属于跨档兜底。
- 一次用户请求始终使用 Token 选择的服务档位，重试和平台兜底不得切换档位。
- 四档 `GroupRatio` 继续固定为 `1`；最终用户扣费使用实际命中供给的倍率。
- 修复按小批次进行，每批包含行为测试、失败路径测试和文档更新，不同时重写全部核心链路。

## 批次 A：倍率语义与配置一致性

优先级：最高。先完成本批，再继续扩展动态权重和容量算法。

- [x] 删除高品质默认值 `100` 的伪无限语义，默认价格保护改为 `1.0`，前后端统一使用 `x` 单位；读取旧值恰好为 `100` 的未上线配置时兼容归一为 `1.0`。
- [x] 将 Ability 从“每个供给只进入一个档位”改为“按每个 Token 档位独立判断资格”，支持一个 `Channel + Model` 同时进入多个档位。
- [x] 高品质候选必须同时满足管理员质量审核和价格保护；提高售价不能自动获得高品质资格。
- [x] 边界值必须全部为有限正数；特价、经济、标准边界严格递增，高品质最高倍率作为独立价格保护校验。
- [x] 增加专用的路由配置保存接口，一次事务保存完整配置，只重建一次 Ability。
- [x] 配置保存失败时不得更新前端基线；后端检查数据库写入和 Ability 重建错误后才发布运行时配置。
- [x] 路由运行时配置改为受保护的不可变快照，避免请求读取与配置发布并发读写 map/slice。
- [x] 增加确定性端到端回归，覆盖供给探测上架、服务档位 Token、渠道商优先、同档兜底、最终扣费、最终渠道商收益和 `hub_attempts` 尝试链。
- [x] 系统设置首次加载失败时显示错误和重试，且不挂载配置表单；后端返回 `success: false` 或非法数据结构同样按失败处理，禁止使用前端默认值覆盖真实生产配置。已有真实缓存但后台刷新失败时仍可继续查看缓存配置。
- [x] Token 创建不检查瞬时供给可用性；运行时同档候选耗尽时返回 HTTP `503`、`error.code = service_tier_unavailable`、`Retry-After: 30` 和 `request_id`。倍率策略 Key 请求一个在当前倍率策略内从未配置供给的模型时返回非重试型 HTTP `404`、`error.code = model_not_found`，避免客户端把永久不支持误判为临时故障。两种情况都不跨档、不禁用或修改 Token，后续增加或恢复合规供给后原 Token 可直接使用。
- [x] Token 创建和完整更新接口在档位路由启用时强制校验四档，拒绝空值、`auto`、任意字符串和不允许的旧分组；注册接口生成的初始 Token 固定使用 `medium`。仅状态更新与历史 Token 读取不受影响，关闭档位路由后保留旧分组写入兼容。
- [x] 管理员固定 Channel Token 在服务档位请求中校验模型、同档 Ability、当前请求端点资格、供给渠道商状态和子域渠道商归属；校验失败固定返回 `503 service_tier_unavailable`，传统 New API 分组继续保留固定渠道的旧行为。
- [x] 高品质渠道商选择器改为服务端搜索和分页（每页 20 条），不再依赖超过后台 100 条上限的单页请求；已选渠道商 ID 跨页和搜索保持。
- [x] 配置变更、模型定价变更和版本升级启动时正确重建相关 Ability，并在成功后刷新缓存。
- [x] 模型家族分类补齐已维护模型清单中的常见 OpenAI/Google 文本、图片、音频、Embedding 和 Moderation 标识，并增加回归用例；未知模型仍归入 `other`，默认不进入服务档位，需管理员显式开启。

验收：`100` 不再出现为默认倍率；低价且已审核的优质供给可服务高品质 Token；多字段保存不会暴露中间配置；非法 Token 分组无法通过 API 创建。

## 批次 B：循环保护与路由安全

- [x] `request_loop_detected` 具有终止语义，不进入普通状态码重试、计费或结算；对外使用 HTTP `400` 阻止旧版 New API 重试，第三方普通 `508` 仍保留现有可配置重试语义。
- [x] `request_loop_detected` 固定排除 Channel 自动禁用；即使管理员调整自动禁用状态码范围，平台生成的循环错误也不会关闭渠道。
- [x] `channel:model_mapped_error` 只记录模型/端点级失败，不触发 Channel 级自动禁用，避免一个模型映射错误误伤同渠道其他模型。
- [x] `channel:endpoint_unsupported` 用于端点不匹配或适配器明确不支持的请求；该错误只影响本次 `Channel + Model + Endpoint` 尝试，允许同档重试且不触发 Channel 级自动禁用。上游 `model_not_found` 同样不触发整条 Channel 自动禁用。
- [x] 多端点模型按现有探测 `ProbeKind` 隔离文本与图片资格；一类探测失败不会删除另一类健康端点的模型 Ability。缓存、数据库直查和 Affinity 命中均按当前请求类型复查，全部探测类型失败后才让该模型退出路由。
- [x] 所有已接入 relay 入口在认证后校验平台签名的 hop 标记；标准 HTTP、multipart/form、任务提交、Midjourney 和 Realtime WebSocket 的统一上游路径最终覆盖并递增标记，达到第 3 跳时终止。
- [x] 请求指纹扩展到非空非 JSON `POST`；JSON 继续规范化，multipart、表单和其他请求体使用原始哈希，Gemini 等查询认证参数不参与指纹。
- [x] 10 个现有后台任务轮询适配器在认证/签名完成后、发出请求前补齐初始 hop 标记；未修改 `TaskAdaptor` 接口。少数其他绕过统一 HTTP 请求层的历史直连适配器仍待单独审计。
- [x] 渠道亲和命中时同时检查 Channel、供给扩展和渠道商均为启用状态；拒绝后清除失效亲和。
- [x] 服务档位在数据库直查和内存缓存路径都严格排除本次已失败 Channel；普通 New API 分组在候选全部尝试后仍保留原有复用行为。
- [x] 服务档位重试预算恰好耗尽且最后错误仍可通过换渠道恢复时，最终统一返回 `503 service_tier_unavailable`；原始上游错误保留在 `hub_attempts`。客户端错误、循环保护、已开始响应和锁定原任务渠道不转换。
- [x] 路由候选、渠道归属、供给倍率和“已配置供给渠道”集合使用同一版本的不可变快照原子切换；完整 Channel 缓存刷新会同步替换 `hubSupplyConfiguredIDs`，普通选路和 Affinity 选路都在持有 Channel 缓存读锁时带出对应供给快照。
- [x] 供给归属或倍率快照缺失时失败关闭：缓存未命中会回查供给归属，确认数据库已有供给扩展但定价快照未发布时拒绝请求；平台自营渠道没有供给扩展时仍使用基础倍率。缓存中的供给归属、提供商状态、供给组和倍率字段不完整或倍率非法时同样拒绝。
- [x] 手工上架/下架将发布状态、供给组状态、Channel 状态和 Ability 重建合并到同一数据库事务；任一 Ability 写入失败时整体回滚，成功后才刷新缓存。
- [x] 运行时缓存刷新使用单一构建互斥和完整发布：Channel、Ability、探测资格、渠道商归属与供给倍率全部构建成功后才切换；任一读取失败继续使用上一份缓存。
- [x] 已选 Channel 后，后续计费和收益结算继续使用本次选路捕获的供给归属/倍率快照；请求内快照还区分平台 Channel 与供给 Channel 的归属缺失，避免把缺失供给误按 `1x` 计费。
- [x] 保留旧 `auto` 分组兼容时，渠道商优先与平台兜底不得破坏原有重试计数状态；渠道商优先按 Token 的有序 `auto` 分组依次尝试，耗尽后才进入平台兜底，平台兜底从独立的阶段重试计数开始。
- [x] 异步任务提交时在现有 BillingContext JSON 中快照入口 Provider 和路由阶段；续作只允许同一入口 Provider 的策略 Key，平台兜底到其他 Provider 不改变原入口归属。
- [x] 候选规模增加前预计算模型/档位/渠道商桶，避免每次请求扫描、分组和排序全部候选；内存缓存刷新时发布有序渠道商桶及其 `priority + weight` 候选，请求时仅对候选执行端点、渠道商状态和本次失败 Channel 校验。数据库直查路径保持原逻辑。

验收：模拟平台与渠道商互相回流时在固定跳数内终止；停用渠道商不会通过亲和继续命中；缓存刷新失败时保留旧的完整快照而不是进入混合状态。

## 批次 C：扣费、退款与渠道商收益

- [x] 高价重试在发起下一次上游请求前原子预留差额；钱包或订阅额度不足时固定停止并返回 `403 insufficient_user_quota`，由外层失败收尾退还此前预扣，不允许通过重试隐式产生负余额。响应已完成后的真实用量结算保持原逻辑。
- [x] 失败请求退款改为以 `request_id` 幂等、可重试的持久化流程；不能在实际退款成功前永久标记完成。`billing_refunds` 只保存用户、令牌、订阅和额度快照，不保存令牌明文；退款记录先落库，钱包、订阅基础预扣、订阅重试补差和令牌额度在同一数据库事务内回退并标记 `complete`。请求中断或瞬时数据库错误留下 `pending` 记录，由已有系统任务框架每 15 秒补扫；重复执行不会重复退款。
- [x] 用户扣费与渠道商收益使用可恢复的一致性流程；同步请求先以 `settlement_deferred=true` 准备收益，准备失败会阻止用户最终结算。用户扣费成功后原子写入最终 gross 并释放为 `false`，已有系统任务每 15 秒补结算；异步任务成功后同样原子发布最终 gross，恢复器不能在两步之间按预估额度抢先结算。
- [x] 用户资金已提交但 Token 调整失败时，不再错误取消渠道商收益；当前结算通过 `FundingCommitted()` 区分“资金尚未提交”和“资金已提交、Token 调整失败”。后者的渠道商收益保持待结算，并由 `billing_token_adjustments` 保存 Token 差额。
- [x] 渠道商可将可提现收益单向转入用户余额；转入记录复用收益账本并使用幂等键，渠道商锁、可提现校验、收益扣减和用户余额增加在同一主库事务完成。已申请提现、已打款或已转入余额的金额不能再次使用。
- [x] 同步请求在用户扣费后崩溃时，后台能够扫描和完成待结算收益；只有 `settlement_deferred=false` 的新记录进入恢复队列，避免旧异步任务被误结算。
- [x] 异步任务使用提交时保存的模型价格和倍率快照；按 token 重算优先读取 `TaskBillingContext.ModelRatio` 和已保存的综合/供给倍率，管理员在任务运行期间改价不会改变旧任务账单。历史任务缺少有效快照时才回退当前模型倍率配置。
- [x] 异步任务只有在成功差额结算完成后才能释放 `settlement_deferred` 并结算渠道商收益。成功任务使用 `billing_task_settlements`，成功终态 CAS 与结算意图在同一主库事务提交；钱包或订阅、Token、用户/渠道 `used_quota`、持久化 `Task.Quota` 和结算状态在后续同一主库事务完成。异步 Token 预扣和补差绕过内存批量余额队列，零差额也保留完成记录；失败保留 pending，15 秒恢复任务补结算并释放收益。任务失败退款继续复用 `billing_refunds`，原子完成资金、Token 和 `Task.Quota=0`，后台恢复后取消渠道商待收益。Suno 成功任务复用同一结算和收益释放流程。
- [x] 同步请求资金已提交但 Token 回写失败时继续使用 `billing_token_adjustments`；成功异步任务差额由 `billing_task_settlements` 整体恢复，失败异步任务由 `billing_refunds` 整体恢复。记录均使用稳定唯一引用且不保存明文 Token key。恢复失败按下一次尝试时间退避，避免永久失败记录阻塞整个批次。若恢复记录本身也无法落库，当前仍只能记录日志；差额日志与主库分离部署时也不宣称跨库原子。
- [ ] 异步差额日志写入和主库完成标记目前仍是跨库两步操作；进程可能在“日志已写、标记未写”之间造成重复日志，或在“标记已写、日志未写”之间造成日志缺失。该问题不影响主库扣费幂等，后续如需严格审计再设计日志 outbox/唯一引用，不在本批次扩大。
- [x] 首版明确不处理“失败但上游可能扣费”的人工补偿关联；失败尝试只保留 `request_id + attempt_index` 排查记录，不扣用户、不记渠道商收益，也不新增上游核账流程。后续若真实业务需要，再单独设计幂等补偿。
- [x] Realtime/WebSocket 在客户端连接升级后禁止跨 Channel 重试；分段预留和最终结算继续复用一个 BillingSession，避免第一次结算后第二条 Channel 继续产生未扣费 usage。
- [x] 收益准备失败不再继续扣用户；收益准备、释放和退款意图创建使用有限幂等重试。退款资金、Token、Task.Quota 和待结算 Provider 收益取消在同一主库事务完成；已结算收益不能同时退款。
- [x] 普通文本、音频和异步任务提交统一传播最终结算错误并禁止重试；未提交结算不增加累计用量，已提交资金或持久化 Token 差额按可恢复成功处理。固定价格音频补齐 `ModelPrice`。
- [x] 钱包和 Token 的预扣、重试补差及最终差额绕过 `BatchUpdate` 直写主库；只有非资金权威的累计用量统计继续使用批量更新。
- [x] 异步任务轮询按 `(channel_id, upstream_task_id)` 隔离，相同上游任务 ID 不再跨 Channel 覆盖其他用户任务。
- [ ] 进程仍可能在“用户资金提交成功、收益释放事务开始前”崩溃；数据库完全不可写时，退款意图和 Token 调整意图也无法落库。彻底关闭这些窗口需要把用户资金和账务意图纳入同一事务/outbox，须单独评审。
- [x] 异步任务失败终态与退款意图在统一轮询分支中以同一 CAS 事务提交；超时、缺少上游 ID、Suno/视频明确失败均不会先落失败再漏退款。查询接口非 `2xx` 只保留 pending，避免把上游查询故障误判为任务失败。适配器仍可能在本地任务与结算持久化前向客户端写出成功响应，这是已知窗口。
- [x] Provider 子域异步续作在使用锁定 Channel 前再次确认入口 Provider 仍为 active；原 Provider 停用后，根域和子域都不能继续续作。
- [x] Affinity 命中的 Channel、Provider 归属、状态和倍率校验均使用同一次捕获的定价快照，并有倍率刷新回归测试，避免管理员恰好更新归属或倍率时混用两代数据。
- [x] 订阅最终补差在允许钱包兜底时转由钱包承担；同步 `BillingSession` 与异步 `BillingTaskSettlement` 使用同一 `allow_wallet_overflow` 规则，只有明确的订阅额度不足才触发钱包补差，订阅不存在或数据库错误不会被误判为兜底成功。零基础价但产生工具/音频附加费的请求也进入标准 BillingSession，不再回落到批量余额更新。
- [x] 钱包最终补差和订阅钱包溢出使用余额条件更新；有限额 Token 的同步扣减、异步结算和恢复调账共用原子非负校验。余额或 Token 不足时不写负数；异步结算和 Token 调账保留 `pending`，无限额 Token 只累计已用额度，不减少展示余额，失败退款也不虚增无限额 Token 的展示余额并支持软删除 Token。
- [x] 成功上游的最终补差失败时不再整笔退回预扣额度：同步请求以已经保留的预扣额度作为最终计费、日志和渠道商收益的统一口径，平台不为未收取的差额支付渠道商收益；异步任务同样把已提交额度写入 Task 并在成功终态按该额度释放收益。首版不建立欠费账本。
- [x] 仍使用旧 `PostConsumeQuota` 的 Midjourney/违规费入口将钱包或订阅与 Token 调整合并到同一主库事务，Token 或资金任一不足都会整体回滚；订阅补差是否允许钱包兜底按本次实际使用的订阅快照判断，不因任务完成时订阅过期或其他订阅状态改变。
- [ ] 用户实际获得的上游用量可能高于补扣失败后保留的预扣额度；当前差额由实际供给方承担，平台和渠道商只按已收取额度结算。是否限制最大输出或建立用户欠费属于真实流量后的独立产品决策。
- [ ] 异步提交仍存在“上游已接受、用户资金已提交，但本地 Task/结算意图尚未插入”时进程崩溃的窗口。彻底关闭需要 request 级提交意图，不通过提前释放渠道商收益来规避。
- [ ] 首版提现后端固定 CNY，实际金额和有效汇率由服务端按统一舍入规则计算，不信任任意客户端币种或汇率。

验收：注入数据库失败和进程中断后，用户余额、Token 额度、渠道商收益都能通过幂等重试收敛；同一请求不会重复扣费、重复退款或重复结算。

## 批次 D：日志、审计与隐私

- [x] 短窗口同时保留全尝试成功率和可切换成功率；客户端错误、循环保护和客户端主动断开不污染渠道健康，状态码映射前的原始上游状态只用于观测归因。
- [x] 服务档位请求无论消费日志或错误日志开关如何，都至少保存一条最终请求审计记录；重试尝试仍按已有错误日志和 `hub_attempts` 记录。
- [x] 进入渠道选路后的服务档位请求只产生一条请求级最终记录，同步和异步任务路径都覆盖；中间失败保存在结构化 `hub_attempts` 中，不再逐次写数据库错误日志。选路前错误与普通 New API 分组行为不变。
- [x] 完整 `hub_attempts` 放入管理员日志详情；普通用户日志 API 会删除该字段，只保留渠道商、是否兜底、实际倍率、耗时和结果等允许字段。
- [x] 流式中断、超时、客户端断开和软错误不再被硬编码为成功；服务档位请求按有效输出区分 `success`、`partial_success` 和 `failed`。无有效输出时最终额度归零并退预扣，部分输出按可测量 Usage 结算；失败重试项固定记录用户扣费为零，管理员尝试链同时显示扣费状态和额度。普通 New API 分组保持原行为。
- [x] 任务提交请求的失败路径，包括已选中渠道后的 `LocalError`，都会记录最终失败；已经开始的渠道尝试写入 `hub_attempts`，并把非渠道错误标记为不参与健康判断。选路前失败保留空尝试链，不伪造渠道责任。
- [x] 异步任务退款、调账和结算日志沿用原始 `request_id`，任务阶段仍保留 `task_id`，可与提交请求和渠道商收益记录关联。
- [x] Midjourney 原任务续作在切回原 Channel 时复用标准渠道初始化并刷新 `RelayInfo`；实际请求、渠道密钥、倍率快照、消费日志、渠道用量和后续渠道商结算均绑定同一原始 Channel。续作按该 Channel 当前配置计价。
- [x] `image-seed` 切回原 Channel 的上下文统一暂跳过，不纳入当前版本验收范围。
- [ ] Midjourney 等旧路径补齐请求开始时间、供给归属、倍率、成功和失败尝试记录（不包含已明确跳过的 `image-seed`）。
- [x] 管理端 Channel Test 的消费日志按量和按次额度统一乘最终 `GroupRatioInfo.GroupRatio`；覆盖折扣供给、高倍率供给和免费组边界。分层计费继续使用已按倍率快照计算的 `TryTieredSettle` 结果，避免重复相乘。该日志不扣真实用户，但现在与实际计费口径一致。
- [x] TTFT 只在流式请求收到有效文本、推理或工具调用增量时记录；角色、usage、结束事件和图片元数据不会触发，日志层也拒绝为非流式请求写入 TTFT。
- [x] 新倍率策略的普通用户日志展示最终供给倍率、计费倍率和首选/平台兜底来源；Channel ID 和完整 `hub_attempts` 仍只对管理员开放。

验收：普通用户接口不暴露内部 Channel 或上游请求 ID；任意成功、失败、重试、流式中断和异步任务都可按同一 `request_id` 还原完整链路。
