# 服务档位路由人工验收计划

## 目标

用一组可重复的本地数据验收“渠道商优先 -> 同档重试 -> 平台同档兜底 -> 最终渠道计费与收益 -> 失败退款 -> 日志和健康观测”完整链路。首轮只验证已实现的静态路由，不把动态健康调权、并发容量和自动熔断混入结果。

## 最小测试数据

优先复用现有渠道商和 Channel；只有角色不足时才新建。建议准备 **3 家渠道商、6 条供给 Channel、2 枚服务档位 Token、1 个共同文本模型**。

### 渠道商和 Channel

| 角色 | 建议名称 | Channel 数 | 用途 |
| --- | --- | ---: | --- |
| A：入口渠道商 | `llm-routers` | 2 | 验证子域优先、同渠道商重试和入口失败 |
| B：同档公共池 | `x-llm` | 2 | 验证平台同档兜底和最终收益归属 |
| C：边界对照 | 任一测试渠道商 | 2 | 验证渠道商停用、档位隔离和公共池排除 |

六条 Channel 中，至少四条能提供同一个已定价文本模型 `M`：

- `A-good`：正常上游，目标档位已上架。
- `A-fail`：可控失败上游，优先级高于 `A-good`，只在重试场景启用。
- `B-good`：正常上游，与 A 属于同一目标档位。
- `B-special`：正常上游，只用于另一个价格档位。
- `C-good`：正常上游，用于渠道商停用和公共池对照。
- `C-boundary`：倍率位于待验证档位边界附近，用于检查 Ability 资格。

`A-fail` 不需要永久保存错误密钥。可以临时填入不可达 Base URL，测试结束后恢复或保持手动禁用。不要用监控探测制造手工禁用状态。

### Token 和配置

- `accept-high`：选择“高品质”服务档位。
- `accept-special`：选择“特价”服务档位。
- 两枚 Token 的密钥字符串保持普通格式，服务档位只保存在 Token 属性中，并可在列表中切换。
- 测试模型 `M` 必须已有平台模型价格。
- 四个服务档位的 `GroupRatio` 均为 `1`。
- 系统 `RetryTimes` 建议设为 `2`，即一次客户端请求最多尝试 3 次上游；测试完成后恢复原值。
- A、B、C 的供给倍率分别设置成容易区分的有效值，并确保 A、B 同时满足目标档位。具体数值以当前模型族的管理员档位边界为准。

## 测试前快照

开始前记录以下值，后续账务都按差额验证：

- 消费用户余额和两枚 Token 的已用额度。
- A、B、C 三家渠道商的可提现收益和累计收益。
- 六条 Channel 的启用状态、手动/自动禁用原因、优先级和权重。
- 测试模型的四档边界、各 Channel 供给倍率和 Ability。
- 每次请求的北京时间、Token 名称、Host、HTTP 状态和 `request_id`。无法直接看到 `request_id` 时，至少记录到秒的请求时间并严格按下面顺序执行。

## 主流程

### 1. 档位资格

1. 打开 `/system-settings/models/service-tiers-routing`，确认模型 `M` 所属模型族的四档边界。
2. 在渠道健康与路由页面检查六条 Channel 的服务档位资格。
3. 调整 `C-boundary` 到边界值和边界外各保存一次。

预期：边界内生成对应档位 Ability，边界外退出该档；高品质还必须满足管理员审批。倍率不会把 Token 的 `GroupRatio` 改成其他数值。

### 2. 入口渠道商优先

1. 启用 `A-good`、`B-good` 和 `C-good`，禁用 `A-fail`。
2. 使用 `accept-high` 调用 `http://llm-routers.localhost:3100/v1` 的模型 `M`。

预期：请求成功并命中 A；日志记录入口渠道商 A、最终渠道商 A、`provider_primary` 路由阶段；用户只扣一次，收益只记给 A。

### 3. 同渠道商重试

1. 启用 `A-fail`，确保它比 `A-good` 更先被选中。
2. 再从 A 子域请求模型 `M`。

预期：`A-fail` 失败后命中 `A-good`；同一 `request_id` 只有一条最终请求日志，`hub_attempts` 至少包含一条失败和一条成功；失败尝试 `charged_quota=0`，最终只扣一次并只给 A 结算一次。

### 4. 平台同档兜底

1. 保持 `A-fail` 可被选择，手动禁用 `A-good`。
2. 保持 `B-good` 可用，使用 `accept-high` 从 A 子域请求模型 `M`。

预期：入口 A 尝试失败后进入平台公共池并命中 B；公共池不再次选择 A 的任何 Channel；账单按 B 的实际供给倍率结算，收益只归 B，与入口 A 无关。

### 5. 不跨服务档位

1. 手动禁用目标档位内 A、B、C 的全部可用 Channel。
2. 保持 `B-special` 可用且模型 `M` 已上架。
3. 使用 `accept-high` 请求模型 `M`。

预期：返回 HTTP `503`，`error.code=service_tier_unavailable` 并带 `request_id`；不能跳到特价或其他档位；用户和 Token 最终扣费为零，预扣退回，A、B、C 都不产生收益。

### 6. 特价档恢复

1. 使用 `accept-special` 请求模型 `M`，先保持 `B-special` 禁用，再启用后重复请求。

预期：禁用时返回统一 `503 service_tier_unavailable`；启用后成功且只命中特价档候选，不会因重试跳到高品质渠道。Token 无需重建，密钥字符串也不变化。

### 7. 渠道商整体停用

1. 启用 A 的正常 Channel，但在渠道商管理中停用 A。
2. 分别从根域名和 A 子域请求模型 `M`。

预期：根域请求不能命中 A；A 子域请求返回渠道商停用错误，不把已停用渠道商的 Channel 通过 Affinity 或缓存选回。重新启用 A 后，仅原本已上架且当前可用的模型恢复候选。

### 8. 手动禁用保护

1. 手动禁用 `A-good`，记录状态和时间。
2. 对它执行模型测试、上游模型获取和一轮监控探测。

预期：Channel 始终保持 `manually_disabled`；只有系统自动禁用的 Channel 才能在健康探测后自动恢复。

## Codex 补充验证

用户完成主流程后，由 Codex 根据时间或 `request_id` 检查：

- 请求级最终日志是否唯一，`hub_attempts` 顺序、Channel、渠道商、路由阶段和失败分类是否完整。
- 用户余额、Token 额度、最终实际倍率、平台服务费和渠道商收益是否守恒，失败尝试是否保持零扣费、零收益。
- 全部失败时预扣是否完整退回，是否存在重复扣费、重复收益或孤立 pending 结算。
- `/system-settings/models/channel-health-routing` 中真实请求和探测样本是否分开，5 分钟/1 小时数据及 P50/P95 是否与本轮请求方向一致。
- 普通用户日志接口是否隐藏内部 Channel ID、上游请求 ID 和完整尝试链；管理员是否能查看。
- 中文和英文界面的服务档位、结果状态、失败分类和扣费字段是否均已国际化。

以下故障由 Codex 使用自动化用例或可控脚本补验，不要求用户手工搭建：

- 上游无有效输出即断开：`failed`，扣费和收益均为零。
- 已输出有效内容后异常断开：`partial_success`，按可测量用量扣费并只给当前渠道商结算。
- 客户端主动断开：已输出部分按实际用量结算，但不计为渠道健康失败。
- Affinity 按模型隔离，硬故障后清除并进入同档兜底。
- 平台与渠道商上游互相回流时，由 hop 和请求指纹在固定范围终止，不重试、不扣费、不结算，也不自动禁用 Channel。

## 执行约束

- 按场景顺序执行，每个场景只改变文中指定状态；不要同时修改倍率、优先级、Token 档位和渠道商状态。
- 每个场景只发一个主请求；需要确认恢复时再发一个，避免日志难以对应。
- 测试使用少量输出并限制最大 Token，降低真实上游成本。
- 手工禁用和渠道商停用必须在场景结束后恢复；`A-fail` 最终保持禁用。
- 测试完成后不要删除日志或账本数据，待 Codex 完成最终核验后再清理测试实体。
