# 倍率路由人工验收计划

## 目标

验收新 API Key 的完整链路：模型族倍率约束、渠道商优先、平台同倍率兜底、最终渠道计费与收益、Affinity、日志和失败退款。新 Key 不再选择旧四档；“特价 / 经济 / 标准 / 高品质”只根据所选最高倍率显示，不参与计算。

本轮只验证静态路由。动态健康降权、并发容量和自动熔断仍是观察功能，不作为通过条件。

## 最小数据

准备 3 家渠道商、6 条供给 Channel、3 枚新 Key 和一个各渠道都支持的已定价文本模型 `M`。

| 角色 | Channel | 倍率 | 用途 |
| --- | --- | ---: | --- |
| A：入口渠道商 | `A-primary` | `0.500x` | 子域首选 |
| A：入口渠道商 | `A-retry` | `0.500x` | 同渠道商重试 |
| B：平台兜底 | `B-fallback` | `0.500x` | 同倍率平台兜底 |
| B：越界对照 | `B-expensive` | `0.800x` | 验证不越界 |
| C：低价对照 | `C-cheap` | `0.200x` | 验证不越界 |
| C：高价供给 | `C-premium` | `5.500x` | 验证倍率大于 `1x` |

所有供给都要完成首次检测并上架。需要可控失败时，临时把 `A-primary` 指向不可达地址或错误 Key；测试结束后手动禁用，不要通过监控改变手工禁用状态。

创建以下 Key：

- `root-range`：根域创建，OpenAI 范围 `0.450-0.550x`。
- `provider-exact`：从 A 子域创建，OpenAI 精确倍率 `0.500x`。
- `root-premium`：根域创建，OpenAI 范围 `5.000-6.000x`。

Key 字符串保持普通格式。策略只保存在 `hub_routing_policy`，内部兼容字段 `group=default` 不参与新 Key 的选路或计费。

## 测试前快照

记录以下基线：

- 用户余额、3 枚 Key 的已用额度。
- A、B、C 的累计收益和结算中金额。
- 各 Provider 的平台服务费配置。
- 6 条 Channel 的状态、优先级、权重、倍率和已发布模型。
- 每次请求的时间、Host、Key、HTTP 状态和 `request_id`。

建议将 `RetryTimes` 临时设为 `2`，测试完成后恢复。

## 主流程

### 1. 根域范围路由

使用 `root-range` 从根域请求 `M`。

预期：只能命中 `0.450-0.550x` 内的供给；`C-cheap`、`B-expensive` 和 `C-premium` 均不能被选中。用户日志显示实际供给倍率和计费倍率。

### 2. 渠道商子域优先

启用 `A-primary`、`B-fallback`，使用 `provider-exact` 从 A 子域请求 `M`。

预期：优先命中 A，`routing_phase=preferred`；用户只扣一次，收益只归最终成功的 A，平台服务费使用 A 的覆盖配置或全局默认值。

### 3. 同渠道商重试

让 `A-primary` 可控失败，保持 `A-retry` 可用并使用相同 `0.500x`。

预期：先失败再命中 `A-retry`；同一请求只有一条最终消费日志，管理员 `hub_attempts` 至少有一次失败和一次成功；失败尝试不扣用户、不产生渠道商收益。

### 4. 平台同倍率兜底

让 A 的两条 Channel 均不可用，保持 `B-fallback` 可用。

预期：命中 B，`routing_phase=platform_fallback`；不能命中 `0.200x` 或 `0.800x`。最终账单按 B 的 `0.500x` 和 B 的平台服务费结算，收益只归 B，与入口 A 无关。

### 5. 同倍率耗尽

禁用全部 `0.500x` 候选，只保留其他倍率。

预期：`provider-exact` 和 `root-range` 均返回 HTTP `503`、`error.code=service_tier_unavailable`、`Retry-After: 30` 并包含 `request_id`；用户和 Key 的最终扣费为零，所有 Provider 收益不变。恢复任一合规供给后，同一 Key 无需重建即可恢复。

再请求一个从未在 `0.500x` 配置过供给的模型。

预期：返回非重试型 HTTP `404`、`error.code=model_not_found`，不带 `Retry-After`，不进入上游、扣费或 Provider 收益链路。后续若增加合规供给，仍可继续使用原 Key。

### 6. 高倍率范围

使用 `root-premium` 请求 `M`，然后把范围改为 `0.010-1.000x` 再请求。

预期：第一次可命中 `C-premium=5.500x`，账单记录 `5.500x`；收窄后不能继续命中该供给。倍率输入允许 `0.01-100.000x`，精度为 `0.001`。

### 7. Provider 整体停用

停用 A，但保持 A 的 Channel 为启用状态。

预期：根域不能命中 A；A 子域不能通过缓存或 Affinity 继续使用 A。重新启用后，仅当前已上架且可用的供给恢复。

### 8. Affinity 复用与隔离

先让 A 失败并由 B 完成一次平台兜底，再用相同会话标识重复请求；随后换模型或换另一个 Provider 子域重复。

预期：相同 Provider、模型和会话可继续复用 B，并保持 `platform_fallback`；不会每次重新撞 A。冷却到期且 A 的当前模型/端点探测资格恢复后，允许一次请求尝试 A，成功后删除临时 B 记录并切回 A；失败仍回到 B 并按现有探测退避延后。不同模型或 Provider 不共享该 Affinity。缓存 Channel 失效时应清除缓存并重新选择。

### 9. 模型列表

分别用 `root-range`、`root-premium` 调用 `/v1/models`。

预期：只返回当前模型族且确实存在合规供给的模型。模型族匹配但没有倍率范围内候选的模型不能先显示、调用时再报 `503`。

### 10. 手工禁用保护

手工禁用一条 Channel，再执行模型测试、上游模型获取和监控探测。

预期：状态保持 `manually_disabled`。只有系统自动禁用的 Channel 才能被健康探测自动恢复。

### 11. Realtime

使用新策略 Key 建立 Realtime/WebSocket 会话并产生多个 usage 事件，再测试异常断开。

预期：累计 usage 最终只结算一次；无有效输出时退回预扣，已有有效输出时按可测量用量结算。连接升级后的错误不得换 Channel 重试，避免复用已经结算的 BillingSession。

### 12. 音频固定价格

配置一个按次固定价格的音频模型并分别使用 `0.500x`、`5.500x` 供给请求。

预期：账单不是 `0`，最终额度等于固定模型价格乘最终供给倍率；收益仍满足 gross 守恒。

### 13. 异步任务最终额度

创建一个预估额度与完成后实际额度不同的任务，例如提交时 `2000`、完成后 `3000`，并在任务完成期间手工触发收益恢复任务。

预期：Provider 收益只能按最终 `3000` 拆分，不得按 `2000` 提前结算；重复恢复不重复扣费或记收益。

### 14. 相同上游任务 ID

让两个不同 Channel 的测试上游都返回相同任务 ID，例如 `1`，分别属于两个用户，再让一个成功、一个失败。

预期：状态、结果、退款、最终额度和 Provider 收益按 `Channel + upstream task ID` 完全隔离。

### 15. 结算故障

在测试库分别注入收益准备失败、Token 差额写入失败、收益释放失败和退款恢复。

预期：收益准备失败不得继续扣用户；可持久化的 Token 差额由恢复任务完成；退款与待结算收益取消同时提交；已结算收益不能再被同请求退款。

### 16. 余额与 Token 下溢保护

在测试库分别构造“钱包只剩 `100`、最终需补扣 `200`”“有限额 Token 只剩 `100`、最终需补扣 `200`”和“无限额 Token 展示余额 `100`、最终补扣 `200`”。

预期：前两种不会出现负数，异步事务保持原钱包、Token 和任务额度并留下 pending；无限额 Token 的 `remain_quota` 仍为 `100`，只增加 `used_quota`。恢复任务重复执行不得重复扣费。

补充构造“同步请求预扣 `800`、实际 `1100`、钱包只剩 `200`”：最终补扣失败后用户和 Token 均保留已扣 `800`，不得触发整笔退款；消费日志的 Quota、用户/Channel 已用额度、平台费和渠道商收益之和全部以 `800` 为准。无限额或已软删除 Token 的失败退款仍只回退 `used_quota`，不得虚增无限额展示余额。

## 账务核对

每个成功请求验证：

```text
用户最终扣费 = gross quota = 平台服务费 + 最终 Provider 收益
```

- 最终成功 Channel 决定供给倍率、收益归属和 Provider 服务费。
- 前序失败 Channel 的用户扣费和 Provider 收益均为零。
- 更贵重试必须在请求前补足预留；余额不足时停止，不允许形成负余额。
- 全部失败时预扣应完整退回。
- 普通用户能看到供给倍率、计费倍率和首选/平台兜底；Channel ID、完整尝试链和上游请求 ID 仅管理员可见。

## Codex 自动验证

用户完成主流程后，由 Codex 根据 `request_id` 核对日志、余额、Key 额度、收益账本和恢复记录，并运行：

```powershell
go test -p=1 ./middleware ./model ./service ./controller ./relay ./relay/channel/openai -count=1
go test -p=1 ./... -count=1
cd web
bun run typecheck
bun run build
```

自动用例已覆盖：政策 Key 不受旧 `GroupRatio` 或用户分组覆盖影响、渠道商每个模型族只能保存一个精确倍率、路由配置加载失败不能退回旧分组创建、旧 Key 仍可按旧分组编辑、跨渠道商子域不能改绑 Key、Provider 任务不能被公共/旧 Key 续作、失败任务退款意图原子落库、视频非 `2xx` 查询保持 pending、Affinity 使用同一倍率快照。

## 已知非阻塞风险

- 收益准备失败已阻止用户结算，收益最终额度发布和退款/收益取消也已原子化；但进程在用户资金提交后、收益释放前崩溃，以及数据库完全不可写导致恢复意图无法创建，仍需要统一 outbox/账务事务才能彻底关闭。
- 任务适配器可能在本地任务与结算持久化前已经向客户端写出成功响应；内测仍应重点观察不可查询的成功任务。失败终态退款、查询接口非 `2xx` 和 Provider 续作权限已有自动化覆盖。
- SQLite 只用于本地测试；生产切换 MySQL 后必须重跑子域优先、平台兜底、倍率耗尽和账务守恒。
- 自动化目前未覆盖完整 HTTP 黑盒链路；切换 MySQL 前还要用真实 Token、Host 和两个 `httptest`/测试上游补验首败次成、实际 usage、最终扣费和收益归属。
- 实际用量超过预扣且余额不足时，平台与渠道商只按已保留预扣结算；未收取差额暂由实际供给方承担。内测仍需记录 `request_id`，核对日志 Quota、用户扣费、平台费和渠道商收益守恒。
- Midjourney 原任务续作/种子策略校验和管理端 Channel Test 日志倍率仍是待补入口，不作为本轮通用模型族倍率 Key 的通过条件。

## 执行约束

- 每个场景只改变指定状态，避免同时修改倍率、优先级和 Provider 状态。
- 每个场景只发一个主请求，需要确认恢复时再发一个。
- 限制输出 Token，降低真实上游成本。
- 测试结束恢复 Provider 和手工禁用状态，但保留日志与账本供最终核验。
