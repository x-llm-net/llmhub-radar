# 渠道排名与 Affinity 恢复切换方案

## 1. 文档状态

本文记录“渠道排名”和“渠道商进入平台兜底后自动切回原渠道”的拆分方案。F1 已确认，F2/F3 第一版已实现；F4-F6 尚未实现。

当前结论：

- 渠道排名和实际路由权重分开定义。
- 排名只面向管理员，不在公开首页展示。
- 排名行以 `Channel + Model + EndpointType` 为单位；渠道商是筛选、归属和聚合维度，不代替具体 Channel 排名。
- 平台超级管理员查看全平台；未来域名级总代理管理员只能查看本域名租户下的渠道和排名。
- F3 第一版保留现有“先按渠道商归一化、再选 Channel”，避免拆分 Channel 获得额外流量；质量带在渠道商分组和 Channel priority 之前执行。
- 供给倍率只做候选资格过滤，不直接进入质量分。
- Affinity 是保护缓存和会话收益的软粘性，不是永久绑定。
- 原渠道亲和与平台兜底亲和不能写入同一个单值状态，否则原渠道恢复后无法稳定切回。

## 2. 产品目标

1. 管理员可以看到渠道商、Channel、模型和端点的真实表现。
2. 用户请求优先使用入口渠道商；入口渠道商不可用时，平台在相同策略边界内兜底。
3. 原渠道短暂故障时不反复撞击，也不因为一次失败造成长期切换。
4. 原渠道恢复后可以自动切回，同时不能影响计费、收益、循环保护和手工禁用语义。

## 3. 明确不做

- 不按价格高低直接排名，不用倍率代替质量评分。
- 不允许仅靠重复创建 Channel 或账号获得不受限制的平台流量。
- 不把一个模型或端点的故障扩大为整个渠道商故障。
- 不自动重新启用管理员手工禁用的渠道或渠道商。
- 不先引入机器学习、复杂公平算法、独立订阅关系或新的价格体系。

## 4. 排名模型

### 4.1 候选硬过滤

排名前先排除以下候选：

- 渠道商或 Channel 未启用、未上架、审核不通过或手工禁用。
- 当前模型、请求端点、服务档位或倍率范围不匹配。
- 自动健康状态处于不可用、冷却或半开限制之外。
- 当前请求已经失败过的 Channel。
- 会造成循环依赖的入口渠道商或受循环保护限制的候选。

硬过滤之后才使用 priority、健康分和 weight。

### 4.2 F1 展示层级

```text
超级管理员
  -> 查看全平台 Channel 排名
  -> 可按渠道商、模型、端点、倍率范围和状态筛选

域名级管理员（后续专题）
  -> 只查看当前域名租户下的 Channel 排名
  -> 不能进入 New API 平台级管理后台
```

每一行代表一个实际参与候选判断的 `Channel + Model + EndpointType`。同一 Channel 支持多个模型或端点时会出现多行，因为它们的成功率、延迟和健康状态可能不同。页面可以按渠道商折叠或聚合查看，但默认排序和筛选对象仍是具体 Channel。

F3 第一版已确定平台公共池保持以下结构：

```text
同一 Model + EndpointType + 倍率策略的合格 Channel 进入质量比较
  -> 全局质量带先排除明显不稳定或明显更慢的 Channel
  -> 按渠道商归一化选择，Channel 数量不增加渠道商级概率
  -> 渠道商内部按 priority 和有效 weight 选择 Channel
```

仅限制“每个账号最多 5 条免费供给 Channel”不能完全解决治理问题，多个账号仍可绕过额度；但第一版的渠道商归一化已经防止同一渠道商仅靠拆分 Channel 增加流量。同上游域名跨渠道商重复属于认证和治理专题，不在路由热路径合并来源。

### 4.3 F2/F3 第一版质量带和有效权重

第一版不再引入新的容量分、固定流量上下限或探索比例，直接复用现有真实请求分钟健康、15 分钟 TTFT 和探测信号。筛选顺序为：

```text
请求硬资格过滤
  -> 真实成功率质量带
  -> 真实 TTFT P95 质量带
  -> 按渠道商归一化选择
  -> 渠道商内部按 priority
  -> 同 priority 内按现有 effective_weight
```

达到 20 个真实请求样本后，成功率进入比较；达到 20 个真实首字样本后，TTFT P95 进入比较。边界为：

```text
success_rate >= best_success_rate - 1 个百分点
TTFT_P95 <= max(best_TTFT_P95 × 1.20, best_TTFT_P95 + 300ms)
```

- 最优成熟候选成功率达到现有健康线 95% 时，样本不足的 Channel 不进入正常质量带，只在成熟候选被本次失败排除后作为兜底；如果所有成熟候选都低于 95%，则保留冷渠道参与现有探测/有效权重选择，避免已知失败渠道压制未知候选。
- 如果当前候选都没有成熟真实样本，则不做质量带淘汰，继续使用现有探测健康和有效权重。
- 图片等没有 TTFT 的请求只应用成功率质量带，延迟继续使用现有有效权重。
- 每次重试排除已失败 Channel 后都会重新计算质量带，因此较慢 Channel 不会被永久删除，只会在更优候选耗尽后进入兜底。
- 倍率、服务档位、模型和端点只决定候选资格，不进入质量分；计费、收益和 Affinity 不因本次排序改变。
- 当前短窗口统计键仍为 `Channel + 归一化模型 + text/image`。管理员按具体 EndpointType 展示行，但同一 Channel/模型下的 Chat 与 Responses 暂时共享 `text` 实时统计；拆分存储属于后续迁移。

### 4.4 管理员排名展示

管理员实时排行展示原始维度和跳过原因，至少包含：

- 渠道商、Channel、模型、端点和倍率资格。
- 手动/自动状态、健康状态、冷却时间。
- 成功率、延迟、样本来源、样本量、TTFT P50/P95。
- priority、基础 weight、有效 weight、实际流量和兜底命中率。

管理员接口会先为完整筛选结果补齐能力、探测样本和实时信号，再全局排序、编号并分页。默认顺序先看可路由、硬可用和真实健康状态，再在同一健康组内看成熟真实 TTFT P95、真实成功率和既有长期排名分；最后使用渠道商、Channel、模型和端点稳定排序。“暂无样本”、手工禁用和当前不可用仍保留在超级管理员视图中。现有七日 `RankingScoreBps` 继续作为长期探测指标展示，不与短窗口实时路由因子合并。

本专题不在公开首页展示渠道排名。未来总代理是否向其终端用户公开某些聚合数据，属于独立域名专题，不复用管理员原始排名页面。

### 4.5 管理权限兼容边界

- 超级管理员拥有平台级模型、New API 系统配置、全平台渠道和全平台排名权限。
- 域名级管理员只管理本租户的渠道商、品牌和运营数据，只能查看本租户范围内的 F1 排名。
- 域名级管理员不能修改模型全局配置、平台路由参数、其他租户数据或进入 New API 平台级管理后台。
- 当前 F1 查询接口未来必须能增加租户范围过滤；在域名租户功能实现前只开放给超级管理员，不能先开放一个依赖前端隐藏的越权入口。
- 总代理分成不进入排名分，也不改变 Channel 健康数据；多方分账另见 `domain-reseller-plan.md`。

## 5. Affinity 与平台兜底

### 5.1 当前风险

现有 Affinity 记录的是选中的 Channel。原渠道失败后，如果平台兜底成功并把兜底 Channel 写回同一 Affinity，后续请求可能持续粘在兜底渠道，原渠道恢复后只能等缓存过期或再次失败才能回来。

因此必须区分：

```text
preferred：用户原本优先使用的渠道商/Channel
fallback：当前临时承接请求的平台渠道商/Channel
```

### 5.2 推荐的最小恢复流程

1. 原渠道正常：使用 `preferred`，成功后延长正常 Affinity TTL。
2. 原渠道发生硬故障：当前请求排除失败 Channel；同渠道商还有可用 Channel 时先在渠道商内部切换，否则进入平台公共池。
3. 进入平台兜底：保留 `preferred` 信息，记录 `fallback` 和一个恢复冷却时间，不覆盖原优先关系。
4. 冷却期间：优先使用 `fallback`，不在每个请求上重新撞击故障渠道。
5. 冷却结束且健康状态显示原渠道/渠道商对当前模型和端点恢复可用：允许一次恢复尝试。
6. 恢复成功：清理临时 `fallback`，重新激活 `preferred`。
7. 恢复失败：继续使用 `fallback`，延长下一次恢复时间；当前请求仍可按既有预算继续兜底。

恢复判断必须按以下范围隔离：

```text
身份指纹 + 渠道商 + 模型 + EndpointType + 服务档位/倍率策略
```

如果渠道商只是 GPT 不可用而 Claude 正常，不能把整个渠道商标记为不可恢复。若原来的具体 Channel 已经失效，但同渠道商有其他合格 Channel，恢复时重新按该渠道商的 priority + weight 选择，不强行回到旧 Channel。

### 5.3 状态和时间建议

首版不新增复杂状态机，只保留有限状态：

```text
preferred_active
fallback_cooling
recovery_probe
preferred_recovered
```

恢复冷却应复用现有健康/探测结果，不另造一套检测体系。恢复尝试可以由一次受控用户请求完成；失败后仍走兜底，不能把恢复检查变成用户可见错误。具体冷却时长、连续成功条件和退避上限列为下一步单独确认项。

### 5.4 不变量

- Affinity 轻微变慢不立即切换，继续保护上游缓存。
- 连接失败、明确不支持、熔断或渠道商禁用时才进入恢复/兜底流程。
- 手工禁用永远不能被恢复逻辑覆盖。
- 失败尝试不扣费、不产生收益；最终成功只扣一次、结算一次。
- 入口渠道商排除和 hop/指纹循环保护优先于恢复切回。

## 6. 拆分步骤

### F1：确定排名展示范围（已确认）

- 排名仅面向管理员，不在公开首页展示。
- 排名单位为 `Channel + Model + EndpointType`，可按渠道商聚合和筛选。
- 超级管理员看全平台；未来域名级管理员只看本租户。
- 展示综合健康分及组成项、样本量和状态，不只展示一个名次。
- F1 先做只读展示，不改变实时路由。

### F2：确定排名计算口径（第一版已实现）

管理员页面已改为完整结果全局计算、排序后分页；第一版复用真实成功率、真实 TTFT、探测和既有长期排名，不新增容量分。

### F3：接入有效权重（第一版已实现）

质量带已在渠道商分组和 priority 之前接入；现有渠道商归一化、providerFilter、失败 Channel 排除、priority、weight 和有效权重保持不变。未引入 Channel 全局平铺、容量调度、固定公平份额、探索流量或同源域名合并。

### F4：拆分 preferred/fallback Affinity

保留现有 Affinity 兼容逻辑，增加恢复记录或独立缓存，不让平台兜底渠道覆盖原渠道优先关系。

### F5：实现恢复切回

按模型、端点、渠道商范围判断恢复；冷却结束后进行一次受控恢复尝试，成功切回，失败退避并继续兜底。

### F6：联调和验收

覆盖单渠道故障、渠道商部分模型故障、整家渠道商故障、恢复、手工禁用、多个用户、循环链路和账务幂等。
