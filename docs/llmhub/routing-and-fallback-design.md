# 用户令牌路由与平台兜底算法

状态：方案草案，先用于逐项讨论，暂不作为代码实现规格。

## 1. 目标

用户使用一个普通 New API Token 调用模型时，平台需要同时满足以下目标：

1. 从渠道商子域名调用时，优先使用该渠道商已经上架且可用的供给渠道。
2. 渠道商供给不可用时，在同一个消费者分组内切换到平台公共池，尽量保持价格和可用性。
3. 不因为一个渠道或一个模型失败而拖垮同档的其他可用渠道。
4. 每次请求都能追踪来源渠道商、实际执行渠道、每次尝试、用户扣费和渠道商收益。
5. 保护平台不被渠道商之间的回流配置形成无限循环。

首版优先保证“选对候选、及时切换、账务可解释”，动态评分只在有足够真实数据后逐步启用。

## 2. 已确认的产品边界

### 2.1 复用 New API 的核心实体

- `Channel` 仍是唯一的上游配置实体，包含 Base URL、密钥、模型映射、端点类型和 New API 原生参数。
- 复用 New API 的 Group 命名空间保存 Token 服务档位，但四个档位的 GroupRatio 统一为 `1`，不再把 Group 当成额外计费倍率。
- 供给资格计算到 `Channel + Model`，不能直接用 Channel 级 `Channel.Group` 表达一个渠道内不同模型的档位资格。
- `hub_supply_groups` 是 Channel 的一对一供给扩展，只保存渠道商归属、供给倍率、探测与上架状态等 Hub 字段。
- 用户、Token、余额、模型价格、基础重试和日志继续使用 New API 的现有能力。

### 2.2 服务档位

普通用户使用四个固定内部档位：

```text
special / low / medium / high
```

产品展示名称暂定为“特价 / 经济 / 标准 / 高品质”。四档不是单纯按渠道售价从低到高分桶，而是用户创建 Token 时选择的服务档位。每个档位同时定义价格上限、来源要求和质量底线：

| 档位 | 产品含义 | 首版资格 |
| --- | --- | --- |
| 特价 | 极低成本、尽力而为 | 满足模型族特价上限，通过基础连接和模型可用性检查 |
| 经济 | 价格优先 | 满足经济档价格上限和基础稳定性要求 |
| 标准 | 价格与质量均衡 | 满足标准档价格上限，由平台确认模型与来源信息 |
| 高品质 | 来源与体验优先 | 满足价格上限，并进入平台认可来源白名单 |

高售价不能自动获得高品质资格。渠道商只能配置供给倍率和申报来源，档位规则、来源等级和最终资格由平台管理员控制。来源不透明、模型套壳或逆向渠道即使主动提高倍率，也不能进入高品质档。经过认证的优质渠道即使价格较低，仍可服务高品质档。

四个 New API Group 的倍率统一配置为：

```text
special = 1
low     = 1
medium  = 1
high    = 1
```

Group 只负责 Token 档位和候选边界，不参与额外价格乘法。实际扣费继续使用最终命中渠道的供给倍率：

```text
模型基础价格 × 最终供给倍率 × 实际用量
```

每个模型族由管理员配置各档位允许的供给倍率上限。例如 OpenAI 特价档可设为 `<= 0.10`，Anthropic/Claude 特价档可设为 `<= 0.20`。阈值比较对象是渠道供给倍率，不是模型自身价格；之所以按模型族配置，是因为不同模型生态的合理市场倍率不同。档位只设置价格上限，不设置“高品质必须足够贵”的下限。

候选资格按以下规则判断：

```text
供给倍率 <= 当前模型族与档位的价格上限
且 来源等级 >= 档位要求
且 质量状态 >= 档位要求
且 当前健康
```

同一个 `Channel + Model` 可以同时符合多个档位。例如一个价格低且来源经过认证的 Claude 渠道可以同时服务特价和高品质 Token；调度时低档优先选择刚好满足要求的候选，避免优先消耗高品质供给容量。具体容量保留和质量权重后续结合真实流量设计。

为了保证“严格不跨组”，Token 必须显式选择上述一个组，不能使用 `auto`，并需要关闭 `CrossGroupRetry`。同一请求的所有重试都沿用初始组，不在失败后重新计算或提升组别。

档位资格落在 `Channel + Model` 的 Ability 层；同一个 Channel 的不同模型可以获得不同资格，但仍共享 Base URL、密钥、并发和故障域。这只能实现逻辑隔离，不能实现物理容量隔离。

模型策略采用两级管理员配置：模型族默认规则，以及少量具体模型覆盖。已识别模型族的新模型可以继承价格上限，但默认进入“待审核”；完成平台价格、端点和基础可用性确认后才进入消费者路由，且不能自动获得高品质资格。无法识别模型族或未配置平台价格的模型显示“平台暂未支持”。

自动化来源识别、开源质量基准、模型身份一致性和能力回归检测后续单独调研。第一版先使用管理员审核、来源白名单、现有连接测试和实时健康状态跑通流程。

管理员控制台后续增加独立的“服务档位与路由策略”页面，不把这些参数散落在 Channel 表单或普通系统倍率配置中。首版页面至少管理：

- 四个服务档位及其固定 GroupRatio `1`。
- 模型族价格上限、具体模型覆盖和新模型待审核队列。
- 高品质来源白名单和管理员资格确认。
- 公共池渠道商基础权重，以及后续动态权重的启停状态。
- 渠道商总并发上限、Channel 并发上限和平台覆盖值。
- 全局重试次数、渠道商优先尝试预算和平台公共池兜底开关。
- 允许切换渠道的错误类别，以及同档耗尽后的返回策略。

上述配置需要提供平台默认值和变更审计。第一版先按文档推荐默认值跑通流程，不在实现前穷举全部参数；真实调用数据产生后再调整阈值、预算和错误分类。

### 2.3 渠道商来源

渠道商身份由请求 Host 推断，而不是绑定在 Token 上：

```text
llm-routers.llm-hub.store/v1
  -> requested_provider = llm-routers
```

同一个 Token 调用根域名时没有渠道商优先级；调用某个渠道商子域名时，只影响本次请求的路由偏好，不改变 Token、余额、用户组或扣费规则。

## 3. 请求生命周期

```text
接收请求
  -> 认证 Token 与确定服务档位
  -> 解析 Host 得到 requested_provider
  -> 生成本次请求上下文
  -> 构建同档候选集
  -> 渠道商优先池
  -> 失败后切换同档平台公共池
  -> 记录每次尝试
  -> 按最终成功 Channel 扣费和结算
```

请求上下文在一次调用内固定保存以下内容：

- `request_id`
- 用户 ID、Token ID、服务档位和请求模型
- 原始 Host、解析出的 provider ID/slug
- 当前路由阶段：`provider_preferred` 或 `platform_fallback`
- 已尝试的 Channel ID 集合
- 是否已经向客户端发送响应头或正文
- 当前请求的总时间预算和剩余尝试次数

上下文不能依赖请求中途重新查询的可变配置来解释历史结果；成功或失败结束时需要把关键值快照到日志。

## 4. 候选集硬过滤

硬过滤在评分之前执行。满足以下任一条件的 Channel 不得进入候选集：

- 请求模型对应的 `Channel + Model` 没有当前服务档位资格。
- 供给倍率超过当前模型族与档位的价格上限。
- 模型仍处于待审核/暂不支持状态，或不满足当前档位的管理员来源要求。
- 没有请求模型对应的已启用 Ability，或模型没有完成上架。
- Channel、渠道商或对应供给扩展已停用。
- 端点类型与请求协议不兼容，例如把图片端点当成文本端点测试。
- 当前处于熔断冷却期。
- 已达到平台为该 Channel 设置的并发上限。
- 已经在本次请求中失败过。
- 会回到本请求的入口渠道商，且当前处于平台公共池阶段。

“没有价格配置”应在候选生成或探测前置校验阶段立即判定为不可服务，并返回可操作的错误，不应进入上游连接超时。

候选过滤必须在内存缓存和数据库查询两条路径保持一致，不能只依赖前端展示过滤。现有相关代码包括：

- `model/ability.go`
- `model/channel_satisfy.go`
- `model/channel_retry_test.go`
- `service/channel_select.go`

## 5. 渠道商优先与平台兜底

以 `llm-routers.llm-hub.store`、`medium`、`gpt-5.5` 为例：

1. 只查 `llm-routers` 且属于 `medium`、已上架、端点兼容、当前健康的候选。
2. 若存在候选，第一版按原生 priority/weight 选择一个；第二版再叠加质量因子。
3. 若候选失败，记录失败 Channel，并在同一阶段排除它，继续尝试该渠道商的其他 Channel。
4. 渠道商候选耗尽、不可用或达到本次阶段预算后，进入平台公共池。
5. 公共池仍然只查 `medium`，同时排除入口渠道商的所有 Channel 和本请求已经失败的 Channel。
6. 公共池成功后，实际服务归属是命中的公共池渠道商，而不是入口子域对应的渠道商。

公共池不是“平台自营池”的同义词。平台可以没有自营渠道，公共池就是所有符合条件且不属于入口渠道商的供给渠道集合。

现有 `RetryTimes` 继续作为一次请求的总尝试预算。例如 `RetryTimes=2` 时最多 3 次上游尝试，不额外增加重试次数。首版默认前两次用于入口渠道商、最后一次用于同档公共池；入口渠道商没有候选时立即把剩余预算交给公共池。该分配策略由管理员配置，先作为可调整默认值，不固化成长期业务规则。

如果入口渠道商没有候选，不等待探测或容量恢复，直接进入公共池。对已经开始向客户端发送流式响应的请求不能再切换上游；只有在响应尚未开始时才允许重试。

## 6. 档位内选择算法

### 6.1 第一版

子域名渠道商优先阶段已经确定入口渠道商，只需要在该渠道商内部选择 Channel。进入平台公共池后必须采用两级分流，不能把所有 Channel 平铺随机：

```text
同档合格候选
  -> 按渠道商聚合
  -> 选择一个渠道商
  -> 在该渠道商内部选择具体 Channel
```

第一版使用以下规则：

- 公共池渠道商默认基础权重相同，管理员可以调整渠道商基础权重。
- 一个渠道商拆分或新增 Channel 不会自动增加其渠道商级流量份额，避免通过堆叠 Channel 获得不公平流量。
- 价格只负责是否满足当前档位上限，不直接提高公共池分流权重。
- 选中渠道商后，在其合格 Channel 内复用 New API 的 priority/weight。
- 被选渠道商已经没有可执行 Channel 时，排除该渠道商并重新选择，不消耗一次真实上游尝试。
- 不属于任何渠道商的管理员自营 Channel 统一视为一个平台渠道商参与分流，不能按 Channel 数量重复获得权重。
- 第一版不把实时成功率、TTFT 或容量自动乘入渠道商权重，只记录数据并保留第二阶段扩展点。

渠道商内部仍遵守以下规则：

- 优先级高的候选先参与选择。
- 同一优先级使用 weight 做分流。
- 本次请求已经失败的 Channel 不重复选择。
- 不把最低价格作为绝对优先条件，避免一个便宜但慢的渠道吃满流量。

这样可以先验证 Host 优先、同档兜底、重试排除和账务归属，改动小且容易回滚。

当前实现还有两个需要在第一版明确修正的例外：

- 严格排除已失败 Channel 不能只用于渠道商优先路径，根域名普通路由也不能在候选耗尽后立刻重新选择本次已经失败的 Channel。
- Codex/Claude 等亲和规则的 `SkipRetryOnFailure` 不能绕过平台兜底。亲和目标满载、熔断或连接失败后，是打破亲和继续可用，还是直接失败，需要作为产品策略明确配置。

### 6.2 第二版动态质量因子

真实流量和探测数据稳定后，再将基础权重乘以质量因子：

```text
effective_weight = base_weight
                 * health_factor
                 * latency_factor
                 * capacity_factor
                 * confidence_factor
                 * fairness_factor
```

这里的因子先作为实现概念，不在第一版写死复杂公式。任何因子都不能突破硬过滤，也不能让一个组的渠道被调度到另一个组。

建议数据时间窗口：

- 路由实时判断主要看最近 5 到 15 分钟。
- 7 天稳定性用于公开排名和长期观察，不直接决定一次请求的即时选择。
- 新渠道没有数据时使用保守的中性因子，不因“无数据”直接判死。

供给倍率先作为服务档位价格上限的硬过滤条件，再作为同档候选中的有限偏好，不能让最低价渠道获得 100% 流量。渠道商自己设置倍率不能改变平台审核的来源与质量资格，也不能通过涨价进入高品质档。

## 7. 并发、首字时间与熔断

### 7.1 并发

并发采用两层控制：

```text
渠道商总并发上限
  -> Channel 并发上限
```

渠道商总上限用于防止通过拆分或新增 Channel 绕过容量控制，Channel 上限用于保护具体 Base URL、密钥或上游账号。渠道商可以申报每个 Channel 的并发能力，管理员可以设置平台上限或覆盖申报值；未配置时使用平台安全默认值，`0` 不解释为无限。

候选选择时至少记录：

- 当前 inflight 数
- 渠道商当前 inflight 和总上限
- Channel 当前 inflight 和有效上限
- 剩余容量比例
- 最近因容量不足被跳过的次数

达到任一层上限时暂时跳过，不把它当成永久故障，也不消耗一次真实上游重试。入口渠道商全部满载时立即进入同档公共池；公共池全部满载时返回 HTTP `503` 和建议重试时间。渠道申报更高并发只扩大其可承接上限，不自动增加渠道商基础权重。

多实例部署时，渠道商和 Channel inflight 计数及容量租约需要使用 Redis 原子操作并设置短 TTL，避免进程退出后永久占用容量。Redis 不可用时首版采用 fail-open，同时启用单实例本地安全上限，优先避免 Redis 故障拖垮所有推理请求。

首版不为高品质档设置硬性容量预留，先通过“低档优先选择刚好满足要求的渠道”减少抢占。第二阶段再根据真实流量决定是否需要档位保留容量。

### 7.2 TTFT

文本流式请求记录 `first_token_ms`，同时保留完整响应 `latency_ms`。图片、Embedding、Rerank 等不适合首字指标的端点不能强行使用 TTFT，应使用完整响应时间和成功率。

实时路由建议关注：

- 首字 P50：反映典型体验。
- 首字 P95：发现排队和长尾劣化。
- 错误率与超时率：确认慢是否已经影响成功率。
- 样本量：避免一条慢请求就大幅降权。

处理顺序建议为“降权、观察、熔断”：

1. TTFT 或错误率连续窗口劣化时先降低质量因子，不立即下线。
2. 劣化持续且超过熔断阈值时进入冷却期。
3. 冷却期结束后用少量探测或请求半开恢复。
4. 恢复成功则逐步增加权重，连续失败则延长冷却。

具体阈值需结合真实日志确认；第一版不把单个 P95 数值直接写成永久业务规则。

短期熔断状态不能复用 Channel 的 `auto_disabled`。后者会改变 Ability 和后台恢复流程，容易把实时调度状态与业务上架状态耦合。`429` 应按过载信号处理，优先遵守上游 `Retry-After` 并短暂降低可用容量，而不是立即永久停用渠道。

Agent 审查给出的首轮校准值可作为压测起点，而不是产品承诺：容量使用率达到 70% 后开始降权，90% 后显著降权；最近 5 分钟至少 20 个样本后再按错误率或 TTFT P95 降权；熔断初始冷却约 30 秒，再指数增加到 5 分钟。最终阈值必须用真实模型、渠道和端点数据校准。

### 7.3 健康状态粒度

实时健康采用两层状态，避免一个模型故障导致整个渠道商退出：

```text
Channel 健康
  -> DNS、连接、TLS、鉴权、账号余额等基础设施状态

Channel + Model 健康
  -> 模型存在性、模型级限流、TTFT 和响应状态
```

基础设施故障可以影响 Channel 的全部模型，单个模型持续失败只影响该 `Channel + Model`。实时状态采用简单的四态模型：

```text
healthy -> degraded -> open -> half_open -> healthy
```

第一版只实现跑通闭环所需的最小规则：

- 单次请求失败后，本请求不再选择该 Channel。
- 连续连接失败或上游 `5xx` 可以临时熔断 Channel。
- 单个模型持续失败只临时熔断对应 `Channel + Model`。
- `429` 优先遵守 `Retry-After`，临时暂停或降低有效并发。
- TTFT 先完整记录，不在第一版自动修改动态权重。
- 短期健康状态独立保存，不修改 Channel 的业务启用、模型上架或 Ability 状态。
- 系统探测或半开请求负责恢复候选，避免降权后永远没有流量证明已经恢复。

第二阶段再使用最近 5 到 15 分钟成功率、TTFT P50/P95 和容量计算动态权重。7 天稳定性继续用于公开展示和长期判断，不直接控制实时请求。

## 8. 失败分类与重试

重试判断应区分“当前 Channel 失败”和“本次请求不可继续”：

| 类别 | 示例 | 是否换 Channel |
| --- | --- | --- |
| 可切换上游故障 | 连接失败、超时、上游 5xx、容量拒绝 | 是，排除当前 Channel |
| 当前配置问题 | 鉴权失败、模型不存在、端点不兼容、缺价格 | 通常不重试同 Channel；可切换其他已知候选 |
| 客户端或请求问题 | 参数错误、权限不足、请求体不合法 | 否，直接返回 |
| 循环保护 | 平台生成的 `request_loop_detected` | 否，不得进入普通重试 |
| 已开始响应 | 已发送流式响应头或正文后上游中断 | 否，避免重复输出 |

同一请求的尝试链必须保存实际顺序、Channel、结果类别、状态码、开始时间、耗时和是否发生计费。不能因为重试成功而丢弃前面失败的尝试。

多密钥 Channel 还需要决定失败隔离粒度。连接级或整个 Channel 的配置错误可以按 Channel 排除；单个 Key 的限额、鉴权或上游分流错误如果能够可靠识别，可只排除 `Channel + Key`。在这个规则明确前，不能假设排除 Channel 后仍会尝试它的其他 Key。

## 9. 循环依赖保护

渠道商可能把 LLM-Hub 配置为上游兜底，平台也可能在入口渠道商失败后再次选中该渠道商。必须同时使用两层保护：

1. **候选隔离**：进入平台公共池后排除入口渠道商的全部 Channel；本次已失败 Channel 在剩余尝试中排除。
2. **请求指纹**：在认证后、Channel 分配前记录规范化请求指纹，同一指纹超过并发阈值时返回 HTTP 508 `request_loop_detected`。

请求指纹不是绝对的递归证明。multipart、协议转换、外部网关改写请求体以及不同认证参数都可能改变指纹，因此：

- 认证参数不能参与指纹。
- 平台自己生成的 `request_loop_detected` 不得再次进入常规重试、扣费或结算。
- 生产多实例必须共享 Redis，并监控 Redis 降级到进程内保护的次数。
- 指纹阈值、租约和总请求超时必须一起配置，不能只增加重试次数。

现有保护实现和边界记录在 `middleware/request_fingerprint.go` 及 `docs/llmhub/README.md`。

## 10. 扣费、收益与审计

### 10.1 归属字段

同一条请求至少区分以下概念：

- `origin_provider_id`：Host 指定的入口渠道商，只用于路由偏好和审计。
- `served_provider_id`：最终成功提供服务的渠道商，用于收益归属。
- `served_channel_id`：实际执行的 New API Channel。
- `routing_phase`：渠道商优先或平台兜底。
- `fallback_reason`：无候选、连接失败、超时、容量不足或熔断等。

入口渠道商的请求如果最终使用平台公共池，收益只结算给 `served_provider_id`，入口渠道商不因“拥有子域名”获得这笔收益。

### 10.2 用户扣费

沿用现有 New API 用户扣费路径。扣费快照至少包括：

```text
model_price
service_tier
platform_group_ratio = 1
supply_multiplier
platform_fee_ratio
actual_usage
charged_quota
```

服务档位、供给倍率、平台组倍率和模型价格必须以本次请求实际生效的值入账，不能事后按当前配置反算。同一档位内允许不同请求命中不同供给倍率，用户通过使用日志查看实际结果。

### 10.3 渠道商收益

请求成功并完成用户扣费后，按现有结算约定拆分平台服务费与实际服务渠道商收益。收益账本使用 `request_id` 做幂等键，重试失败记录挂在同一个请求下；同一笔请求不能因多次重试成功而重复结算。

一次请求经过多个失败 Channel 后由最终 Channel 成功时，用户只按最终成功 Channel 的实际倍率和实际用量扣费一次，收益也只结算给最终成功 Channel 所属渠道商。入口渠道商和中间失败渠道商都不因参与尝试获得自动收益。

探测和测试连接不产生渠道商收益。

### 10.4 上游失败但可能已扣费

上游连接失败不等价于上游没有扣费。首版不自动给失败渠道商记收益，也不自动二次扣用户，避免把不确定状态扩大成确定账务。应保存：

```text
upstream_charge_status = not_charged / charged / unknown
```

失败尝试产生的上游成本默认由对应供给渠道商承担，因为用户没有得到该次服务。只有能够确认异常消耗由平台自身故障、错误重试或错误路由造成时，管理员才从平台侧人工补偿；不自动追扣用户。所有渠道都失败时用户不扣费，已经预扣的额度必须通过幂等流程退回。

当日志、上游账单或管理员确认上游确实扣费后，可以关联 `request_id + attempt_index` 进行人工核对和平台责任调账。这个策略牺牲一部分自动化，换取不会因重复重试造成重复扣费或重复收益。

## 11. 数据链路和日志

首版不新增复杂调度数据库。优先复用已有请求日志、`use_channel`、计费和 Hub 结算扩展：

### 请求级

- request ID、用户、Token、模型、服务档位、入口 Host/provider
- 最终状态、客户端响应是否开始、总耗时
- 路由阶段、兜底原因、最终 Channel/provider
- 档位价格上限、平台组倍率、供应倍率、模型价格和扣费额度快照

### 尝试级

- attempt index、Channel ID、provider ID
- 候选阶段、开始/结束时间、连接耗时、TTFT、总耗时
- 状态码、错误类别、是否排除、是否可能产生上游费用

第一版确定不新增尝试明细表，在最终请求日志的结构化字段中保存完整 `hub_attempts` 数组。成功和全失败请求都必须写一条请求日志，不受全局 `ERROR_LOG_ENABLED` 开关影响；逗号分隔的 `use_channel` 只用于兼容，不能作为唯一审计来源。

```text
hub_attempts[]
  -> attempt_index
  -> routing_phase
  -> provider_id / channel_id
  -> result / error_category / status_code
  -> started_at / latency_ms / first_token_ms
  -> upstream_request_id
  -> upstream_charge_status
```

用户端只展示渠道商、渠道商优先/平台兜底、实际倍率、耗时和结果；管理员可以查看 Channel、内部错误、上游请求 ID 和扣费风险。人工调账通过 `request_id + attempt_index` 定位失败尝试，收益账本仍以 `request_id` 为权威幂等依据，日志 JSON 不承担余额记账。

动态健康统计使用请求期内指标和 Redis/内存聚合，不扫描日志 JSON。第一版接受“进程在最终日志写入前异常退出可能丢失本次尝试详情”的限制；真实流量证明需要逐尝试持久化、批量查询或申诉举证后，再迁移到最小尝试表。

## 12. 监控与验收指标

第一版上线前需要能回答以下问题：

- 某次请求从哪个 Host 进入，是否先尝试了入口渠道商？
- 为什么跳过某个 Channel，是价格缺失、未上架、容量满、熔断还是之前已失败？
- 最终实际服务的是哪个 Channel 和渠道商？
- 用户选择了哪个服务档位，实际供给倍率和扣费是多少，收益记给谁？
- 失败是否可能已经产生上游费用？有没有重复结算？
- 是否出现平台与渠道商之间的回流，是否被 508 指纹保护终止？

建议最少提供这些指标：

- 各组/模型请求成功率、重试率、兜底率
- 渠道商优先成功率
- Channel 级连接失败、5xx、超时和容量拒绝率
- TTFT P50/P95、完整响应 P50/P95
- inflight、容量跳过和熔断次数
- 请求指纹拦截次数、Redis 降级次数
- 结算成功、待确认、人工调账和幂等冲突次数

## 13. 第一版实施边界

建议拆成三个可独立验收的小步：

### 第一步：固定候选边界和可追踪性

- Host 解析入口渠道商。
- Token 明确选择服务档位，四个平台 GroupRatio 固定为 `1`。
- 管理员通过独立的“服务档位与路由策略”页面配置模型族价格上限、新模型待审核状态、高品质来源白名单，以及首版重试与兜底默认值。
- 按 `Channel + Model` 计算档位资格，并完成上架/Ability 校验。
- 渠道商优先、公共池兜底，公共池排除入口渠道商。
- 公共池先按渠道商基础权重分流，再在渠道商内部按 Channel priority/weight 选择；拆分 Channel 不增加渠道商级份额。
- 每次尝试和最终归属写入请求日志的结构化 `hub_attempts`，成功和全失败请求都不受错误日志开关影响。
- 使用现有 priority/weight，不启用复杂动态评分。
- 禁用 Token `auto` 与跨组重试，检查亲和规则不会阻断失败切换。
- 根域名和子域名路径都严格排除本次已经失败的 Channel。

验收重点：不同模型族按各自倍率上限生成正确候选；渠道商正常时优先命中；其渠道失败后能在同档公共池成功；不会重复命中已失败 Channel；日志能展示入口渠道商、平台兜底、实际倍率和扣费。

### 第二步：接入实时质量和容量

- 统计近 5 到 15 分钟错误率、TTFT 和容量。
- 在现有 weight 外增加有限质量因子。
- 实现“降权 -> 冷却 -> 半开恢复”。
- 增加渠道商总并发上限、Channel 并发上限和平台保护上限。
- 分离 Channel 基础设施健康和 `Channel + Model` 模型健康，避免单模型故障扩大下线范围。

验收重点：慢渠道不会长期吃满流量；短暂抖动不会立即永久下线；容量恢复后能自动回来。

### 第三步：账务异常和运营调参

- 完善 `unknown` 上游扣费状态的查询和人工处理。
- 增加按组/模型/渠道商的路由与收益报表。
- 用真实数据调整权重、阈值、冷却时间和公平分流规则。

## 14. 暂不做的内容

- 不新建专属 Token、订阅关系或渠道商独立价格体系。
- 不跨服务档位兜底。
- 不把最低价作为唯一调度目标。
- 不首版引入复杂机器学习模型、全局实时优化器或独立钱包汇总缓存。
- 不首版接入开源模型质量平台、自动来源识别或复杂质量基准；高品质资格先由管理员白名单控制。
- 不自动处理无法确认的上游扣费，不做自动差价补贴或二次分佣。
- 不允许渠道商通过自定义脚本改变平台路由和结算。

## 15. 需要逐项确认的决策

以下内容不应由实现阶段自行猜测：

1. 多密钥失败隔离按 Channel 还是 `Channel + Key`；建议仅在能够可靠识别 Key 级故障时使用后者。
2. 亲和渠道失败或满载时是否打破亲和继续兜底。建议是，亲和不能高于可用性。
3. 流式请求已经返回部分内容后中断，按已知 usage 扣费还是全退后人工审查。

这些问题确认后，再把本草案拆成具体接口、字段和测试用例；在此之前不修改核心路由代码。
