# 渠道商入驻与审核

## 目标

渠道商资料不再在创建后立即生效。新申请必须经过管理员审核，审核通过前不能配置供给渠道，也不会进入公开页面或路由池。

本方案继续复用 `HubProvider`，不额外引入申请表，避免两套资料状态和迁移成本。

## 第一阶段：已实现

渠道商状态：

- `pending`：待审核。可查看和修改申请资料，不可管理供给渠道。
- `active`：已通过。可管理供给渠道，可进入公开页面和路由池。
- `rejected`：已驳回。展示驳回原因；修改资料后自动重新进入 `pending`。
- `disabled`：已禁用。供给退出路由池，不可修改、探测或上下架渠道；历史收益和提现入口保留。

审核记录保存在渠道商资料中：审核备注、管理员用户 ID、审核时间。驳回必须填写原因，通过、禁用和恢复的备注可选。

后端对以下写操作统一校验渠道商必须为 `active`：

- 创建、修改、删除供给渠道。
- 从上游拉取或预览模型。
- 手动发起渠道或模型检测。
- 修改模型检测端点。
- 单个或批量上架、下架模型。

公开渠道商首页、平台首页和路由选择继续只读取 `active` 渠道商。审核备注使用内部字段，不会进入公共身份数据结构。

## 第二阶段：已实现

渠道商资料增加两类联系信息：

- 审核联系方式：类型和内容必填，仅渠道商本人和管理员可见，不进入公开身份 API。当前支持 QQ、微信、Telegram、邮箱、手机号和其他，QQ 排在首位。
- 公开用户服务入口：可选，用于用户社群、QQ群、TG 群、客服、公告频道或邮箱，展示在渠道商首页。基础版只配置一个入口；二维码上传和多入口管理后续按实际需要增加。

渠道商说明继续使用原 `description` 字段，限制 1000 个字符。入驻和资料编辑界面明确提示支持 Markdown，并提供预览；展示时复用项目现有经过 DOMPurify 清洗的 Markdown 渲染器，不新增内容解析体系。

官网改为选填。子域名输入框只接受 `your-name` 这一类基础名称，页面会明确展示短码占位；新申请始终先分配一个稳定的四位短码，例如用户填写 `skyhope` 后得到 `skyhope-k7m2.llm-hub.store`。短码在创建后不再随机变化，避免审核期间链接反复失效。

官网归属和上游渠道使用是两个独立概念：没有官网、使用共享上游或借用其他中转渠道，不影响用户申请渠道商和创建供给。官网未验证时只对渠道商本人和管理员可见，公共首页使用平台分配的子域名，不向普通用户展示未验证官网；验证通过后，官网作为已认证的官方链接公开展示。

官网归属支持三种方式：

1. 管理后台截图：内测阶段推荐。截图必须同时显示浏览器地址栏和已登录的管理页面，页面提示遮挡 API Key、余额、订单等敏感信息；截图由管理员人工审核，不自动通过。
2. DNS TXT：在 `_llm-hub-verification.<hostname>` 发布系统生成的验证值。
3. HTTP 文件：在 `/.well-known/llm-hub-provider-verification.txt` 发布系统生成的完整文本。

入驻表单直接提供“暂不验证”和“后台截图验证”两种选择。选择截图时，渠道商资料、私有截图和官网待审核状态通过同一个事务提交，管理员不会看到未完成的半条申请；DNS TXT 与 HTTP 文件保留在后续官网验证页面。

待审核页在后台截图已提交时只展示审核状态和凭证预览，不再显示空的上传框；需要替换时才展开文件选择。编辑申请复用入驻表单中的官网验证选项：官网变更、验证被驳回或用户主动更换截图时，资料、私有截图和官网待审核状态同样通过一个事务更新。已提交且未变更的截图会保留，不要求重复上传。

截图使用独立的私有凭证表和接口，限制 PNG、JPEG、WebP，最大 5 MB；只有申请人和管理员可以读取。现有提现二维码接口与渠道商、收款账户和提现资产生命周期绑定，不能复用。当前徽标仍使用外部 `logo_url`，官网验证截图也不作为公开徽标资源。

官网验证状态为 `unverified / pending / verified / rejected`。管理员通过渠道商申请时可选择是否同时确认官网：

- 不确认官网：渠道商仍可审核通过，继续使用带短码子域名，官网保持私有。
- 确认官网：人工截图进入 `verified`，DNS/HTTP 必须已经自动验证成功；如果基础名称未被占用，待审核渠道商升级为 `skyhope.llm-hub.store`。
- 已经启用的渠道商后来修改官网时，当前 API Base URL 不自动变化；官网重新验证后只恢复公开展示，避免破坏已有客户端配置。

因此子域名的固定时机是首次入驻审核通过：审核前完成官网验证并由管理员一并确认时，可以从带短码地址升级为无短码地址；审核通过后再补充官网验证，只更新官网认证状态，不改变现有子域名。

渠道商资料编辑不再允许自由修改已经生效的完整子域名。独立域名、旧子域名别名和主动换域名留到后续域名映射模块，不在本轮引入。

## 第三阶段：已实现

保留自定义上游站点归属验证能力，由管理员在“系统设置 > 运营设置 > 系统行为”中控制，默认关闭。关闭时，已审核通过的渠道商可以直接使用自定义 Base URL 创建、修改供给渠道或预览上游模型，同一个上游可以由多个渠道商使用；管理员渠道商列表会按规范化 origin 展示复用该上游的渠道商数和渠道数，供人工审核参考。

开启归属验证后，渠道商使用自定义 Base URL 前必须先完成归属验证，站点按规范化 origin 唯一认领：

- 归属范围为 `scheme + hostname + 非默认端口`。
- API 路径、查询参数和 API Key 不参与归属计算。例如 `https://relay.example/v1` 与 `https://relay.example/models` 属于同一个站点。
- 默认 `http:80` 和 `https:443` 端口会被移除，数字端口会先规范化，非默认端口会保留。
- 国际化域名会规范化为 punycode，避免 Unicode 与 ASCII 写法重复认领。
- 规范化 origin 最长 191 个 ASCII 字符，以兼容 MySQL 5.7 的旧索引限制；超长域名不进入基础版本。
- 不接受内嵌账号密码、IP 地址、`localhost` 或非 HTTP(S) 地址。
- 同一个 origin 只能归属于一个渠道商，数据库使用唯一索引保证并发申请时也不会重复认领。

以下情况无需验证：

- 项目内所有官方默认 Base URL。
- 项目内置的特殊官方上游标识。
- 使用标准 HTTPS 端口的微软托管 Azure AI 资源端点（`*.openai.azure.com`、`*.cognitiveservices.azure.com`、`*.services.ai.azure.com`）。HTTP、自定义端口以及其他自定义域名仍必须验证。免认证规则只由规范化 origin 决定，认领表单、渠道创建/编辑和迁移共用同一判断。

当前支持两种验证方式：

1. DNS TXT：在 `_llm-hub-verification.<hostname>` 发布接口返回的验证值。
2. HTTP 文件：在 `/.well-known/llm-hub-provider-verification.txt` 发布接口返回的完整文本。

HTTP 验证使用始终启用的公网访问保护，不受系统通用 SSRF 开关影响；DNS 解析结果会在实际拨号前再次校验，拒绝私网和保留地址。验证文件请求不跟随重定向，最大读取 4096 字节，并要求去除首尾空白后与验证值完全一致。

验证令牌使用系统加密安全随机源生成。待验证认领自创建起保留 24 小时，超时后自动释放；验证失败不会续期，避免单个渠道商长期占用他人站点。

站点验证不是一次性的网络放行。渠道商供给渠道的实际 HTTP、WebSocket、模型发现、异步任务轮询和视频结果代理均强制公网直连，每次重定向和实际拨号都会重新校验 DNS 结果，且不读取环境代理。渠道商供给不允许配置 HTTP/SOCKS 代理，也不允许覆盖 `Host` 请求头；平台自营渠道继续保留原有私网上游和代理能力。

基础版本暂不允许渠道商创建 Midjourney/MidjourneyPlus 供给，因为其请求和后台轮询链路尚未汇入统一出站策略；运行时也会拒绝历史或异常关联的渠道商 Midjourney 供给。平台管理员原有渠道不受影响。

渠道商中心只在归属验证开关开启时展示“上游站点”区块。待验证站点展示准确的 DNS/HTTP 配置和复制操作；验证成功后才能用于自定义供给渠道。官方上游无需提前添加。开关关闭时不渲染空区块。

归属验证关闭时，不执行历史认领迁移，也不会因为多个渠道商共享同一上游而阻断启动。归属验证开启时，迁移策略为：

- 已有渠道使用且只属于一个渠道商的自定义 origin，会迁移为 `legacy + verified`，不打断现有供给。
- 已有渠道中被多个渠道商共同使用的 origin，会迁移为 `conflict`，不会静默分配给任意一方。
- 已有认领记录与历史供给归属、状态不一致时同样迁移为 `conflict`，不会用待验证或其他渠道商的记录掩盖冲突。
- 发现历史冲突时启动迁移会明确失败，要求管理员在上线前清理测试数据并重新启动。当前未实现冲突裁决页面，因为系统尚未上线且没有需要保留的正式历史数据。

基础版本暂不实现定期复验、验证历史、DNS 自动配置、批量认领和管理员强制转移。已验证站点暂不允许渠道商自行删除，避免仍在使用时释放归属；后续可增加“无渠道引用时释放”的受控流程。

此开关只影响自定义上游归属校验，不改变渠道可用性检测、路由选择、收益归属或平台兜底。渠道商自己的渠道不可用时，仍按现有平台兜底逻辑选择其他可用渠道。

## 后续模块

第四阶段：按运营需要增加全局入驻开关和独立申请限流。目前仍保留一名用户只能创建一个渠道商的数据库唯一约束和通用关键接口限流。

暂不加入实名 KYC、人脸识别、营业执照 OCR、设备指纹或自动风险评分。

## 品牌与独立域名演进

基础阶段仍使用平台域名下的渠道商子域名，不实现自定义独立域名。未来需要支持总代理或品牌方时，单独引入 `Brand/Tenant` 和域名映射，不使用 `parent_provider_id` 把层级硬编码到渠道商表：

渠道商子域名属于渠道商自己的获客入口。普通用户在子域名控制台中不展示“成为渠道商”导航和命令菜单入口；直接访问子域名下的 `/provider/onboarding` 会跳转到平台根域名的入驻页面。该规则只做品牌入口隔离，不限制用户回到根域名申请；已经是渠道商的账号仍可访问自己的渠道商中心。

- `a.com` 映射到品牌首页。
- `xllm.a.com`、`skyhope.a.com` 分别映射到品牌下的渠道商。
- 品牌负责域名、展示和成员关系；平台继续负责账号、密钥、计费、路由和兜底。
- 域名决定品牌和流量入口，不改变供给收益归属。请求最终使用谁的渠道，收益就结算给谁。

总代理抽成、多级代理和跨层级结算暂不实现，避免在品牌与域名需求尚未验证时扩大账单复杂度。

## 验收流程

1. 普通用户提交渠道商资料，状态应为待审核，且不能创建供给渠道。
2. 管理员在渠道商管理页填写原因并驳回，用户能看到原因。
3. 用户修改资料，状态自动回到待审核，旧驳回原因被清除。
4. 管理员通过申请，用户可以创建、检测和上架供给渠道。
5. 管理员禁用渠道商，已有供给退出路由池，渠道商仍可查看历史收益。
6. 未填写审核联系方式的申请无法提交；渠道商本人和管理员可以查看该联系方式。
7. 公共渠道商接口和首页不包含审核联系方式，只展示可选的公开服务入口。
8. 渠道商说明中的 Markdown 在预览、审核和公开首页均安全渲染。
9. 新申请填写 `skyhope` 后获得稳定的 `skyhope-xxxx` 子域名；不验证官网也能通过渠道商审核并正常供给。
10. 官网未验证时不进入公共 API；截图只允许申请人和管理员读取。
11. 管理员审核截图并勾选官网确认后，待审核渠道商在名称可用时升级为无短码子域名；不勾选时保留带短码地址。
12. DNS TXT 和 HTTP 文件验证成功后，管理员可在渠道商审核时启用无短码子域名。
13. 默认关闭上游归属验证时，渠道商中心不显示空的“上游站点”区块，渠道商无需认领即可创建自定义上游渠道；管理员能看到该上游被多少渠道商和渠道复用。
14. 开启上游归属验证后，渠道商按 DNS TXT 或 HTTP 文件完成归属验证；未验证站点不能创建渠道。
15. 渠道商渠道提交代理、`Host` 覆盖或 Midjourney 类型时应被拒绝；平台自营渠道原有代理能力不受影响。
16. 待验证上游认领超过 24 小时后自动释放；同一站点的有效已验证认领仍只能属于一个渠道商。
17. 无论上游归属验证开关是否开启，渠道不可用时的平台兜底行为保持不变。
18. 普通用户从渠道商子域名进入控制台时看不到“成为渠道商”；直接访问子域名入驻路径会跳转到根域名，根域名入驻入口保持正常。
